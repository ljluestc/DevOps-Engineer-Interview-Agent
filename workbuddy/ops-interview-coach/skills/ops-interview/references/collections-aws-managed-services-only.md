## 面试官执行手册

1. **这套题考什么**：不是背 AWS 服务目录，而是**约束驱动的选型**。给定「只用托管服务」这条约束，候选人要能：
   ① 为每个组件指名一个托管服务；② 说出它**换掉了什么**、**换不掉什么**；③ 当没有托管答案时，
   **老实命名缺口**并给出两条路（自建 / 换一个更大的托管服务），而不是含糊过去。
2. **级别映射**：🟢 认得服务并能说用途 → 🟡 能读懂 / 写出「chosen vs rejected」对比表，含成本量级 →
   🔴 能就「托管带来的能力损失」做权衡（没有直方图的 SLO、没有 gang scheduling 的 GPU 队列、
   没有 K8s 对象备份的 DR），并为「未经验证的设计」定出验证顺序。
3. **反套路提问**（本批题的灵魂）：候选人报出一串托管服务时追问三句——
   「这个数字你测过还是推理的？」「这个服务**做不到**什么？」「不用它的话，你自建的那份要谁值班？」
4. **一条贯穿全批的判据**：**托管服务换掉的是「运维工时」，换不掉「语义」**。
   凡是候选人用托管服务去解决一个语义问题（幂等、事务、排队公平性、备份完整性），就是可以深挖的地方。
5. **评分**沿用五维：概念清晰 / 原理理解 / 排障方法 / 权衡到位 / 实战经验（见 [docs/STANDARD.md](../docs/STANDARD.md)）。

## 一、「只用托管服务」这条约束本身（10 题）

1. ☆ 🟡 有人给你一条架构约束：「每个组件都必须是 AWS 托管服务，指不出来的要写明缺口」。这条约束**买到了什么**、**卖掉了什么**？
   - 要点：买到——没有控制面要打补丁、没有第二套 IAM、故障域和 AWS 的 SLA 对齐、审计统一进 CloudTrail、
     人力从「运维 N 个系统」转成「配置与治理」；卖掉——**表达能力**（PromQL / 直方图 / 标签选择器、
     Velero 的命名空间级恢复、gang scheduling）、**可移植性**（换云要重写）、**按量计费的下限**
     （OpenSearch Serverless 最低约 $700/月，是整个 demo 的 8 倍）。判断句：*托管换掉运维工时，换不掉语义与表达力*。
2. ☆ 🟡 为什么「说不出托管服务时要把缺口命名出来」比「找一个勉强能用的托管服务顶上」更重要？
   - 要点：勉强顶上的后果是**设计里出现一个没人知道它不成立的假设**（例：用 CloudWatch agent 的 GPU 利用率
     顶替 DCGM 的 tensor-core 活跃度，结论直接反了）。命名缺口会强制做三件事：写下它的影响面、
     给出两条备选路、决定「现在接受 / 以后再解」。文档层面表现为一张表：
     `layer | AWS-managed option | what is left to you`。
3. 🟡 「托管」在 AWS 语境下至少有三档，请区分并各举一例，说明运维责任的差别。
   - 要点：① **全托管无实例**（DynamoDB、S3、Lattice、Backup）——只配策略；
     ② **托管实例 / 集群**（RDS、OpenSearch Service、ElastiCache、MSK、EKS 控制面）——仍要选规格、
     定维护窗口、管版本升级；③ **托管 add-on / capability 但跑在你的节点上**
     （`amazon-cloudwatch-observability`、AWS Load Balancer Controller、EKS managed Argo CD capability）——
     AWS 管版本，资源和故障域还是你的。第三档最容易被当成第一档，事故时才发现要自己看 Pod。
4. ☆ 🔴 一个团队说「我们全用托管，所以不需要 SRE」。请反驳。
   - 要点：托管去掉的是**安装与打补丁**，没去掉：容量与配额（OpenSearch 分片、Kinesis 分片、Lambda 并发）、
     成本（托管的计价模型就是新的容量模型）、**跨服务的失败组合**（RDS failover 掉连接池、
     ALB 目标注册的是 Pod IP）、SLO 与错误预算、变更与回滚、DR 演练、IAM 最小权限、
     以及「托管服务自己出事时你的降级路径」。托管把值班内容从「进程」换成「策略与依赖」。
5. 🟡 只用托管服务的架构，**故障演练**该怎么做？和自建栈有什么不同？
   - 要点：不同点是你不能 kill 进程，只能触发服务自己的故障原语：RDS **reboot with failover**、
     ElastiCache 手动 failover、把一个 AZ 的子网路由掐掉、撤掉 IRSA 注解模拟 403、
     用 AWS Backup **restore testing plan** 做真实恢复、把 NAT 网关删掉验证私有子网出网依赖。
     共同点：先写下「预期现象」，再演练，差异即缺陷。
6. 🟡 为什么「一个 NAT 网关而不是三个」是一个可以被接受的托管取舍，而「一个 AZ 的 RDS」通常不是？
   - 要点：NAT 只影响**出网**（拉镜像、调 AWS API），单 AZ NAT 失效时该 AZ 的 Pod 出网中断但服务仍可由其他
     AZ 承载，代价是省下约 $64/月；RDS 是**系统记录**，单 AZ 丢的是数据与可写性，不可逆。
     判据：**可重建 / 可绕行的组件可以省，持久且唯一的真相不能省**。
7. ☆ 🟡 同一个需求「把 TLS 证书管好」，托管与自建分别是什么，边界在哪？
   - 要点：托管 = **ACM** 签发 + 自动轮换，私钥不落到任何人手里，只能绑在 ALB / CloudFront / API GW 等 AWS
     终结点上；自建 = cert-manager + ACME，任意位置可用（Pod 内、mTLS、非 AWS 终结点），
     代价是一个控制器和一套 Secret。边界：**TLS 终结在 AWS 边缘 → ACM；终结在 Pod 里 → 你自己**。
8. 🔴 「只用托管服务」与「可移植 / 多云」是一对冲突约束。你怎么在同一份设计里给它们留位置？
   - 要点：把**接口层写成开放标准，把实现层交给托管服务**——Gateway API 的 `HTTPRoute` 由 AWS Gateway API
     Controller 编排到 VPC Lattice（换云换控制器不换清单）、OpenTelemetry SDK 埋点由 ADOT 收集进 X-Ray
     （换后端不换代码）、Kubernetes 清单 + Kustomize 保持 EKS/kind 双跑、Terraform 模块化。
     反例：直接写 CloudWatch 专有 metric 查询、把业务逻辑写进 Step Functions。
9. 🟡 评审一份「AWS-only 目标架构」时，你会先问哪三个问题？
   - 要点：① **哪些是已经建成的、哪些只是目标？**（来源文档用绿点标出 Terraform 真正 provision 的 5 项，
     其余 21 项是目标）② 每个选择**拒绝了什么**、理由是成本还是语义？③ 哪些数字是**测出来的**？
     没有这三问，架构图只是服务图标的排列。
10. 🔴 一份 26 个服务的目标架构里，有两个服务「图上有、代码里没有、也没人写过针对它的东西」（这里是 Fargate 与 DynamoDB），还有三个是账号级的（GuardDuty / Config / CloudTrail）。你怎么处理这五个？
    - 要点：前两个降级为**待验证假设**，写明「因为负载形状像，不是因为写过代码」，并给出验证动作
      （Fargate 起一个 burst profile 实测冷启动；DynamoDB 用 `PutItem` + `attribute_not_exists` 写幂等键的原型）；
      后三个**从 landing zone 继承**而不是在应用仓库里声明，否则每个应用重复声明账号级控制，
      漂移与权限都会失控。这道题考的是**「诚实的架构图」**：图上的东西要标明成熟度。

## 二、目标架构与选型表：26 个服务，每个都要说出「换掉了谁」（14 题）

11. ☆ 🟢 一个请求从浏览器到 Pod，在这套架构上依次经过哪些 AWS 组件？哪一跳是今天唯一真实存在的？
    - 要点：Route 53（apex + 健康检查）→ CloudFront（边缘 TLS + 缓存，WAF/Shield 挂载点）→ WAF → ALB（ACM 证书）
      → **Pod IP**（不是节点）→ 应用 → OpenSearch（SigV4）/ RDS MySQL，热读走 ElastiCache。
      今天真实存在的只有 **ALB → Pod** 这一跳。追问：为什么 ALB 能直接把 Pod IP 注册进目标组？
      因为 Ingress 用 `target-type: ip`，而这依赖 **VPC CNI 给每个 Pod 一个可路由的 VPC 地址**。
12. ☆ 🟡 `target-type: ip` 与 `instance` 有什么区别？它把哪些后续选择锁死了？
    - 要点：`instance` 模式注册节点 + NodePort，多一跳 kube-proxy，滚动更新时摘流粒度是节点；
      `ip` 模式直接注册 Pod IP，少一跳、就绪探针与目标组健康检查对齐、支持 Fargate。
      锁死的是 **CNI 选择**：换成 Cilium 替换 VPC CNI 后 Pod IP 不再是 VPC 地址，这条路就断了——
      这正是「Cilium mesh 在本架构被拒」的真实原因，不是功能不够。
13. 🟡 ALB / NLB / API Gateway / ingress-nginx 四选一，各自的决定性理由是什么？
    - 要点：**ALB** — L7 路径与 Host 规则、ACM、WAF 挂载、Pod IP 目标，约 $16/月 + LCU，Kubernetes Ingress 的默认答案；
      **NLB** — L4、静态 IP、PrivateLink、极高连接数，gRPC/TCP 或需要固定 IP 时才用；
      **API Gateway (HTTP API)** — 每消费者的 key、限流、用量计划，约 $1/百万请求，**只有当租户与配额要在网关层强制时才值**
      （本例租户已在应用内强制，付这笔钱买不到东西）；**ingress-nginx** — 多服务共享一个 LB，省 LB 钱但多一个你自己升级的组件，
      服务数超过约 5 个再回头看。
14. ☆ 🟡 EKS / ECS on EC2 / Fargate / 裸 EC2 + Docker：这套系统为什么选 EKS？什么情况下你会推翻它？
    - 要点：选 EKS 的理由是**清单与本地 `kind` 一致**（同一套 YAML、DaemonSet、IRSA），代价是控制面约 $73/月 + 节点；
      ECS 更省控制面钱但要重写全部清单、丢掉本地对等环境；Fargate 适合**突发或不可信负载**（按 Pod 计费、
      无节点补丁），但**没有 DaemonSet、没有特权 Pod**，所以 CloudWatch agent / 设备插件这类都跑不了，
      只能作为 burst profile；裸 EC2 丢掉滚动更新、探针和 IRSA。推翻条件：团队没有 Kubernetes 投入，
      或工作负载是少数长期服务——那 ECS 的总拥有成本更低。
15. ☆ 🟡 RDS MySQL Multi-AZ vs Aurora vs DynamoDB 作为「系统记录」，本例为什么是 RDS？
    - 要点：决定性因素是**事务语义**：写路径要把业务行和 outbox 行**在一个事务里提交**，还要 Flyway 迁移与 JOIN；
      DynamoDB 有事务但没有 JPA / Flyway / JOIN，等于重写数据层。Aurora 更快的 failover（约 30 秒）
      和 15 个读副本对「一个写入者 + 一个 outbox」是过剩，成本 2–3 倍。RDS Multi-AZ（db.t4g.medium 约 $100/月）
      与本地 Compose 是同一个引擎，迁移成本最低。
16. 🔴 把搜索投影放在 OpenSearch Service 上而不是自建 Elasticsearch，除了「不想升级」还有一个更硬的理由，是什么？
    - 要点：**认证模型**。OpenSearch Service 支持 SigV4，配合 IRSA 后集群里**没有任何搜索凭据**；
      换成自建 Elasticsearch 就要回到用户名密码 / API key（又是一个 Secret），还要改客户端
      （应用现在用 `opensearch-java` + SigV4）。另一条理由是**投影是可丢弃的**：它能从 MySQL 重建，
      所以「托管 + 不备份」是自洽的取舍。
17. 🟡 OpenSearch Serverless 在这里为什么被拒？这反映了托管服务选型里的哪类陷阱？
    - 要点：OCU 的**最低消费**约 $700/月，是整套 demo 的 8 倍。陷阱是**「更托管 ≠ 更便宜」**：
      Serverless 类产品通常有容量下限或最小计费单元，只有在**峰谷比大且规模够大**时才划算；
      小规模下按实例计价的托管集群反而便宜一个数量级。选型时要先算**下限**，再算单价。
18. ☆ 🟡 幂等键存在哪？为什么不是 RDS 的一张表，也不是 Redis 的 `SET NX`？
    - 要点：选 **DynamoDB**：`PutItem` + `attribute_not_exists(pk)` 条件写就是这个功能的全部，
      再加 TTL 自动过期，单数毫秒点读，无热行锁。RDS 表的问题是**热行的行锁会和 outbox 事务争用**；
      Redis `SET NX` 的问题是**failover 可能忘记一个键**，于是放过一次重复——而幂等键丢一次就等于没做。
      判据：**幂等是正确性，不能建在「大概率不丢」的存储上**。
19. 🟡 缓存为什么必须是 ElastiCache 而不是进程内 Caffeine？key 设计上有一个必须的字段是什么？
    - 要点：三个副本 = 三份不一致的进程内缓存，且扩缩容即失效；ElastiCache（cache.t4g.micro 约 $12/月）
      是共享的一份，支持 TTL 与 keyspace 事件。key **必须带租户 ID**，否则多租户下会跨租户命中——
      这是缓存类最常见的越权漏洞。
20. ☆ 🟡 NAT 网关 vs VPC 端点，钱花在哪里、怎么决定？
    - 要点：NAT 约 $32/月 + **$0.045/GB**，按流量计费；接口端点约 $7/月/个，走 AWS 内网不计 NAT 流量费。
      决策法：**看流量构成**——镜像拉取（ECR）与对象读写（S3）通常是私有子网的大头，
      所以先加 ECR + S3 端点（S3 是网关端点，更便宜），STS 视调用量。这类题要求候选人给出
      「多少 GB/月以上加端点划算」的量级估算，而不是背概念。
21. 🟢 为什么镜像放 ECR 而不是 Docker Hub？请给出一个真实发生过的故障形态。
    - 要点：ECR 在同 region 内拉取、IRSA 认证、推送即扫描、支持**不可变 tag**与生命周期策略（保留最近 10 个）；
      Docker Hub 的**匿名/免费额度限流**会在节点批量扩容或 CI 重试时触发 `ImagePullBackOff` —— 
      这是本地 `kind` 实验室真实踩过的坑。且跨互联网拉取还要经 NAT 付流量费。
22. 🟡 「不可变 tag」在这套架构里承担了哪两个职责？
    - 要点：① **回滚的载体**——`kubectl rollout undo` 指向的是一个仍然存在且内容不变的 tag，
      所以「镜像不需要备份，tag 就是制品」；② **供应链完整性**——tag 不能被覆盖，
      扫描结果与运行内容一一对应。配套缺口：今天**扫描结果只在控制台可见、不阻断发布**，
      目标是加一个策略门禁。
23. 🔴 请为这套架构画出「丢掉一个可用区」时每一层的行为，并指出**应用必须自己承担**的那一小部分。
    - 要点：ALB 把该 AZ 的目标标记不健康、其余两个 AZ 承载；第三个副本被重新调度、节点组补节点；
      RDS Multi-AZ **端点不变**地 failover；OpenSearch 的 zone-aware 副本顶上；ElastiCache 提升副本。
      应用要做的两件事：**连接池必须把 failover 时断掉的连接还回去**（否则拿到坏连接），
      **drain / 重试逻辑要能重试而不是把整批标记失败**。这题的价值在于「托管做了 90%，剩下 10% 在你代码里」。
24. 🔴 这份目标架构用了官方 AWS Architecture Icons（2026 年 7 月版）绘图。从合规角度这里有什么注意事项？
    - 要点：AWS 图标条款要求**原样使用、不得修改**（不改颜色、不加元素、不做成自己的 logo），
      并注意不得暗示 AWS 背书。工程上的做法是把图标目录固定在仓库里、由脚本生成图（可复现），
      并在文档里注明版本与用法。延伸问：企业文档里用云厂商图标 / 商标，该由谁签字？

## 三、身份与密钥：IRSA、Pod Identity、Secrets Manager（10 题）

25. ☆ 🟢 IRSA 的完整链路是什么？请按「谁签发、谁验证、换到什么」讲一遍。
    - 要点：ServiceAccount 上注有 role ARN → EKS 的 webhook 给 Pod 注入一个**投影的 OIDC token**
      （有受众、有过期）→ SDK 调 **`sts:AssumeRoleWithWebIdentity`** → STS 用集群的 **OIDC provider** 验证签名与
      受众 → 返回**临时凭据** → 用它对 OpenSearch 请求做 SigV4 签名。结果：集群里没有任何长期密钥。
26. ☆ 🔴 IRSA 配错时的失败形态为什么特别难查？给出你的排查顺序。
    - 要点：**失败是静默的**——ServiceAccount 少了注解不会启动报错，SDK 会沿凭据链继续往下找
      （节点角色 / 无凭据），于是第一个信号是**数据面中途的一个 403**（例如一次 drain 打到一半）。
      排查顺序：`kubectl describe sa` 看注解 → Pod 内看 `AWS_ROLE_ARN` / `AWS_WEB_IDENTITY_TOKEN_FILE`
      环境变量是否被注入 → 看信任策略里的 OIDC issuer 与 `sub`（`system:serviceaccount:<ns>:<sa>`）是否匹配
      → CloudTrail 看 `AssumeRoleWithWebIdentity` 有没有发生、失败原因 → 最后才看资源侧策略。
27. 🟡 EKS Pod Identity 和 IRSA 有什么区别？本例为什么仍留在 IRSA？
    - 要点：Pod Identity 不需要给每个集群建 OIDC provider、跨账号更简单、用一个 agent（DaemonSet）发凭据；
      IRSA 依赖集群 OIDC，信任策略更啰嗦但**不要求 DaemonSet 能跑**（Fargate 场景相关）。
      本例保留 IRSA 只是因为 **ALB controller 的官方文档假定 IRSA**；新集群两者等价，选 Pod Identity 更省事。
28. ☆ 🔴 数据库口令的四种做法——Kubernetes Secret、External Secrets Operator、Secrets Store CSI Driver、
    应用自己读 Secrets Manager——请排序并说明本例为什么选最后一个。
    - 要点：Kubernetes Secret 是 **etcd 里的 base64**，任何有该命名空间 `get secret` 的人都能读，且没有轮换；
      ESO 与 CSI driver 的产物**仍然是一个 Kubernetes Secret**（CSI 也可只挂载文件，但多数部署仍同步 Secret），
      本质是**管理一份副本，而不是消除副本**，代价是一个控制器 + 一套 CRD；
      应用自己在启动时用 IRSA 角色读 Secrets Manager（本例的 `AwsSecretsEnvironmentPostProcessor`，约三十行），
      **副本不存在**、每次读取都有审计、轮换由服务负责。反方观点要给分：**多语言集群**里让每种语言都写一遍
      不现实，这时 ESO/CSI 是对的。
29. 🟡 「Secrets Manager 每个密钥约 $0.40/月」看起来便宜，什么情况下它会变贵、怎么设计？
    - 要点：按**密钥数 × 环境数 × 租户数**膨胀（每租户一个密钥 × 三套环境很快上千），
      再加每万次 API 调用的费用。设计：一个密钥装一个 JSON（多字段），按服务而不是按字段建；
      非敏感配置放 **SSM Parameter Store**（免费档，但没有轮换）；应用**缓存**取到的值并在轮换事件时刷新，
      不要每次请求都调 API。
30. 🟡 Secrets Manager 的「轮换」对应用提出了什么要求？只把密钥换掉会发生什么？
    - 要点：轮换通常是 **AWSCURRENT / AWSPENDING / AWSPREVIOUS 三个版本**的多步过程；
      应用必须能**在不重启的情况下重新读取**，或者至少在认证失败时重试一次读取新版本；
      只换密钥而应用缓存了旧值 → 轮换窗口内认证失败雪崩。数据库侧要支持**双用户交替**策略以避免窗口期。
31. 🟢 为什么「节点实例角色」不能当作 Pod 的权限来源？
    - 要点：节点角色是**节点上所有 Pod 共享**的权限，等于把最小权限彻底作废——任意一个被攻破的 Pod
      都能拿到 OpenSearch / S3 权限。生产上还应**屏蔽 Pod 访问 IMDS**（跳数限制 / 强制 IMDSv2 /
      网络策略），否则即便配了 IRSA，Pod 仍能绕过去取节点凭据。
32. 🔴 你要给「应用自己读 Secrets Manager」这条路补上最小权限策略，会写成什么样？
    - 要点：`secretsmanager:GetSecretValue` **限定到具体 secret ARN**（含版本阶段条件 `AWSCURRENT`），
      若用 KMS CMK 加密还需 `kms:Decrypt` 限定到该 key，并在 key policy 上加 `kms:ViaService` 条件；
      角色的信任策略把 `sub` 限死到具体 ServiceAccount；再用 CloudTrail 对该 secret 的读取建告警
      （非预期主体读取即告警）。
33. 🟡 把「谁在调用我」这个问题从证书换成 IAM 主体（VPC Lattice auth policy / SigV4），有什么优点与代价？
    - 要点：优点——身份与 AWS 授权模型统一（策略、条件键、CloudTrail 审计），不需要签发与轮换网格证书，
      跨 VPC / 跨账号天然可用；代价——**只在 AWS 内有效**（VM、其他云、本地开发要另想办法）、
      粒度是 IAM 主体而不是工作负载证书里的 SPIFFE 身份、且策略生效路径依赖服务端支持。
34. 🔴 「集群里没有任何 Kubernetes Secret」这个目标，现实里最难消除的是哪一类？
    - 要点：**镜像拉取凭据（imagePullSecrets）**、第三方 SaaS 的静态 token（没有 IAM 可用）、
      以及**控制器自己需要的凭据**。ECR 可以靠节点/Pod 角色免掉 pull secret；第三方 token 只能放
      Secrets Manager 再由应用读；控制器类要评估它是否支持 IRSA。结论：目标是**尽可能少**而不是零，
      并且对剩下的每一个写明「为什么它必须存在」。

## 四、可观测性：CloudWatch、AMP + Managed Grafana、还是自建（16 题）

35. ☆ 🟡 在「只用托管」的前提下，可观测性有三个候选：CloudWatch（+ X-Ray）、AMP + Managed Grafana、自建 kube-prometheus-stack。请把它们摆成一张表。
    - 要点：**CloudWatch + X-Ray** — 指标 / 日志 / 告警 / 追踪一站式，EKS 侧靠 `amazon-cloudwatch-observability`
      add-on（Container Insights），告警写在 Terraform 里与资源同处；日志约 $0.57/GB、
      自定义指标 $0.30/指标/月。**AMP + Managed Grafana** — 仍是托管，但买回 PromQL、**真直方图**、
      标签选择器，代价是按样本计费 + 一个托管采集器 + 第二块看板。**自建** — 唯一不是托管服务的选项，
      要自己升级 Prometheus/Loki/Tempo 并保证 Prometheus 单点丢失时数据不丢。
36. ☆ 🔴 选 CloudWatch 具体**丢掉**了哪两样东西？它们各自把什么 SLO 变成了什么？
    - 要点：① **没有直方图** → 延迟 SLO 从「p95 < 300ms」退化成「窗口内最大值 / 或近似统计」，
      分位数不可加、跨维度聚合失真；② **没有标签选择器** → 每个比率都要写成 `SUM(SEARCH(...))` 的
      指标数学表达式，可读性与可维护性下降，且新维度要改表达式。结论句：
      **「延迟 SLO 必须是真 p95 的那一天，就是换 AMP 的那一天」**。
37. ☆ 🟡 CloudWatch 自定义指标按「每个指标 $0.30/月」计费，这条计费规则如何把一个老问题变成账单问题？
    - 要点：老问题是**基数爆炸**（自建 Prometheus 里表现为 scrape 超时、`up=0`、TSDB 内存涨）；
      在 CloudWatch 里，**每一个不同的维度组合就是一个独立指标**，于是一个未做归一化的 `uri` 标签
      （含 ID、查询串）直接变成发票上的行数。防御不变但要前移到应用内：
      用 Micrometer 的 **`MeterFilter` 把 `uri` 归一到已知路由**（`/api/products/{id}`），
      发布前就截断，而不是靠采集端 `metricRelabelings` 丢弃。
38. 🟡 从 Prometheus 迁到 CloudWatch，`rate(http_requests_total{status=~"5.."}[5m])` 这类查询怎么表达？会失去什么？
    - 要点：CloudWatch 侧用 Metrics Insights（类 SQL：`SELECT SUM(...) FROM ... WHERE ... GROUP BY ...`）
      或指标数学 `SUM(SEARCH('{ns,dim} MetricName="..."', 'Sum', 300))`，比率用 `m1/m2` 表达式；
      失去的是**正则标签匹配的灵活性**与**即席探索**（没有 label 枚举、没有 `topk`、没有 `histogram_quantile`），
      以及把告警表达式和录制规则放在一个文件里版本化的体验（CloudWatch 侧靠 Terraform 补回来）。
39. ☆ 🔴 这套系统定了四条 SLO。请评价它们的「可测量性」，并指出哪一条在 CloudWatch 下最难兑现。
    - 要点：四条为——搜索可用性（非 5xx 比例）99.9% / 30 天滚动（约 **43 分钟**错误预算）；
      搜索延迟（< 300ms 的比例）99% / 30 天；**索引新鲜度**（outbox 行提交到标记 sent 的 p99 < 60 秒 / 7 天）；
      **索引正确性**（MySQL 计数与索引计数的对账差 = 0，每次运行）。最难的是**延迟**：它需要分位数，
      而 CloudWatch 没有直方图；新鲜度的 p99 同理。正确性那条最好，因为它是布尔的——
      「差值不是预算，是 bug」。
40. ☆ 🟡 为什么用**双窗口 burn-rate**告警而不是「错误率 > 1% 持续 5 分钟」？
    - 要点：单窗口要么太灵敏（一分钟抖动就呼人）要么太迟钝；burn-rate 把告警锚定在**错误预算的消耗速度**上，
      并要求**快窗口与慢窗口同时成立**才呼人（快窗确认「现在正在烧」，慢窗确认「不是一次抖动」）。
      效果：持续 1.4% 的错误率几分钟内呼人，单次 5xx 永远不呼人。配套是**错误预算策略**：
      预算烧完后下一个迭代做可靠性工作——这条要产品一起签字，否则形同虚设。
41. 🔴 告警路由从 Alertmanager 换成 CloudWatch 告警 + SNS 后，具体丢了哪三个能力？怎么补？
    - 要点：丢了 **分组（grouping）**（一次故障产生的 N 条告警合成一条）、**抑制（inhibition）**
      （critical 存在时压住同范围的 warning）、**静默（silence）**（变更窗口内临时闭嘴）。
      补法：在 SNS 之后放一层（PagerDuty 的 event rules / EventBridge + Lambda 去重）、
      用**复合告警（composite alarm）**表达「A 且非 B」来近似抑制、变更窗口用告警动作的启用/禁用
      或复合告警里的抑制条件。追问：如果文档一边写「CloudWatch 是选定方案」、
      一边在路由小节里描述 AMP Alertmanager 的分组与抑制，你会怎么处理这份不一致？
      （答：这就是选型代价没有被贯彻到落地细节的典型症状，要么补上述替代，要么承认路由层仍需 AMP。）
42. 🟡 什么样的告警应该呼人、什么样的只应该开工单？请用这套系统的例子说明分级判据。
    - 要点：**呼人（critical）**= 用户可见且正在恶化、且有人能在 30 分钟内缓解：可用性快速燃烧、
      outbox drainer 消失、连接池超时、探针失败、低于 PDB。**工单（warning）**= 预算在慢速消耗或容量趋紧：
      慢速燃烧、延迟 SLO、积压增长、GC 暂停、HPA 顶到上限。**只上看板（info）**= 录制规则与容量趋势。
      判据三问：用户感知到了吗？会自己恢复吗？现在有可执行的缓解动作吗？
43. 🟡 X-Ray 与 Tempo、ADOT 在这套「AWS-only」里各自的位置是什么？
    - 要点：埋点用 **OpenTelemetry SDK**（保持厂商中立）→ 收集用 **ADOT**（AWS 自己的 OTel 发行版，EKS add-on）
      → 存储与分析用 **X-Ray**（服务地图、Application Signals），Managed Grafana 可以用 X-Ray 数据源读它。
      Tempo 被拒的原因与 Prometheus 一样：它是你要运维的存储。这个组合的好处是
      **换后端不用改代码**，只换 collector 的 exporter。
44. 🟡 日志侧「CloudWatch Logs vs Loki」的取舍是什么？为什么日志格式的选择让这个决定变得便宜？
    - 要点：CloudWatch Logs 无需自建存储、用 Logs Insights 查询、约 $0.57/GB 摄入；
      Loki 按标签索引、存储便宜，但要 S3、ruler 与升级。让决定变便宜的是**应用输出结构化 JSON 到 stdout**：
      同一份日志在两边都能用，迁移只是换采集器（`aws-for-fluent-bit` ↔ promtail/alloy）。
      **日志格式是可移植性的真实边界，存储不是。**
45. 🔴 CloudWatch Logs 的成本怎么压？请给出四个层次的动作。
    - 要点：① **源头**——降低无用日志（把 DEBUG 关掉、把每请求一行的访问日志采样）；
      ② **摄入**——用 Fluent Bit 过滤 / 丢弃健康检查行，敏感字段脱敏后再送；
      ③ **保留**——按日志组设置保留期，冷数据导出到 S3（或用 Infrequent Access 日志类）；
      ④ **查询**——Logs Insights 按扫描量计费，先缩时间窗、再加过滤。追加：把
      「每 GB 日志对应多少请求」做成容量指标，日志费用才可预测。
46. 🟡 `amazon-cloudwatch-observability` add-on 到底在集群里放了什么？它是「托管」的哪一档？
    - 要点：它安装 CloudWatch agent（DaemonSet）与 Fluent Bit，采集 Container Insights 指标与日志，
      并可采集 NVIDIA GPU 指标；属于第三档托管——**AWS 管版本与配置模型，Pod 与资源占用仍在你的节点上**，
      也会出现在你的告警与容量预算里。追问：它挂了谁告警？（答：用 add-on 健康 + 指标缺失告警，
      即 `absent()` 类语义；在 CloudWatch 侧用「无数据时告警」的处理策略。）
47. 🟡 micrometer **推送**到 CloudWatch 与 Prometheus **拉取**，在运维上有什么实质差别？
    - 要点：推送模式下**没有 scrape 目标**，也就没有 `up` 指标可用——「应用还活着吗」要靠别的信号
      （心跳指标、ALB 目标健康、日志）；短命 Pod 的指标不会漏（拉取模式可能在两次 scrape 之间死掉），
      但**指标丢失是静默的**；另外推送把发布决定权交给应用（基数与成本控制必须在应用内做，见第 37 题）。
48. 🔴 Container Insights 之外，这套架构里「谁的指标最容易被忘记」？
    - 要点：**托管服务自己的指标与配额**：RDS 的连接数 / CPU credit / 复制延迟、OpenSearch 的
      JVM 内存压力与分片数、ALB 的 `TargetResponseTime` 与 5xx（区分 ELB 5xx 与 Target 5xx）、
      NAT 的 `ErrorPortAllocation`、ElastiCache 的 evictions、DynamoDB 的节流。
      这些不需要装任何东西就有，却最常缺告警——因为它们不在「应用指标」的心智模型里。
49. 🟡 「一块看板还是两块看板」为什么是一个真实的运维论点？
    - 要点：值班时**多一块看板就多一次上下文切换和一次「在哪看」的犹豫**；
      因此本例选择把 JVM Micrometer 那套面板（堆、GC 暂停、线程、Hikari）**重建成 CloudWatch dashboard**，
      而不是把 Grafana JSON 导进 Managed Grafana——后者更快但留下第二块看板。
      反方：如果团队已经活在 Grafana 里，那第二块看板成本是零、第一块才是新负担。**看板的成本是人的，不是钱的。**
50. 🔴 如果让你把这套可观测性从 CloudWatch 迁到 AMP + Managed Grafana，迁移顺序怎么排？哪一步最容易出事？
    - 要点：顺序——① 先并行采集（AMP managed collector 抓 exporter，CloudWatch 不停）；
      ② 迁录制规则与告警规则（rule groups namespace），**在 AMP 里只发通知不呼人**跑两周对账；
      ③ 比对两边的同一 SLI 数值差异（尤其是分位数与计数口径）；④ 切换呼人路径；⑤ 下线 CloudWatch 自定义指标。
      最容易出事的是**第三步的口径差异**：CloudWatch 的窗口最大值和 Prometheus 的 `histogram_quantile`
      本来就不是同一个数，直接切会让 SLO 看起来「突然变差」。

## 五、备份与恢复：AWS Backup 覆盖到哪，以及被诚实命名的缺口（13 题）

51. ☆ 🟡 请把这套系统的「要恢复的东西」列成一张表，并给每一项指定 AWS 托管服务与恢复点。
    - 要点：系统记录（RDS）→ **AWS Backup** + 自动备份 / PITR，恢复点约 5 分钟；
      持久卷 → **AWS Backup** 按标签做 EBS 快照 / EFS 备份（例：每日、保留 35 天）；
      **搜索投影 → 不备份**（可由 `POST /api/admin/rebuild` 从 MySQL 重建）；
      镜像 → **ECR** 不可变 tag + 生命周期策略（制品就是 tag）；对象 → **S3** 版本控制 + Object Lock；
      密钥 → **Secrets Manager** 的版本；控制面 etcd → **EKS 自己负责**；
      命名空间级 API 对象 → **git + Terraform**，由流水线应用。
52. ☆ 🔴 「投影不备份」这个决定怎么论证？什么情况下它会翻车？
    - 要点：论证——投影是**派生数据**，备份它等于制造第二个可能过期的副本；只要重建路径存在并且被定期演练，
      RTO = 重建时间。翻车条件：① 重建耗时远超容忍（亿级文档重建几小时）；
      ② 重建依赖的源已经不完整（outbox 被清理、历史无法回放）；③ 重建过程本身要打满 RDS，
      在事故中形成二次伤害。所以这条决定必须附带一个**实测的重建时长**——文档里恰恰没有测过。
53. ☆ 🟡 AWS Backup 的「restore testing plan」为什么被称为整页最有价值的一项？
    - 要点：它把**「我们有备份」这个信念变成一个被度量的事实**——按计划把恢复点还原到隔离目标，
      并报告是否在你声明的窗口内完成。没有它，备份的成功率指标只证明「写成功了」，不证明「能还原」。
      面试延伸：你上一次真正演练恢复是什么时候？RTO 是测出来的还是写在文档里的？
54. 🟡 AWS Backup Audit Manager 解决的是哪一类「看不见的风险」？
    - 要点：**覆盖缺口**——有资源命中了备份选择的标签口径、却没有恢复点（或没打标签因而根本不在计划里）。
      它把「那个谁都没打标签的卷」在事故**之前**找出来。配套实践：备份选择用标签驱动，
      并在 IaC 里强制打标签（tag policy / Config 规则），否则漏标是常态。
55. ☆ 🔴 「AWS 没有任何服务备份 Kubernetes API 对象」——这个缺口具体会漏掉什么？
    - 要点：① **控制器创建、没人写下来的对象**：Ingress 生成的 ALB、Gateway API 控制器生成的 Lattice 服务、
      ServiceAccount token、HPA 的状态；② **事故中手改、事后没提交**的东西；
      ③ **PVC → PV 的绑定关系**：AWS Backup 还原了 EBS 卷，但**没有任何 AWS 服务会重建指向它的 PVC**。
      第三条最致命，因为它让「卷还在」与「应用能用」之间出现断层。
56. ☆ 🔴 面对这个缺口，只有两条路。请各自说明代价，并说出你会怎么选。
    - 要点：**路一（AWS-only，本例所选）——把缺口变成空的**：所有对象进 git，流水线里加**漂移检查**，
      集群里出现仓库没有的对象就失败。代价：漂移检查要自己写、控制器生成的对象需要显式忽略清单、
      恢复 = 重放一次流水线（RTO 是一次流水线时间）。**路二——上 Velero**（不是 AWS 服务）：
      能按命名空间恢复集群里真实存在的东西，代价是一个控制器 + CRD + 带快照权限的 IAM 角色 +
      版本边界（1.10 改过一次参数名）+ 备份可能与 git 悄悄漂移。选择判据：
      **集群状态能不能从一个 commit 完整重建**——能，选路一；不能（多数集群其实不能），Velero 才是对的答案。
57. ☆ 🟡 在采用任何一条路之前，文档要求先做一个实验。是什么？为什么它比备份本身更值钱？
    - 要点：**把线上集群的命名空间级对象导出，和 `k8s/` 里声明的做 diff**。
      出现在集群、不在仓库里的东西，要么该提交、要么该删除。这个 diff 直接回答
      「我的缺口到底有多大」，而在不知道缺口大小的情况下选备份方案，是在赌。
58. 🟡 Velero 的快照路径和 AWS Backup 的 EBS 快照，底层是同一个 EC2 API。那么两者的真实差别在哪？
    - 要点：差别不在快照本身，在**编排与权限**：AWS Backup 提供计划、保管库、跨区域 / 跨账号复制、
      合规锁定、审计与恢复测试；Velero 提供**与 Kubernetes 对象一致的恢复单元**（命名空间、标签选择）。
      另外来源文章给 Velero 的 IAM 策略权限过宽（例如 `ec2:DeleteSnapshot` 不加条件），
      收窄时要注意**条件键在不同 EC2 动作上的支持不一致，写错会静默失败并让快照过期停摆**。
59. 🔴 「恢复不是故障转移」——请解释这句话在 DR 设计里的含义。
    - 要点：恢复（restore）是**把数据搬回来**，需要时间、需要目标环境、常常伴随数据丢失窗口（RPO）；
      故障转移（failover）是**把流量切到已经在运行的副本**，以持续成本换取接近零的 RTO。
      把备份当作高可用方案，会在事故中发现 RTO 是小时级。对应到本例：RDS Multi-AZ 是 failover，
      AWS Backup 是 restore，两者都要有，且都要演练。
60. 🟡 跨区域怎么办？在只用托管的前提下，最小可行的跨区域恢复设计是什么？
    - 要点：AWS Backup 的**跨区域复制**（RDS/EBS/EFS 恢复点复制到第二区域）、
      **S3 跨区域复制 + 版本控制**、**ECR 跨区域复制**（镜像必须在目标区域可拉）、
      Secrets Manager 的**多区域复制**、以及 IaC 能在第二区域从零建出 VPC/EKS。
      RTO 的决定项通常不是数据，而是**镜像与基础设施是否就位**——这三样没提前复制，恢复就卡在起点。
61. 🟡 S3 版本控制 + Object Lock（治理模式）在恢复设计里解决的是哪个具体威胁？
    - 要点：**覆盖与删除**（包括误操作与勒索）。版本控制让每次写都留旧版本，Object Lock 让保留期内
      **连有权限的人也不能删**（治理模式允许特权角色绕过，合规模式不允许）。它对应的是
      「备份被同一套凭据一起删掉」这个经典失败——所以备份的**权限边界**要和生产分开。
62. 🔴 有人说「EKS 托管控制面，所以 etcd 不用管了」。这句话对在哪、错在哪？
    - 要点：对——**你确实拿不到也不需要 etcd 快照**，控制面的可用性与备份是 AWS 的责任；
      错——你仍然要为 etcd 里**内容**的丢失负责（对象定义、CRD、Secret），而 AWS 不提供对象级恢复；
      同时集群本身的**重建**（版本、add-on、身份映射、网络）要靠 IaC。
      所以在 EKS 上，「备份 etcd」这个任务变成了「保证集群可由代码重建 + 对象在 git 里」。
63. 🟡 这套系统今天实际拥有的恢复能力只有一项，是什么？这说明了什么？
    - 要点：只有 **`kubectl rollout undo` 回到一个不可变的 ECR tag**——它只能救「一次坏发布」，
      救不了数据丢失、误删命名空间、区域故障。说明：**没有 apply 的 DR 设计等于没有 DR**；
      面试里遇到漂亮的恢复方案，第一句该问「哪一部分已经存在并被演练过？」

## 六、GPU on EKS：托管边界在哪里断掉（13 题）

64. ☆ 🟡 在 EKS 上跑 GPU，请按层列出「AWS 托管给你什么」与「剩下的是你的」。
    - 要点：硬件与网络 → **EC2 加速实例、集群置放群组、EFA、Capacity Blocks**（你只负责选对）；
      驱动与容器工具链 → **EKS 加速 AMI 自带**，与 AMI 版本绑定（你负责 pin AMI）；
      **设备插件 / NFD / MIG manager / DCGM → AWS 什么都不给**，这些是 NVIDIA 的 DaemonSet；
      GPU 指标 → CloudWatch（通过 observability add-on）或 AMP + DCGM exporter；
      队列与配额 → **AWS Batch on EKS** 或 **SageMaker HyperPod**；
      **gang scheduling → EKS 本身没有**，要 Kueue / Volcano。两行没有 AWS 答案，且都对共享 GPU 集群是承重墙。
65. ☆ 🔴 当「谁来运维设备插件」这个答案不可接受时，正确的出路是什么？为什么不是再装一个 add-on？
    - 要点：出路是**换一个服务而不是换一个插件**——**SageMaker HyperPod** 把整个集群（含调度与
      「健康检查即替换节点」的循环）接管过去。理由：缺的是**调度语义与节点生命周期管理**，
      这不是一个 DaemonSet 能补的；再装插件只是把同一份运维责任换个名字。
      代价要说清：那是**另一套控制面**，和平台其余部分不同构。
66. ☆ 🟡 在 EKS 加速 AMI 上装 NVIDIA GPU Operator，哪两个开关必须关掉？关错了会怎样？
    - 要点：`driver.enabled=false` 与 `toolkit.enabled=false`——因为**加速 AMI 已经自带驱动与容器工具链**。
      重复安装是「让一个好好的 GPU 节点进入 crash loop、且永远不上报一个 `nvidia.com/gpu`」的头号原因。
      保留的是 NFD、GFD、device plugin、DCGM exporter、MIG manager 与 validator。
67. 🟡 「加速 AMI + 只装设备插件」「加速 AMI + 关掉驱动的 Operator」「通用 AMI + 全量 Operator」三条路怎么选？
    - 要点：只装设备插件——动的东西最少，驱动版本随 AMI 走，但 DCGM 与 MIG 要自己接；
      关驱动的 Operator——一个 Helm release 管住插件 / 指标 / MIG / NFD，代价是要理解 `ClusterPolicy` CRD；
      通用 AMI + 全量 Operator——驱动版本与 AMI 解耦、跨云同一套配方，但 Operator 要编译或下载驱动，
      更慢、更易错。**三条都不错，错的是在同一个节点上同时用两条。**
68. ☆ 🔴 为什么说「GPU 利用率」是一个会撒谎的指标？该看什么？
    - 要点：`utilization` 回答的只是**「最近一个采样窗口内是否至少有一个 kernel 驻留」**——
      一个整段时间都卡在访存上的 kernel 也报「忙」。该一起看：
      **tensor core 活跃度 `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE`**（贵的单元在干活吗）、
      **DRAM 活跃度 `DCGM_FI_PROF_DRAM_ACTIVE`**（是不是在搬字节）、
      NVLink / PCIe 吞吐（是不是被传输主导）、**功耗**（饿着的 GPU 是凉的，粗糙但诚实）。
69. ☆ 🔴 这套「AWS-only」文档在 GPU 指标这一处明确说「最便宜的 AWS 选项是错的」。请复述这个论证。
    - 要点：CloudWatch agent（observability add-on）能直接采 NVIDIA GPU 指标——**利用率、显存、温度、功耗**，
      集群里不用跑 exporter；但它**不发布 `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE`** 这类 profiling 序列，
      而那恰恰是上一题说「没有它就别信利用率」的那个指标。所以对 GPU 机队，正确默认是
      **AMP + 托管采集器 + DCGM exporter**，尽管它是更大的服务。判据：
      **指标的目的是判断一台每小时几十美元的机器有没有在干活，省下的监控费远小于误判的浪费。**
70. 🟡 AMP 的「agentless / 托管采集器」（`aws_prometheus_scraper`）解决了什么问题？
    - 要点：集群里**不需要跑 Prometheus、不需要 Operator CRD**：采集器通过 EKS API 发现目标（如
      `gpu-operator` 命名空间里的 DCGM exporter Pod），按你给的 scrape 配置抓取并写入工作区，
      规则由 AMP 的 ruler 评估。于是「保留 PromQL 与直方图」不再等于「自建一套监控」——
      这是本批题里托管与表达力少有的双赢点。注意它仍需 VPC / 子网与安全组可达。
71. ☆ 🟡 `nvidia.com/gpu: 1` 是不可分割的。有哪些切分手段，各自适合什么？
    - 要点：**time-slicing**（时间片共享，多个 Pod 轮流用同一张卡，无隔离、无显存保护，适合开发 / 推理小模型）；
      **MIG**（硬件分区，A100/H100 等支持，显存与 SM 真实隔离，规格固定，适合多租户推理）；
      **MPS**（并发内核，延迟友好但故障隔离弱）；**整卡独占**（训练）。
      选择判据：**要隔离与配额 → MIG；要提升闲置卡利用率 → time-slicing；要极致吞吐 → 整卡**。
72. 🔴 什么是 gang scheduling？为什么分布式训练没有它就会「静默烧钱」？
    - 要点：gang scheduling = **要么全部 Pod 同时拿到资源，要么一个都不调度**。
      没有它时，8 卡任务先拿到 5 个 Pod 的 GPU 并**空转等待**剩下 3 个，同时阻塞其他任务，
      形成资源死锁与账单。EKS 原生没有，需要 Kueue / Volcano，或换到 AWS Batch / HyperPod。
      面试追问：怎么发现自己正在烧这笔钱？（答：看「已分配但功耗/张量活跃度接近零」的 GPU 时长。）
73. 🟡 GPU 节点上「最贵的静默故障」是什么形态？怎么监控？
    - 要点：常见形态——ECC 错误 / Xid 错误导致卡不可用但节点仍 Ready、驱动与工具链版本错配导致
      永不上报 `nvidia.com/gpu`、MIG 配置未生效、热降频。监控：DCGM 的健康与 Xid 指标、
      节点上 `nvidia.com/gpu` 可分配数与期望数的差、Pod 长期 Pending 的原因聚合、
      以及**每卡功耗下限告警**。托管侧的对应能力是 HyperPod 的健康检查与自动替换。
74. 🟡 为什么 GPU 节点要用集群置放群组和 EFA？什么时候不需要？
    - 要点：多节点分布式训练的瓶颈常在**集合通信**（all-reduce），置放群组把实例放近以降低网络跳数，
      EFA 提供绕过内核的低延迟高带宽（配合 NCCL）。单节点多卡（走 NVLink）或推理服务
      （请求之间无通信）不需要，此时为 EFA 付出的实例族限制与复杂度没有回报。
75. 🟡 数据侧怎么喂饱 GPU？在 AWS 上按访问模式选存储。
    - 要点：**共享训练集** → FSx for Lustre（可与 S3 桶链接，按需加载）；
      **大文件顺序读** → Mountpoint for S3；**海量小文件** → 先 reshard 成分片格式
      （AWS 没有服务能让这个模式变快，这是被点名的缺口）；**scratch** → 实例自带 NVMe（已付费的盘）；
      **checkpoint** → 异步写 S3，绝不阻塞训练步。跨区域训练数据是**流量账单 + 延迟**，
      桶、文件系统与加速器尽量同区同 AZ（这也是 S3 Express One Zone 的立论基础）。
76. 🔴 「Capacity Blocks」「Spot」「On-Demand」「预留」四种 GPU 容量获取方式，怎么和任务类型配对？
    - 要点：**Capacity Blocks** 为一段确定时间预留成片 GPU（适合有 deadline 的训练）；
      **Spot** 便宜但会被回收——只适合有 checkpoint 且能重启的任务，或可弹性伸缩的推理；
      **On-Demand** 适合基线推理；**预留 / Savings Plan** 适合长期稳定占用。
      配对失败的典型：把 Spot 用在没有 checkpoint 的长训练上，回收一次损失几小时。

## 七、东西向流量与网关：VPC Lattice 还是网格（11 题）

77. ☆ 🟡 在「只用托管」的约束下，服务间通信的第一选择是什么？它给了你什么？
    - 要点：**Amazon VPC Lattice**（通过 AWS Gateway API Controller）：用 `HTTPRoute` 表达服务间路由，
      **IAM auth policy + 每次调用 SigV4** 回答「谁在调我」，请求指标与访问日志进 CloudWatch，
      跨 VPC / 跨账号可用，**集群里没有东西要运维**。计费按服务小时 + 处理的 GB。
78. ☆ 🔴 VPC Lattice **做不到**什么？这个缺口在什么时候会真的疼？
    - 要点：**没有每次调用的重试与异常点驱逐（outlier ejection）**，也没有网格级的细粒度 L7 策略
      （故障注入、请求镜像、每 Pod WASM）。疼的时刻：后端有一个实例半死不活（响应慢但不报错），
      没有驱逐就会持续把流量喂给它。缓解：客户端超时 + 重试 + 断路器留在应用里
      （本例的做法），或者退回到 Istio ambient。
79. ☆ 🟡 为什么采纳顺序是「网关优先、网格其次、sidecar 最后」？这个顺序的依据是组织性的还是技术性的？
    - 要点：主要是**组织性的**：网格常常失败于「运维团队推给看不到收益的开发」，而网关能落地是因为
      **开发要的是路由、运维顺带拿到遥测**。技术上这个顺序是**可逆的**：`HTTPRoute` 是 Gateway API，
      对着 Envoy Gateway 写的路由可以原样绑到 Istio 的入口网关，所以先上网关不会在上网格时推倒重来。
      在 AWS 上同样的顺序 = 同样的清单交给 AWS Gateway API Controller 去编排 Lattice。
80. 🟡 Istio ambient 与 sidecar 模式在成本与能力上的差别是什么？本例为什么两个都没选？
    - 要点：sidecar 每 Pod 约 50m CPU / 60–100MiB 内存，注入要重启，升级与 Pod 生命周期耦合，
      换来完整的每 Pod L7 能力；ambient 用每节点 ztunnel 提供 mTLS 与 L4 遥测，
      **不改 Pod**，需要 L7 时才按命名空间加 waypoint。两个都没选的原因只有一个：
      **istiod 是一个非 AWS 的控制面，要你运维和升级**——在本约束下这就是否决项。
      但它被列为「Lattice 的驱逐缺口咬人时」的退路。
81. 🟡 Linkerd、Kuma/Consul、Cilium mesh 在这份对比里各自因为什么被拒？
    - 要点：**Linkerd** — 数据面最小、路由级黄金指标开箱即用，但同样是你要运维的控制面；
      **Kuma / Consul** — 强在多区域与纳管虚拟机，本例没有 VM 需求；
      **Cilium mesh** — 用 eBPF 免掉每 Pod 代理，但它要**替换 VPC CNI**，
      而 ALB 的 `target-type: ip` 依赖 VPC CNI 给 Pod 可路由地址 —— 
      这是**架构选择之间的耦合**，不是功能优劣。
82. ☆ 🟢 AWS App Mesh 在今天的选型里处于什么位置？
    - 要点：**已于 2026 年 9 月 30 日结束支持**，不应用于任何新设计；AWS 侧的替代是 VPC Lattice
      （+ ECS Service Connect 之类的服务内建能力）。面试价值：考察候选人**是否跟踪服务生命周期公告**——
      「托管」不等于「永远存在」，EOL 风险是托管选型必须评估的一项。
83. 🔴 「这套系统今天正确的网格方案是：不上网格」。请把这个结论论证完整。
    - 要点：网格解决的是**多服务之间**的身份、重试、遥测与策略；今天只有一个服务在边缘后面，
      mTLS 的收益被 VPC 内的现有边界覆盖，超时与租户令牌已经在应用里。
      上网格会引入控制面、升级负担与新的故障模式，换来零个当前需求。
      正确的产出不是「上」或「不上」，而是**写下触发条件**：出现第二个互调服务 / 第二个搜索 API 消费者时，
      第一步是 Lattice，不是网格。
84. 🟡 Gateway API 相比 Ingress，在这套 AWS 架构里带来的最实际好处是什么？
    - 要点：**同一份路由清单，换实现不换文件**：Envoy Gateway ↔ Istio ingress ↔ AWS Gateway API
      Controller（Lattice）都消费 `HTTPRoute`；此外角色分离（`GatewayClass` / `Gateway` / `Route` 分属平台与应用团队）
      与更明确的策略附着点。代价：控制器成熟度与字段支持差异大，跨实现的可移植性要实测。
85. 🟡 边缘（ALB）与东西向（Lattice）分工时，请求 ID 与可观测性怎么串起来？
    - 要点：请求 ID 在 **ALB 处生成或沿用调用方传入**，应用日志（结构化 JSON）打印同一个 ID，
      Lattice 的访问日志与 CloudWatch 指标按服务记录，链路追踪由 OTel/ADOT → X-Ray 串成一张服务图。
      关键工程约束：**应用必须转发 trace / request 头**，托管组件不会替你做跨进程传播。
86. 🔴 用 IAM auth policy 取代 mTLS 身份，在「零信任」话术下是进步还是退步？
    - 要点：两面都要说。进步：身份来自 AWS 控制面、可用条件键做细粒度授权、有 CloudTrail 审计、
      无证书轮换负担、跨账号天然可用。退步：**传输层的双向证书与工作负载身份（SPIFFE）不再存在**，
      身份粒度取决于角色划分（多个工作负载共用角色就退化了），且只在 AWS 边界内成立。
      结论：在纯 AWS 内部这是合理的等价替换，混合环境里不是。
87. 🟡 「一个服务时 ALB 就够，超过约 5 个再看共享入口」——请把这条经验规则的成本模型说清楚。
    - 要点：每个 ALB 约 $16/月起 + LCU；N 个服务各一个 ALB 是 N 倍固定成本与 N 个 DNS/证书条目；
      共享入口（ALB group / ingress-nginx / Gateway）省钱但引入**共享故障域**与配置冲突。
      拐点取决于「固定成本 × N」与「你愿意为共享承担的风险 + 运维」的比较，
      ALB 的 IngressGroup 注解可以在不引入自建组件的前提下先做合并。

## 八、交付链：CodePipeline、EKS 托管 Argo CD、push 还是 pull（11 题）

88. ☆ 🟡 在「只用 AWS」的约束下，CI 引擎为什么是 CodePipeline V2 + CodeBuild 而不是 GitHub Actions？
    - 要点：不是功能优劣，是**边界**：CodePipeline 之后的每一步都跑在账号内，
      审计进 CloudTrail，不需要信任外部 OIDC 颁发者，审批动作原生；
      GitHub Actions 的构建跑在 AWS 外、审计也在 AWS 外。代价要承认：
      流水线定义写在 Terraform 里而不是代码旁边的 YAML，Docker 化的 e2e 需要特权 CodeBuild 项目，
      每条活跃流水线约 $1/月 + 构建分钟数。
89. ☆ 🔴 push 与 pull 两种部署模型的本质差别是什么？请用「谁持有集群凭据」来回答。
    - 要点：**push**（CodePipeline 的 EKS deploy action）——流水线角色持有集群写权限，
      一条链路从 commit 到集群，简单，但**凭据在 CI 里**且**漂移不可见**；
      **pull**（Argo CD）——流水线**唯一的写操作是写 git**，集群凭据只在集群内的控制器手里，
      `OutOfSync` 成为一个可以告警的信号。判据：**你愿意让 CI 拥有生产集群的写权限吗？**
90. 🟡 「EKS managed Argo CD capability」和自建 Argo CD 的差别是什么？对本约束意味着什么？
    - 要点：同样的 `Application` 清单与同步模型，但**控制器由 AWS 运行与升级**，
      不再是这个仓库要打补丁的 Helm release（自建还要管它的 Redis）。
      对约束的意义：GitOps **终于有了一个托管答案**，于是 pull 模型不再违反「只用托管」。
      风险：**区域可用性**——不可用时的退路是 CodePipeline 的 push action。
91. ☆ 🟡 把 `make deploy` 改造成 GitOps，最小的一步是什么？
    - 要点：`make deploy` 今天**渲染**镜像引用与角色 ARN 然后 `kubectl apply`；
      GitOps 化只需把「渲染结果**提交**」替换「apply」——CI 改两个参数（镜像 tag），
      Argo CD 去收敛。这是**最小的 CI 写权限**：它只会写 git。
92. 🟡 镜像扫描「只在控制台可见、不阻断发布」是什么级别的问题？怎么补？
    - 要点：这是**有信号没有闭环**——等于没有。补法：在流水线加**策略门禁**读取 ECR 扫描结果
      （或 Inspector 的发现），按严重度与是否有修复版本决定阻断；配合**基础镜像更新**流程，
      否则门禁只会被一路 override。还要定义「例外怎么批、批多久」。
93. 🔴 流水线的凭据怎么给？请对比 CodeBuild 的服务角色、GitHub OIDC、以及长期 access key。
    - 要点：**CodeBuild 服务角色**——凭据由 AWS 注入，无密钥，最小权限按项目区分，最优；
      **GitHub OIDC**——无长期密钥但要在 IAM 里信任外部颁发者，**必须把 `sub` 条件限死到
      具体仓库与分支/环境**，否则任意 fork 的工作流可能拿到角色；
      **长期 access key**——任何情况下都不应出现在 CI 里。追加：构建产物的**推送权限**与
      部署权限要分离，构建角色不应能改生产。
94. 🟡 IaC 的 apply 应该由谁执行？「`make check` 到受控 apply」这条路上要加什么？
    - 要点：加**远程 state + 锁**（S3 + DynamoDB 或 S3 原生锁）、**plan 作为评审产物**（PR 上贴 plan）、
      **apply 只在流水线里执行**（人不在本地 apply 生产）、**审批动作**、
      以及**漂移检测**（定期 plan，非空即告警）。本例今天是从笔记本驱动的，
      所以这条是「目标」而不是现状——面试时要让候选人区分二者。
95. 🟡 部署方法（滚动 / 蓝绿 / 金丝雀）在 Kubernetes 上分别落成什么？托管服务能帮到哪一步？
    - 要点：滚动 = Deployment 自带（配 `maxSurge/maxUnavailable` + readiness gate）；
      蓝绿 = 两个 Deployment + Service 切换，或两个目标组由 ALB 加权；
      金丝雀 = ALB 目标组加权 / Lattice 权重路由 / Argo Rollouts。
      托管能帮的是**流量切分**（ALB 加权、Lattice 权重）与**指标**（CloudWatch），
      帮不了的是**回滚判据**——那要你定义 SLI 和阈值。
96. 🔴 「发布门禁」应该检查什么？请给出一个可执行的清单。
    - 要点：镜像扫描无未豁免的高危；单元 / 集成测试通过；**冒烟脚本**（就绪副本数、endpoints 非空、
      health UP、指标已被采集、告警规则已加载）；变更未处在错误预算冻结期；
      迁移（Flyway）向前兼容且可回滚；配置漂移检查通过。关键是**每一项都要能自动判定**，
      不能自动判定的就不是门禁，是习惯。
97. 🟡 为什么「在另一个构建镜像上再跑一遍同一条流水线」值得？
    - 要点：这是对「在我机器上能过」的制度化回答——不同基础镜像 / 不同 runner 暴露
      **环境依赖、时区、locale、CPU 架构（arm64 vs amd64）、缓存污染**等问题。
      在 CodePipeline 里就是同一 stage 放第二个 CodeBuild action，成本是构建分钟数。
98. 🔴 多架构镜像（arm64 + amd64）在 EKS 上会带来哪些具体的坑？
    - 要点：`docker buildx` 构建 manifest list 并推 ECR；节点组混架构时要用
      **`nodeSelector`/`affinity` 按 `kubernetes.io/arch` 约束**或确保镜像确实是多架构，
      否则会出现 `exec format error`；DaemonSet 与第三方镜像（agent、exporter）不一定有 arm64；
      基准与内存占用要重测（Graviton 性价比高但 JVM 参数与本地库需验证）。

## 九、数据、流与 AI 存储：托管选项之间的取舍（14 题）

99. ☆ 🟡 ElastiCache 与 MemoryDB 都说 Redis/Valkey 协议，一句话说清差别，并指出选型里最容易被忽略的一行。
    - 要点：**ElastiCache 是带副本的缓存，MemoryDB 是会说缓存协议的数据库**——
      MemoryDB 的每次写在确认前先进**多 AZ 事务日志**，所以 failover 不丢数据，代价是写延迟更高、
      按节点小时 + 写入日志量计费。最容易忽略的一行是**区域覆盖**：ElastiCache 约 37 个区域，
      MemoryDB 约 21 个——把「持久化的 Agent 记忆」放进 MemoryDB，等于**悄悄做了一个区域决策**，
      要先对照你模型所在的区域。
100. 🟡 什么时候「这个缓存根本不该是 Redis」？
     - 要点：如果它承载的只是**按会话 ID 读写一次的会话状态**，那是键值访问模式：
       **DynamoDB** 单数毫秒、持久、TTL 自动过期、没有节点要运维，直接把这个框删掉。
       Redis 值得存在的理由是：数据结构（排行榜、限流计数、Stream）、极低延迟的热读、
       跨副本共享的短寿命状态。
101. 🟡 ElastiCache Serverless 适合什么场景？为什么对「语义缓存」特别合适？
     - 要点：它把**节点规格**这个必须提前猜的参数去掉了，按存储量与请求量计费。
       语义缓存的流量就是产品流量，事前无法容量规划，且命中率随模型与提示变化剧烈——
       这正是「不该预先买一个节点」的形状。代价：单位成本更高，稳定大流量时不如固定节点划算。
102. ☆ 🟡 MSK、Kinesis Data Streams、Data Firehose 三选一，判据是什么？
     - 要点：**MSK** = AWS 运维的 Apache Kafka，保留协议与全部 Kafka 生态，有压缩主题与长回放；
       **Kinesis Data Streams** = AWS 原生有序日志，分片 + SDK，运维面更小，保留期内可重放；
       **Firehose** = **投递管道，没有日志可读**（S3 / OpenSearch / Redshift），不承诺顺序、**不能重放**。
       诚实版判据：已有 Kafka 消费者、schema 与人 → MSK；没有 → Kinesis 更省事；
       只是要把记录落到 S3 且没人 tail → Firehose。**为了每请求几百字节而引入 Kafka 平台，是引入了一个平台。**
103. 🟡 为什么说「流层不会成为把架构钉死在某个区域的那一环」？这个观察怎么用在架构评审里？
     - 要点：MSK / Kinesis / Firehose 都是约 37 个区域全覆盖，而 MemoryDB 是 21——
       评审时应当**把每个托管服务的区域可用性列进选型表**，先找出覆盖最窄的那个服务，
       它决定了你多区域扩张的下限。这个习惯能在设计早期避免「到了新区域才发现核心组件不可用」。
104. ☆ 🟡 「至少一次投递」对消费者提出了什么要求？请结合这套系统的幂等键回答。
     - 要点：消费者必须**无聊**——同一条记录处理两次的结果与一次相同。手段：
       用业务键 + DynamoDB 条件写做幂等、把写操作设计成幂等的 upsert、
       避免「读-改-写」的非原子序列、把副作用（发邮件、扣款）挪到有去重保护的路径后面。
       关键认知：**顺序与去重是消费者的责任，托管消息服务只保证投递。**
105. 🔴 按租户分区有什么代价？怎么诚实地为它定价？
     - 要点：代价是**热点**（大租户的分片被打满而其他分片闲置）与**分区数上限**；
       诚实定价 = 把每租户的流量与保留期折算成分片/分区成本，并把大租户单独隔离（专用分片或专用主题）。
       同时要监控**每分区滞后**而不是总滞后，否则一个租户的积压会被平均掉。
106. 🟡 保留期为什么是「成本旋钮」，S3 为什么是地板？
     - 要点：流服务的存储成本与保留期线性相关，而重放需求通常集中在最近几小时；
       所以典型做法是**短保留 + 落地 S3**（Firehose 或消费者写），需要长回放时从 S3 重放。
       S3 是地板的意思：最终所有记录都便宜地躺在对象存储上，流系统只承担「近期与顺序」。
107. 🟡 DocumentDB 的典型误用是什么？
     - 要点：**在应用还不存在时就选它**。它的合理理由只有一个：「我已经有一个 MongoDB 应用，想让别人来运维」。
       从零开始设计时，用文档模型的理由要来自访问模式，而不是「文档数据库听起来灵活」。
       本例的系统记录留在关系库，因为写路径需要**跨两行的事务**、Flyway 迁移与 JOIN。
108. 🔴 「为你拥有的查询选型，就等于对其他查询做了取舍」——请用 NoSQL 选型解释这句话。
     - 要点：DynamoDB 的性能来自**按访问模式建模**（分区键 / 排序键 / GSI），
       换来的是**临时查询能力的丧失**：没有 JOIN、没有任意谓词的高效扫描、GSI 有成本与最终一致性。
       所以选型的正确顺序是**先列出全部访问模式与它们的 SLA**，再挑存储；
       反过来做，第二个季度就会出现一个「只能全表扫」的需求。
109. 🟡 AI / 训练数据在 S3 上的「小文件问题」为什么没有托管解？
     - 要点：S3 的成本与延迟按**请求**计，百万级小文件意味着百万次请求与元数据开销，
       任何托管缓存层都改变不了这个形状。诚实的两条路：**重新分片**（打包成
       webdataset / parquet / tar shard）或**接受请求成本并为之扩容**。
       这类「AWS 不给答案」的条目值得单独写进设计文档。
110. 🟡 checkpoint 为什么「不能阻塞训练步」？在 AWS 上怎么落地？
     - 要点：同步 checkpoint 会把 GPU 停在等 IO 上，直接乘以机队成本。
       落地：先写本地 NVMe（已付费的 scratch），再**异步**上传 S3；
       控制频率（按步数与容忍的重算时间权衡）、只保留最近 N 份 + 里程碑；
       分布式时用分片 checkpoint 避免单点串行。
111. 🔴 Mountpoint for S3 与 FSx for Lustre 各自适合什么？选错的症状是什么？
     - 要点：**Mountpoint for S3** 适合大文件顺序读、只读或追加写的场景，它不是 POSIX 完整语义
       （随机写、重命名、目录语义受限）；**FSx for Lustre** 是真并行文件系统，
       可链接 S3 桶按需加载，适合多节点共享训练集与高 IOPS 小文件。选错的症状：
       用 Mountpoint 跑需要随机写/重命名的框架会失败或极慢；
       用 Lustre 存冷数据则是为不需要的吞吐持续付费。
112. 🟡 为什么「桶、文件系统与加速器尽量同区同 AZ」，这条建议和 S3 Express One Zone 的关系是什么？
     - 要点：跨区数据传输既是**延迟**也是**账单**；即便同区，跨 AZ 也有传输费与额外延迟。
       S3 Express One Zone 正是把「单 AZ」当作明确取舍来换取个位数毫秒延迟与更高请求率——
       它用可用性换性能，所以只适合**可重建的数据**（训练集缓存、中间产物），不适合唯一副本。

## 十、Agent / MCP 在 AWS 上：托管边界的最新前沿（8 题）

113. ☆ 🔴 把 MCP 服务器搬上 AWS 时，AWS **能**真正约束的是哪几件事？
     - 要点：网络可达性（VPC、安全组、PrivateLink、DNS Firewall 的域名清单）、
       身份与授权（IAM / Cognito / Verified Permissions）、出网边界（无 NAT 即无出网）、
       审计（CloudTrail 记录**它调用的 AWS API**）、以及运行时隔离（独立账号 / 容器 / 会话级角色）。
       这些都是**基础设施边界**，而不是协议语义边界。
114. ☆ 🔴 AWS **不**给你的是什么？请举出至少五项，并说明团队通常怎么凑合。
     - 要点：① JSON-RPC 级别的 WAF 规则（只能做 body 正则，格式一变就废）；
       ② **工具调用本身的 CloudTrail 记录**（只记录它引发的 AWS 调用，不记录"调用了哪个 tool"）；
       ③ 每工具的授权模型（要自己写 Verified Permissions schema）；
       ④ 「Agent 被批准使用了哪些 tool 定义」的记录（自己把定义哈希存 DynamoDB 定期比对）；
       ⑤ 运行时启动的 stdio 服务器扫描（只能把它们固化进镜像）；
       ⑥ 认识「Agent」这个概念的 GuardDuty 发现与 Security Hub 标准。
       共同点：**协议层的语义，云厂商的通用控制面看不见。**
115. 🔴 「致命三角」——私有数据、不可信输入、外发能力——在 AWS 上怎么逐条拆？
     - 要点：把三者**不要同时授予同一个执行角色**：读私有数据的角色不给出网（无 NAT / 端点白名单）；
       处理不可信内容的组件跑在无凭据的隔离账号；需要外发的组件只允许到白名单域
       （DNS Firewall + egress 代理）。落地难点在于**没有现成的分析告诉你哪些角色同时具备三者**，
       只能自己盘（文档里的原话是"一张表格"）。
116. 🟡 为什么「每次调用授权」比「每次连接授权」更适合工具调用？
     - 要点：一个 MCP 会话可能调用几十个能力，权限差异极大；连接级授权只能取并集，
       等于把最高权限给了整个会话。每调用授权可以按工具名 + 参数做判定
       （例如只允许对某些资源做只读），并让审计记录到"哪个主体调用了哪个工具"这一层。
117. 🟡 JWT 校验里 `ClockSkew` 默认 0、过期缺失需显式允许，这类细节为什么值得在面试里问？
     - 要点：它考的是**候选人是否读过库的默认值**。时钟偏移为 0 时，客户端与服务端几秒的漂移
       就会造成间歇性 401，而这种故障"重试就好了"，极难定位；
       允许缺失过期时间则是把一个安全默认关掉。结论：**认证类配置要逐项读默认值并写下理由**。
118. 🔴 给一个已经在跑的 MCP 服务器做安全评审，你的清单前五条是什么？
     - 要点：① 传输与认证（是否强制 TLS、token 从哪来、受众与过期校验）；
       ② 工具清单与权限（每个工具能碰什么资源、有没有危险动作、是否可禁用）；
       ③ 输入来源（哪些内容是不可信的：网页、文件、第三方 API）与注入防护；
       ④ 出网与凭据（服务角色权限范围、能不能访问元数据服务、有没有长期密钥）；
       ⑤ 可观测与审计（工具调用是否有结构化日志、能否重建一次会话）。
119. 🟡 「把每个缺口写成一条独立的产品诉求（wish）」这种做法有什么工程价值？
     - 要点：它把"抱怨"变成**可跟踪、可验证、可关闭的条目**：每条说明缺什么、今天怎么凑合、
       如果厂商实现了会长什么样。价值有三：评审时能一眼看出风险面、厂商发布新功能时能快速对账、
       团队换人时知识不丢。对面试而言，能写出这种清单的人，通常也能写出好的架构决策记录。
120. 🔴 Agent 相关的托管服务（Bedrock / AgentCore 一类）正在快速变化。你会如何设计以避免被一次改版打穿？
     - 要点：把**模型调用、工具执行、记忆存储**三者解耦，各自放在自己的接口后面；
       用 OTel 记录请求与 token 用量（不依赖厂商控制台）；
       把提示与工具定义**版本化在 git 里**而不是控制台配置；
       为"区域不支持 / 模型下线"预留降级路径（另一模型、规则兜底）。
       判据：**厂商功能可以用，但不要让它成为唯一的数据与状态所在地。**

## 十一、把「没部署过的架构」写成可信文档：方法论（10 题）

121. ☆ 🔴 一份架构文档的每一页都带一个 *Verified, and not*（"哪些读过、哪些跑过、哪些没验证"）小节。这个习惯解决了什么问题？
     - 要点：解决**「文档的自信与证据不匹配」**——读者无法区分哪句是实测、哪句是推理、哪句是记忆。
       分三类写：**读过（附来源与日期）/ 跑过（附命令与结果）/ 未验证但承重**（明确点名"我最想先测的是哪一条"）。
       对团队的意义：新人知道哪里可以信、审计知道去哪找证据、作者被迫承认自己的不确定。
122. ☆ 🔴 这套设计里的告警阈值是"推理出来的，不是观测到的"。作为评审人，你会要求先测哪三个数？
     - 要点：① **p95 延迟的真实分布**（决定 300ms 这个阈值是否合理，以及是否必须要直方图）；
       ② **outbox 从提交到 sent 的实际分布**（决定 60 秒的新鲜度 SLO 与告警窗口）；
       ③ **投影重建耗时**（决定"不备份投影"这个决定是否成立）。
       共同点：这三个数一旦实测，可能推翻的是**设计决策本身**，而不只是阈值数值。
123. 🟡 「目标架构」和「已建成」在同一张图上时，怎么表达才不误导？
     - 要点：用显式标记（本例用绿点标出 Terraform 真正 provision 的 5 项）、
       在正文第一段就写"这是目标不是部署"、为每个未建成项写明**为什么还没建**
       （这里是"apply 会产生 RDS 与 OpenSearch 账单"）。
       反面教材是把目标图当现状图挂在 wiki 上——事故时它会把人引向不存在的组件。
124. 🟡 为什么每张选型表都要有「拒绝了什么」这一列？
     - 要点：没有被拒选项的决策记录是**不可复查的**：后来者不知道某个方案是没想到还是想过被否；
       也无法在条件变化时重新评估（"当初拒绝 Serverless 是因为最低消费，现在规模涨了，该复看了"）。
       好的拒绝理由要写**成本量级或语义原因**，而不是"不合适"。
125. ☆ 🔴 什么是「诚实的缺口」写法？给一个模板。
     - 要点：模板四段——**缺什么**（AWS 没有服务备份 K8s API 对象）／**它具体漏掉什么**
       （控制器创建的对象、手改未提交的对象、PVC→PV 绑定）／**两条路与各自代价**
       （补成空缺口 vs 引入非托管组件）／**本例选哪条以及触发改选的条件**。
       关键是第二段：不写清楚漏什么，缺口就只是一句免责声明。
126. 🟡 一次「把所有文档改成只用托管服务」的批量修改，怎么保证没有漏网之鱼？
     - 要点：先**枚举而不是抽查**：对每个非托管组件名（Velero、Prometheus、External Secrets、
       Istio、Argo CD 自建…）在全仓库 grep 计数，形成清单；逐页处理并记录处理方式
       （改为 chosen / 降级为 rejected 行 / 保留并注明是实验室记录）；最后**复跑 grep 对账**，
       并检查**图与图注**（alt text）是否同步——图片里的旧选择最常被遗忘。
127. 🔴 上题的批量修改里，有一类内容**不应该**被改。是哪一类？
     - 要点：**对现实的记录**。例如"实验室里跑的是 GitLab CI / Jenkins / Vault / Envoy Gateway / 自建 Argo CD"
       这类描述是**事实**，不是目标；把它改成 AWS 服务就是把文档改成谎言。
       判据：**目标可以被约束改写，记录不行。** 处理方式是把两者在文中显式分栏。
128. 🟡 文档里的成本数字应该怎么写才不会过期成谎言？
     - 要点：写成**量级与形状**而不是报价（"约 $16/月 + LCU"、"Serverless 最低约是本 demo 的 8 倍"），
       注明区域与计价模型、注明日期，并强调"这是形状不是报价"；
       把**驱动成本的变量**写出来（每 GB、每指标、每请求），这样读者能用自己的量代入。
129. 🔴 「把非 AWS 的工具从 chosen 降级为 rejected」时，最容易犯的错误是什么？
     - 要点：把**理由写成偏见**（"它不是 AWS 服务"）而不是**代价**（"它是这里唯一一个你要自己升级的控制面，
       并且它的规则文件已经帮我们验证了告警算式"）。降级要保留它的贡献与再次启用的条件，
       否则文档会在下一次条件变化时失去指导力。本例的好范式：
       自建 kube-prometheus-stack 被拒，但明确写"它的规则文件证明了 CloudWatch 告警现在承载的那套算术"。
130. ☆ 🔴 最后一道开放题：给你同样的约束（"只用托管服务，指不出来的写明缺口"）和一套已有系统，你的前两周计划是什么？
     - 要点：好的回答有顺序感——第 1 周：**盘点**（组件清单 × 现状 × 托管候选 × 缺口），
       挑出**可逆且高收益**的先做（密钥、备份计划、告警）；第 2 周：**测量**那三个会推翻设计的数字
       （延迟分布、重建时长、恢复演练），把"推理"替换成"观测"。
       并且从第一天起做**两件不要做的事**：不要在没有 diff 的情况下换备份方案，
       不要为了"全托管"这个称号把语义（幂等、事务、调度公平性）交给不具备该语义的服务。

## 十二、经典系统设计的 AWS-only 渲染（一）：读多写少、实时通道与高并发抢占（27 题）

> 来源是同一批文档里的 `docs/system-design/` 页面（11 篇，覆盖语料库 17 个题目）。
> 每篇的共同做法值得先讲给候选人：**把通用设计逐行翻成托管服务，然后数一数「消失了几个组件」**——
> 消失的组件就是这道题在 AWS 上的答案，而**没消失的**那部分才是真正要设计的东西。

### 12.1 短链服务（url-shortener）

131. ☆ 🟡 通用短链设计有五个组件：负载均衡、应用层、关系库、Redis、独立分析库。在「只用托管」下有三个会消失。哪三个，各被谁吸收了？
     - 要点：**关系库 → DynamoDB**（12B 条、单键访问、TTL 过期，正是它的形状）；
       **Redis → CloudFront**（重定向是互联网上最可缓存的响应：同样输入永远同样输出，CDN 不是优化而**就是读路径**，
       DAX 只作为冷缓存长尾的可选项）；**独立分析库 → CloudFront 访问日志 → S3(Parquet) → Athena**
       （CloudFront 已经为每个请求写了一行，包括源站看不到的命中）。剩下的两个：ALB/API GW（HTTP API）与 Lambda。
132. ☆ 🟡 这道题的数字里，哪一个决定了「不能从数据库服务重定向」？
     - 要点：**p99 < 10ms 配 4,000 QPS 与 3.4TB 数据**。DynamoDB 点读是同区域单数毫秒，
       但跨洲的**光速本身**就超过预算，所以常见路径必须在**边缘**结束。这题的价值是让候选人明白
       延迟预算要先拆成「传播 + 处理」，再决定组件位置。
133. ☆ 🔴 301 还是 302？请把它论证成一个成本与产品决策，而不是 HTTP 知识题。
     - 要点：**301** 被浏览器与 CDN 近乎永久缓存 → 第二次跳转免费且**你永远看不到**，代价是链接
       **不可编辑、不可撤销**（你到不了那些缓存）；**302 + `max-age=300`** 可编辑可撤销，
       多数请求仍命中 CloudFront；**302 + `no-store`** 每次都打到 Lambda（10B 次/月调用）。
       正确做法：把它做成**链接本身的属性**存在 item 上——印刷品的固定活动链接用 301，用户可编辑的用 302。
134. ☆ 🔴 发号（生成 7 位 code）有三种 AWS-only 做法，为什么选「块分配」？
     - 要点：**随机 base62 + `attribute_not_exists` 条件写**——无热点，但随表增长重试率上升；
       **DynamoDB 原子计数器单 item**——无碰撞但**所有写序列化在一个分区**，40 w/s 能活、突发会死，被拒；
       **块分配**（每个 Lambda 执行环境一次 `UpdateItem` 领 1,000 个 id，然后在内存里发）——
       每 1,000 次写只有一次读改写，**选它**。浪费的是执行环境回收时未用完的 id，
       而在 3.5 万亿的键空间里，这是「该浪费的东西」。这就是 Snowflake 的思想，用已有的 AWS 零件、不需要 ZooKeeper。
135. 🟡 「每次重定向写一行点击记录」为什么是这套设计里最大的错误？
     - 要点：它把一个 **40 写/s 的应用**绑上了一个 **4,000 写/s 的分析库**——分析成了系统里最大的组件，
       而它回答的问题没人需要实时知道。替代：CloudFront 标准日志 v2 直接以 Parquet 分区落 S3，Athena 就地查询。
       **诚实的代价**：计数**不是实时的**（日志分钟级落地），"今天到现在的点击数"是近似值；
       真要实时就加 Firehose 订阅 + Lambda 更新 DynamoDB 计数器，并把它当作一个**单独的、带账单的决定**。
136. 🟡 数据模型里为什么「列出某用户的所有链接」要放 GSI，而不是做成主表的排序键？
     - 要点：**重定向路径不能为仪表盘的 schema 付费**。主表保持 `code` 单键点读最快；
       `owner` 维度是第二访问模式，放 GSI，它的成本与一致性（最终一致）只影响控制台页面。
       通则：**把最热的访问模式放在最便宜的形状上，其余用索引承担。**
137. 🟢 为什么用 API Gateway HTTP API 而不是 REST API？什么时候该反过来？
     - 要点：HTTP API 约为 REST API 三分之一价格、延迟更低，而这个场景不需要 REST 的那些功能
       （请求校验、API key 用量计划、WAF 直挂、私有集成的全套）。反过来的条件：要卖 API 给第三方
       （用量计划与 key）、要请求/响应转换、要 mTLS 客户端证书。
138. 🟡 限流为什么放在 WAF 的 rate-based rule 而不是应用里的令牌桶？
     - 要点：通用设计把令牌桶写进 Redis——它在请求路径上、要运维、且**攻击流量已经进到你的代码里**了；
       WAF rate-based rule 是**边缘上的托管计数器**，恶意流量在到达源站前就被拒，
       再叠加 API Gateway usage plan 做按 key 的配额。判据：**限流越靠前越便宜。**
139. 🔴 这道题的多区域方案是什么？为什么它比通常的"多活"讨论简单？
     - 要点：读路径**本来就是全局的**（CloudFront 边缘），所以多区域只需要把**未命中路径**变全局——
       DynamoDB 全局表 + 两区域的 Lambda/API。因为写极少（40/s）且**冲突语义简单**
       （code 一旦分配就不变），全局表的最后写入者胜出几乎不会产生实际冲突。
       对比：写多、且写需要事务的系统（票务、库存）没有这个便利。

### 12.2 即时通讯（messaging-platform）

140. ☆ 🟡 这道题「难」在哪里？为什么不是难在存储？
     - 要点：消息本身是 300 字节 item 的海量追加写，正是 DynamoDB 擅长的
       （`pk = CONV#id`、`sk = SEQ#nnnn`，"最近 50 条"是一次反向 `Query`）。
       难的是**连接**：数亿条大部分空闲的长连接，且必须能在毫秒内**根据用户找到连接**。
       所以设计的重心是连接注册表、扇出与计费（连接分钟数），不是消息表。
141. ☆ 🔴 API Gateway WebSocket 与 AppSync 都是托管的，怎么选？在 500 人群聊这个场景哪一行决定了答案？
     - 要点：决定性的是**扇出**那一行：API Gateway WebSocket 下，你的 Lambda 要对 500 个连接
       逐个 `PostToConnection`（一次调用里 500 个 API 调用 + 部分失败处理 + 每个死连接一个 410），
       **连接注册表也是你自己维护**；AppSync 把这个循环搬进服务里（按 schema 过滤的订阅、
       与 Cognito 集成的字段级授权）。所以默认 AppSync，**协议不是 GraphQL 时**（二进制、自定义帧）才用前者。
       两者共同点：扇出循环是**延迟方差的最大来源**。
142. ☆ 🔴 消息顺序从哪来？请逐一否掉三个看似可行的来源。
     - 要点：**队列不行**——SQS 标准无序；SQS FIFO 按消息组有序但上限约 300 msg/s（批量 3,000），
       热群聊会超，而且你要的顺序本来就是"按会话"；**时间戳不行**——两个客户端、两个 Lambda 的时钟都不一致；
       **流不行**——DynamoDB Streams 只保证**分区键内**有序，那是在顺序已被决定之后才有用。
       正解：**会话 item 上的原子计数器**（`ADD last_seq :one` 取回 seq，再用
       `attribute_not_exists(sk)` 条件写入 `SEQ#{seq:020d}`）。
143. 🔴 上题的方案每条消息多一次写、且写在**一个** item 上。为什么这个热点是可接受的？
     - 要点：因为它的热度**上界是这个会话自己的发送速率**，而不是全系统的速率——
       所以全局 1.15M msg/s 也不会压垮任何单个计数器，而一个**全局序列**就会。
       客户端侧的顺序检查也因此变得极简：收到 `SEQ#…41` 之后收到 `…43` 就知道有空洞，回拉即可。
       边界：**一万人的"频道"是另一个产品**，需要另一个模型（不能按会话单调计数）。
144. ☆ 🔴 「在线状态（presence）」为什么被称作「最贵的谎言」？给出按优先级排序的 AWS-only 做法。
     - 要点：500M 用户、30 秒心跳写一次 = **1,600 万写/s**，是消息速率的七十倍，
       而它是产品里最不承重的功能。优先级：① **从连接推导**（presence = 有活连接，按需读连接表，
       只在 connect/disconnect 时写）；② **心跳 + TTL**，每用户每分钟最多一次写（有界陈旧）；
       ③ ElastiCache 短 TTL 键（快，但多一个集群和第二个真相源）；④ 每事件一写（精确且负担不起）。
       结论也是产品结论：**presence 是缓存，永远不是事实**，所以 UI 该写"最近活跃"而不是"在线"。
145. 🟡 已读回执与未读数怎么建模才不会写放大？
     - 要点：不要"每消息每读者一行"。把 **`last_read_seq` 存在成员关系 item 上**
       （`pk = USER#id`, `sk = CONV#id`）——每次"读"一次写，而不是每条消息一次；
       **未读数 = `last_seq − last_read_seq`，读时计算、不存储**；
       "已被谁看过"的扇出与消息扇出是同一条流，这也是真实产品里群已读普遍限流的原因。
146. ☆ 🟡 `PostToConnection` 返回 410 意味着什么？处理它和不处理它的区别是什么？
     - 要点：410 Gone = **这个连接已经死了**（客户端静默掉线，连接表里的行是幽灵）。
       处理：删掉连接行，并**回落到推送通知**（推送不是消息，是"请重连"的提醒）。
       不处理：死连接不断累积，扇出打给不存在的人——**"消息显示已投递但对方从未收到"**，
       并且连接表越来越脏、扇出越来越慢。
147. 🟡 发送方超时重试会产生重复消息，怎么根治？
     - 要点：**客户端生成 `message_id`**，服务端写入时带 `ConditionExpression: attribute_not_exists`，
       于是重试天然幂等。要点在于幂等键必须由**发起方**生成并在重试时保持不变——
       服务端生成的 id 每次重试都不同，等于没做。
148. 🔴 这套设计的账单里哪一行最大？产品上能动哪个旋钮？
     - 要点：**连接分钟数**（数亿条大多空闲的 socket），与消息量无关。
       旋钮是产品的：**激进的空闲断连 + 推送通知**（推送比持有 socket 便宜），
       以及"实时"到底意味着多少秒。其次是 DynamoDB 每条消息 2 次写（计数器 + item）——
       回执批量化是可省的部分；归档 6TB/天的成本由**保留策略**决定（Object Lock + 生命周期转 Glacier）。

### 12.3 票务 / 抢票（ticketing-platform）

149. ☆ 🔴 这套系统的「全部正确性论证」是一行代码。是什么？它替掉了通用设计里的什么？
     - 要点：一次 **DynamoDB 条件写**：`ConditionExpression: #st = :available`，
       把座位从 AVAILABLE 改为 HELD。它是**存储引擎内部**对单个 item 的 compare-and-swap，
       一个座位一个 item，所以**争用与吞吐上限都是"每座位"而不是"每场次"**；
       抢不到的那个拿到 `ConditionalCheckFailedException`，单数毫秒内得到"座位已被占"。
       它替掉了：分布式锁管理器、Redis `SETNX` + 租约、`SELECT ... FOR UPDATE`、乐观版本列——
       **锁在存储里，没有锁服务要运维、要故障转移、要 fencing。**
150. ☆ 🔴 「持有的座位泄漏」有三种过期机制，其中一个是常见陷阱。请全讲。
     - 要点：**DynamoDB TTL 是陷阱**——它是 48 小时内尽力而为的清理机制、**没有 SLA**，
       用来做 10 分钟的持有过期是错的；**每分钟扫表的 Lambda** 能用，但成本与延迟随库存增长；
       **EventBridge Scheduler 每个 hold 一个一次性 schedule**（`ActionAfterCompletion: DELETE`）
       **准时、不扫表、自清理**，选它。**但最关键的一句**：无论用哪个，读路径都必须把
       `hold_expires < now` 视为可售并能用条件写拿下它——**过期机制只是清理，条件表达式才是真相**。
151. ☆ 🔴 公平性（waiting room）为什么要放在应用之外？边缘方案的诚实局限是什么？
     - 要点：1,000 万并发等待者如果在应用层排队，**这个队列本身就是故障**（每个等待者都是连接、
       会话查询和轮询）。方案：**CloudFront Function + KeyValueStore** 在边缘按固定速率签发准入令牌，
       没有令牌就从 S3 拿到等候页、**永不触达源站**——1,000 万人被 CDN 吸收。
       局限要说清：令牌桶是**限速意义上的公平**，不是先到先得；真正的全局 FIFO 需要一个
       代价超过收益的全局排序，这也是现实中所有大型开售都是抽签或令牌准入的原因。
       被拒方案：SQS FIFO 做购买队列（**让成功路径变慢去修失败路径**）、ElastiCache 里的队列。
152. 🔴 购买流程为什么用 Step Functions Express 而不是写在应用代码里？
     - 要点：hold → pay → confirm 是一个**每步都有补偿动作的 saga**，而状态机就是这个东西：
       重试、超时、补偿、可视化执行历史都不再是你的代码。选 Express 而非 Standard 的两个理由：
       **无需预热即可扩容**（开售瞬间很关键）与此量级下的价格（按时长与请求计费，不按状态转换）。
153. ☆ 🔴 「自动扩缩容看不见的开售」是什么问题？AWS-only 的应对全部有一个共同点，是什么？
     - 要点：流量在公布的时刻从近零到千万并发，而所有**反应式**扩容（Lambda 突发限额、
       DynamoDB 按需的自适应、OpenSearch 分片预热）都以数十秒到数分钟为尺度，
       而开售在**前十秒**就决出结果。共同点：**全部必须在开售之前做**——
       DynamoDB 预置容量（或按需预热吞吐）、Lambda 预置并发（用 EventBridge Scheduler 按开售窗口排程）、
       CloudFront 等候室让源站根本看不到尖峰。这是**日历问题，不是架构问题**，也是最常被漏掉的一环。
154. 🟡 把一个场次的所有座位放在同一个分区键下，好处与风险各是什么？
     - 要点：好处是**浏览路径一次 `Query` 拿到整张座位图**；风险是一万座的场次**一个分区承担全部开售突发**。
       缓解有两层：热操作是**单 item 条件写**，DynamoDB 自适应容量会隔离热 item；
       浏览路径由 CloudFront 承担而不是打表。追问：如果座位图还是打满了怎么办？
       （答：把座位按 section 拆分区键，用牺牲"一次查全图"换取写入分散。）
155. 🟡 为什么支付是这套设计里唯一的外部依赖，而且是刻意的？
     - 要点：AWS 不处理卡支付。把 PSP 放在外面，**PCI 范围留在 PSP**，
       你的账号里只有一个 Lambda + Secrets Manager 里的密钥。
       这是"托管优先"的一个重要延伸：**有些边界不是技术决策而是合规决策**，
       主动把范围推出去比自己拿进来便宜得多。
156. 🟡 票本身怎么交付？为什么这正好是签名 URL 的形状？
     - 要点：一张票是**一个带过期的静态对象**——S3 预签名或 CloudFront 签名 URL 正是这个语义，
       QR 在 Lambda 里生成。含义：交付路径不经过应用、可被 CDN 承载、
       过期与撤销靠签名有效期与对象替换而不是靠会话。
157. 🔴 请用这道题总结「AWS-only 抢占类系统」的通用配方。
     - 要点：① **争用点做成单 item 条件写**（锁在存储里）；② **等待与公平放到边缘**（CDN 吸收）；
       ③ **多步事务交给状态机**（补偿即设计）；④ **定时器用 Scheduler 而不是 TTL 或扫表**；
       ⑤ **突发靠预热，且预热是排程出来的**；⑥ 分析走 Streams → Firehose → S3 → Athena，
       绝不在应用里写第二份。这六条可以直接当作面试评分维度。

## 十三、经典系统设计的 AWS-only 渲染（二）：调度、投递、抓取、聚合、流媒体、存储与分析（38 题）

### 13.1 定时任务调度（job-scheduler）

158. ☆ 🟡 「作业调度」在 AWS 上要先做一道分类题：三个服务分别回答什么问题？
     - 要点：**EventBridge Scheduler** = "**到点**跑这个"（cron / rate / 精确一次性时间戳）；
       **Step Functions** = "按顺序跑这些，并处理出错"（重试与分支不再是代码）；
       **AWS Batch** = "大量这类作业，带依赖与优先级，找最便宜的容量"（三者中唯一有原始意义上的
       *调度器*：优先级队列、作业依赖、自伸缩计算环境）。
       多数系统需要其中两个，**说清哪类作业进哪个服务比画一张架构图更有用**。
159. ☆ 🔴 这道题里有一整行组件被「删除」了。是哪一行？为什么删得掉？
     - 要点：**leader election / 协调者故障转移**（以及它连带的 ZooKeeper、etcd、租约、脑裂故事）。
       删得掉的原因：**托管队列 + 竞争消费者没有协调者需要保活**。
       原设计的"无单点故障"需求于是**由构造满足，而不是由协议满足**——
       这是整页最漂亮的一句，也是判断候选人有没有想清楚的地方。
160. ☆ 🟡 「每个作业一个 schedule」与「due-time 表 + 扫描器」怎么选？各自在哪里崩？
     - 要点：**每作业一个一次性 schedule**（按 job id 命名、触发后自删）——最省组件，
       崩在**schedule 数量的服务配额**与创建 API 速率（1M 作业/天≈12 创建/s，属寻常）；
       **DynamoDB `dueAt` GSI + 每分钟扫描**——不受配额限制，但你又养回了一个扫描器，
       它的失败模式是**漏掉一分钟就延迟那一分钟的全部作业，而且没人会发现**（除非专门对
       schedule lag 告警）。建议：**先用前者**（少一个组件），被配额或突发逼到了再换后者。
161. ☆ 🔴 「调度器的最坏失败」是什么？为什么常规告警抓不到它？
     - 要点：**什么都没发生**。其他系统失败得很吵（错误率、5xx、延迟），
       调度器失败是**一条归零的曲线**——错误率告警永远不会触发，因为没有请求产生错误。
       正解：**对"预期完成的缺席"告警**（absent / no-data 告警、对完成计数设下界），
       而不是对错误率告警。这一条几乎是所有调度系统设计里最常缺的。
162. 🟡 Step Functions 什么时候比它编排的工作更贵？三种解法是什么？
     - 要点：Standard 按**状态转换**计费——20 个状态 × 100 万次/天 = 2,000 万转换/天，
       编排可能比被编排的 Lambda 更贵。解法：① 高频短时无长等待 → **Express**（按时长与请求计费）；
       ② 需要持久执行历史 → Standard 但**把状态做粗**（三个 Lambda 合成一个）；
       ③ 高频无分支 → **根本不要状态机**，SQS + 消费者。
       通则：**Step Functions 的价钱值在"失败处理是难点"的时候**；
       当作业只是"调一个东西并记录结果"，状态机就是带按次发票的仪式。
163. 🟡 为什么扩容指标要用「队列年龄」而不是「队列深度」？
     - 要点：深度分不清"大积压正在快速消化"与"小积压卡死了"；
       **年龄（最老消息的等待时间）直接对应用户可感知的延迟**，也是 SLO 的语言。
       实践上两者都看：年龄做扩容与告警，深度做容量趋势。
164. 🟡 可见性超时（visibility timeout）怎么定？定错的两个方向各是什么后果？
     - 要点：按**作业时长的 p99** 设定。太短 → 作业还在跑消息就回队，**重复执行**；
       太长 → 工作节点死掉后**恢复很慢**（消息要等到超时才重新可见）。
       配套：`maxReceiveCount` + DLQ + **DLQ 深度告警**（没有告警的 DLQ 就是一个装丢件的文件夹）。
165. ☆ 🟡 这里所有机制都是「至少一次」。列出会重复触发的三个地方，以及统一的解法。
     - 要点：**EventBridge Scheduler 的调用是至少一次**；**SQS 标准投递是至少一次**；
       **Step Functions 的任务超时后可能其实已经成功**。统一解法：**执行键上的 DynamoDB 条件写**
       （`jobId#scheduledTime` 加 `attribute_not_exists`），在干活之前写，把重复调用变成 no-op 确认。
       没有它，"1M 作业/天高可用"的真实含义是"有未知数量的作业跑了两次"——
       **给你可用性的那个重试，正是破坏正确性的那个东西。**
166. 🟡 为什么 SQS FIFO 在这里通常是错的捷径？
     - 要点：两点——**按消息组封顶吞吐**，以及**去重窗口只有 5 分钟**，
       比任何值得调度的作业的重试horizon都短。也就是说它既限速又给不了你真正需要的幂等。

### 13.2 通知系统（notification-system）

167. ☆ 🟡 通知设计里「整个调度器组件消失」是怎么发生的？哪两个前提必须同时成立？
     - 要点：原设计要存未来任务、分区、扫描到期、入队；**EventBridge Scheduler 直接接收带精确时间戳的
       一次性 schedule**，支持数百万个，直接调用目标并可在完成后自删——
       于是"定时通知"不是一行要扫的记录，而是一个按通知 id 命名的 schedule。
       两个前提：① **幂等必须做对**（调用是至少一次，会触发两次）；
       ② **schedule 是资源不是行**——一千万个就是一千万次 API 调用和一个配额；
       超过这个尺度，群发要**折叠成每个人群一个 schedule**，扇出移到目标里。
168. ☆ 🔴 幂等键写在 provider 调用之前还是之后？这个选择的语义差别是什么？
     - 要点：写在**之前**＝用"极少数通知丢失"换"永不重复发送"；写在之后＝相反。
       营销流量应选前者，**密码重置应选后者**（宁可重复也不能不到）。
       所以它必须是**消息上的一个字段（按渠道/消息类决定）而不是全局策略**。
       另外两个看似可行的机制要否掉：SQS FIFO 内容去重**只有 5 分钟窗口**（provider 超时后的重试很容易落在窗外）、
       Lambda 自己的重试语义**根本不是去重机制**。
169. ☆ 🔴 「偏好与限流是 AWS 不做的那部分」——具体有哪四项？哪一项有真实的并发危险？
     - 要点：① **退订 / 渠道同意**（错了是**合规事故**，不是 bug）；② **免打扰时段**（错了就是凌晨三点的推送，
       也就是用户卸载的原因）；③ **每用户每日上限**；④ **每租户发送速率**（一个租户的营销活动会把
       别人的事务通知饿死）。有并发危险的是**每日上限**：两个 worker 读-改-写会双双通过上限 2，
       必须用 `UpdateItem` 的 `ADD` 加当前值条件做成**一次原子调用**；
       放在 ElastiCache 里更快，但那是**法律意义上的记录**，多一个真相源不合适。
       还有一条铁律：**事务类消息绕过全部规则**，而且"消息类别"必须是一等字段，
       否则终会有人用营销规则抑制掉一封安全邮件。
170. ☆ 🟡 这些检查为什么必须在 ingest 做，而不是在渠道 worker 里做？
     - 要点：在 worker 里做，**扇出到四个渠道就查四次**，而且四次的结果可能**互相矛盾**
       （读到不同版本的偏好），还浪费四倍读。在 ingest 做一次，把判定结果随消息带下去。
171. ☆ 🔴 「按渠道分队列」是显然的，也是不够的。缺的是什么？
     - 要点：缺**按优先级分队列**。真正要命的队列是"卡在 400 万封营销邮件后面的那封密码重置"。
       渠道隔离解决的是 provider 故障隔离，优先级隔离解决的是**延迟隔离**，两者都要。
172. 🟡 每个 provider 的熔断器在 AWS 上落成什么？为什么说它是「把 provider 的速率限制表达成基础设施」？
     - 要点：**Lambda 事件源的最大并发（maximum concurrency）**——它直接限制同时调用 provider 的函数数，
       队列吸收积压。于是"provider 每秒只接受 200 个请求"这件事不再写在代码的重试逻辑里，
       而是一个可审计、可改、不会被绕过的配置项。
173. 🟡 SES 的送达率怎么监控？为什么必须在被限流之前发现？
     - 要点：SES 事件目标 → Firehose → S3，对**退信率与投诉率**告警——
       一旦 AWS 判定账号声誉过低会**限流甚至暂停发送**，那时候再修已经影响全部邮件。
       这是一个典型的"**外部系统对你的评价**也是一个必须监控的 SLI"的例子。

### 13.3 网络爬虫（web-crawler）

174. ☆ 🔴 「礼貌性是队列拓扑，不是抓取器的一个设置」——请解释，并给出三个推论。
     - 要点：由**调度器**决定某个 URL 何时可被抓，做法是每 host 一个 item 加**按秒分桶的自重置计数器**
       （`sk = W#<秒>`，条件 `hits < budget`，带 TTL），条件失败就用 `DelaySeconds` 重新入队而不是抓取。
       推论：① **frontier 不能是 FIFO**——某个域名的一百万 URL 会饿死后面所有人，
       每 host 预算 + 延迟重入队把队列变成公平调度器；② **优先级用"哪个队列"表达**
       （fast / normal / slow 各自的消费者数量），因为单个 SQS 队列内部没有优先级；
       ③ **`DelaySeconds` 上限 15 分钟**——比这更礼貌（例如每小时一次）就必须用
       EventBridge Scheduler 或一个"下次可抓时间戳"，而不是 SQS 延迟。
175. ☆ 🔴 百亿级的「见过没有」集合怎么做？为什么共享 Bloom filter 被拒而本地的可以？
     - 要点：**DynamoDB 条件写 `sha256(canonical_url)` 作为真相**（每个**新** URL 一次写、每次检查一次读）；
       每个抓取进程可以带**进程内 Bloom filter 作为提示**。差别在于误判的后果：
       本地过滤器的假阳性**只丢一个 URL、影响不可见**；
       **共享**过滤器的假阳性**让这个页面对所有人永久丢失**，而"为什么这个页面从没被抓过"
       是一个无法调试的问题。另外：**哈希前必须做 URL 规范化**（scheme、host 大小写、默认端口、
       末尾斜杠、查询参数排序、去 fragment、剥离跟踪参数），否则 seen-set 会被同一个页面的一百个变体填满。
176. ☆ 🟡 抓取器为什么用 Fargate 而不是 Lambda？请给出四条理由。
     - 要点：① 抓取是**I/O 密集且长尾**——慢 host 占住 worker 30 秒，Lambda 按全内存计费每一毫秒的墙上时间；
       ② **连接复用**对同 host 很重要，而每个 Lambda 执行环境各有自己的池；
       ③ **DNS 缓存**只有在进程活得够久时才有意义；④ 负载是**稳定的**而不是尖峰的，
       这正是按秒的容器计价胜过按调用计价的地方。Lambda 留给调度器、robots 抓取、链接提取扇出
       （短、突发）。抓取器吃 **Spot** 很合适：被杀掉的抓取就是一条回到队列的消息。
177. 🟡 这道题的账单里「没人计划的那一行」是什么？
     - 要点：**NAT 网关的数据处理费**。爬虫从私有子网出网抓取整个互联网的内容，
       每 GB 都要付 NAT 处理费（约 $0.045/GB）——在抓取量面前这是主要成本之一。
       缓解：抓取器放公有子网（带安全组限制）或用自管 NAT 实例、对目标内容做大小限制与类型过滤。

### 13.4 信息流聚合（news-feed-aggregator）

178. ☆ 🔴 推模式、拉模式还是混合？请给出阈值，并说明 AWS 上「扇出在哪里跑」这个细节为什么重要。
     - 要点：**写扇出**（推）每篇文章对每个订阅者一次写——50 万订阅者的源就是 50 万次写；
       **读扇出**（拉）每次刷新要查 N 个源并合并——关注 500 个源的用户每次刷新都付这个代价；
       **混合**是唯一活得下来的：**订阅者 < 约 1 万走写扇出，以上走读扇出**，
       并把它做成**源上的一个标志位**，可以不发版就逐源调整。
       AWS 细节：扇出跑在**文章表的 DynamoDB Stream → Lambda**，
       于是有序、至少一次、且没有自己的队列——而且 50 万订阅者的扇出是
       **一次必须分页的 Lambda 调用**，不是一次会超时的写。
       因为流是至少一次，feed 写必须用**确定性的排序键 `PutItem`**，重投递就是覆盖而不是重复。
179. ☆ 🟡 「先去重再排序」为什么是硬要求？三种去重手段怎么排优先级？
     - 要点：去重放在排序之后就**太晚了**——排序器的预算已经花在近似重复上了，
       用户看到的正是"同一条新闻来自五个源"这个最显眼的缺陷。三级：
       ① **URL 规范化 + 哈希 + 条件写**（抓完全重复的转载，几乎免费）——**总是跑**；
       ② **OpenSearch `more_like_this`** 对最近 N 小时（抓改写与联合发布，每篇一次查询）——**都跑**；
       ③ **Bedrock Titan embedding + OpenSearch k-NN**（抓翻译与深度改写，每篇一次 embedding）——
       **只在第二级判定模糊时跑**。这样 embedding 账单与"难例数量"成正比，而不是与语料规模成正比。
180. ☆ 🟡 10 万并发 WebSocket 是这道题最容易被低估的成本。为什么？有哪三条出路？
     - 要点：API Gateway WebSocket 按**连接分钟数 + 消息**计费，
       10 万连接持有一小时就是 **600 万连接分钟**，**不管有没有发东西**。出路：
       ① **空闲断连**，客户端重连——"实时更新"很少真的意味着"永远一秒内"，
       移动端 60 秒轮询在每个维度上都比持有 socket 便宜；② **AppSync**，当客户端要的是按字段订阅时；
       ③ **推送通知（Pinpoint / SNS）**——"你有新消息"这个场景占了大多数，而且用户不在应用里时它不花钱。
       另外必须处理 410 Gone 删除死连接行，否则扇出打给空气。

### 13.5 直播（live-streaming）

181. ☆ 🔴 「延迟是一份按档定价的菜单」——三档各是什么路径、什么代价？这个决定该记在哪里？
     - 要点：**亚秒（200–800ms）**= IVS 实时 stage / WebRTC，按参与者分钟计费、stage 规模有上限，
       适合互动（拍卖、连麦、家教）；**低延迟（1–3s）**= IVS 低延迟频道，或
       MediaLive → MediaPackage LL-HLS → CloudFront，按输入小时 + 出流 GB，是体育赛事与带聊天的活动的默认；
       **标准（6–30s）**= 大分片的 HLS/DASH，**每观看小时最便宜**，适合 24/7 线性频道。
       规则：**延迟是按频道选的，记录在频道记录上，绝不全局设定**——
       把所有频道都放进亚秒档，等于为一个多数频道用不到的功能把账单乘了好几倍。
182. ☆ 🔴 500 万人同时看一个频道，为什么这几乎完全是 CloudFront 的问题？三个前提是什么？
     - 要点：① **分片可缓存且共享**——同一区域的所有观众请求同一个分片 URL；
       **如果播放器在 URL 上附加了每用户的查询串（例如会话令牌），缓存键就每人一份，
       源站会看到 500 万个请求而不是一个**——这是直播里最贵的单一错误；
       ② **playlist 的 TTL 要合理**——LL-HLS 的媒体 playlist 每个分片都更新，
       TTL 必须**小于分片时长且大于零**（零＝每播放器每分片打一次源站，500 万 ×(1/2 秒) 不是源站该看到的速率）；
       ③ **开启 Origin Shield**，把所有边缘的未命中收敛成一次源站请求。
       无论如何都随观众线性增长的是**出流带宽**：500 万 × 3Mbps = **15Tbps**，那就是账单本身。
183. 🟡 ABR 阶梯为什么是转码账单？在 5 万频道的规模上怎么定？
     - 要点：MediaLive 按输入小时**和每个输出**计费，所以**阶梯的每一级都是 5 万的乘数**。
       定法：5 级（1080p→240p）只给**付费/优质频道**；3 级（720p/480p/240p）作为 UGC 频道的默认；
       **passthrough 不转码**用于可信编码器的投稿源（观众设备自己适配或失败）。
       这是继出流之后**最大的可控成本项**。
184. 🟡 IVS 与 MediaLive+MediaPackage 怎么选？为什么在 5 万频道时理由是运维性的而不是技术性的？
     - 要点：IVS 一个服务包完投稿、转码、打包、全球分发与聊天，**没有 CloudFront 分发要配、没有源站要扩**；
       **5 万个 MediaLive 频道意味着 5 万个要创建、监控、启停的资源**——这就是运维性的理由。
       选组合路径的条件是 IVS 给不了的东西：自定义 ABR 阶梯、影视级 DRM（SPEKE）、
       服务端广告插入（MediaTailor）、SCTE-35 标记、时移观看、特定打包格式——
       每一个旋钮从此都是你的。

### 13.6 文件存储与同步（file-storage）

185. ☆ 🔴 内容定义分块（content-defined chunking）解决了什么？它带来的那个「必须命名的后果」是什么？
     - 要点：解决"2GB 文件改一个字节不能变成 2GB 上传"——用滚动哈希切出平均约 4MB 的块，
       **插入只移动一个块边界**而不是之后的所有边界；每块以 **SHA-256 为键**存进 S3（`chunks/<sha256>`），
       于是存储**跨所有用户全局自动去重**；文件版本是 DynamoDB 里一个有序的块哈希列表；
       上传变成"问哪些哈希你已经有了，只传剩下的"（一次 `BatchGetItem`）。
       **后果**：块在用户之间共享，所以**删除必须引用计数**——
       一个粗率的"删除该用户数据"作业按前缀删块，会摧毁别人的文件。
       引用计数放 DynamoDB，由处理删除的同一条流递减，清理只删计数为零的块，并且要有宽限期。
186. ☆ 🔴 「给每个用户一个 IAM 角色 + 前缀策略」为什么行不通？正确的模式是什么？
     - 要点：IAM 的角色数量与策略大小是**账号级配额**，5 亿用户比它大**六个数量级**。
       正确模式正好相反：**一个应用身份**，授权信息放 DynamoDB，用户的可达范围用
       **预签名 URL** 或**限定到单个前缀的短时 STS 会话策略**表达。
       一句话：**IAM 保护服务，应用保护租户**——这与搜索平台在多租户上的结论是同一个，可以推广。
187. ☆ 🟡 两台设备离线编辑后重连，三种冲突策略怎么选？为什么这里不能有锁？
     - 要点：**服务端序号的后写胜出**（一个编辑静默消失）——文档绝不可用，派生文件可以；
       **两个版本都留**（`file (conflicted copy).docx`）——**默认选它，丑但永不丢数据**；
       **操作合并（CRDT/OT）**——只在格式端到端由你控制时。
       机制还是条件写：客户端带上它所基于的版本，`current_version = :expected` 要么赢要么被告知去生成冲突副本。
       **不能有锁**的理由：一个离线设备持有的锁，就是一个谁都编辑不了的文件。
188. 🟡 100PB 规模下，Intelligent-Tiering 替掉了整个「冷热分层子系统」，但有一个必须算的账。是什么？
     - 要点：它**按被监控的对象数计费**。4MB 的块 × 100PB ≈ **250 亿个对象**，
       监控费是真金白银——所以这是**冷端应该用更大块**的论据。
       其余分层：工作集用 Standard、可再生的缩略图用 One Zone-IA（单 AZ 正确，因为可重建）、
       旧版本与"已删除但可恢复"进 Glacier（保留承诺是一个成本决定）。

### 13.7 分布式缓存与 Web 分析（distributed-cache / web-analytics）

189. ☆ 🔴 ElastiCache / MemoryDB / DAX 三选一，有一个单句判据。是什么？
     - 要点：**"这个缓存周一早上是空的，会坏掉什么？"**
       答"没事，会自己填回来"→ **ElastiCache**（默认）；
       答"购物车全丢了"→ 那它从来就不是缓存，应该在 **MemoryDB**（多 AZ 事务日志，持久）或 DynamoDB；
       **DAX** 只用在 DynamoDB 前面，它在**写路径上**，所以顺带消灭了失效问题。
       补充：ElastiCache Serverless 去掉了分片数决策（按存储与 ECPU 计费），
       适合峰值未知的负载，不适合稳定可预测的负载（预置节点更便宜）。
190. ☆ 🔴 「缓存该放在哪一层」——AWS 上有四个位置，为什么应用层通常只排第三？
     - 要点：**CloudFront**（整个响应，按 URL，边缘单数毫秒）→ **API Gateway 缓存**（按 stage 与 key，同区域）
       → **ElastiCache**（对象与查询结果，同 AZ 亚毫秒）→ **进程内**（纳秒，但**每个 Pod 各自发散**）。
       排序的理由：**边缘命中对下游零成本**——不占节点、不占连接、不占应用线程。
       规则：**先缓存响应，再缓存对象**，分布式缓存留给按用户/按租户、
       或者"算起来太贵但又太小不值得做成页面"的值。
191. ☆ 🔴 「失效才是设计，其余都是配置」——四种失效策略各错在哪？AWS-only 的推荐组合是什么？
     - 要点：**只用 TTL**——每个条目永远都带一个等于 TTL 的陈旧窗口；
       **write-through**——一次写里有两个系统，缓存写失败时只能选"让写失败"或"提供陈旧数据"；
       **write-behind**——写最快，但缓存成了真相源（于是该用 MemoryDB）；
       **显式失效**——正确，直到某个写入方忘了，而这个失败是**静默且永久**的。
       推荐：**TTL + 事件驱动失效**（DynamoDB Streams / RDS 经 DMS → Lambda → `DEL key`）——
       流保证常态新鲜，TTL 是失效链路挂掉时的**兜底上界**。
       只有其中一个的设计，必须说明它接受哪种失败。
192. ☆ 🟡 缓存雪崩（thundering herd）为什么托管服务解决不了？最高性价比的一行防御是什么？
     - 要点：热键过期的瞬间所有请求同时穿透到数据库——**缓存的保护作用恰好在最需要时反转**。
       托管服务没有这个开关，全部靠设计：**给 TTL 加抖动**（`ttl = base + random(0, base/10)`）
       是一行代码、也是性价比最高的防御，因为它避免"同时写入的一百万条目同时过期"；
       其次是**单飞**（第一个未命中者用 `SET key NX PX 5000` 拿短锁去重算，其余短暂等待后重读）。
193. ☆ 🔴 Web 分析的采集层「可以什么都没有」。这是怎么做到的？代价是什么？
     - 要点：把采集做成 **CloudFront 上的 1×1 像素**，事件放在查询串里——
       CloudFront 已经在边缘终结 TLS、已经用单数毫秒响应、已经把 URI、查询串、客户端 IP、
       User-Agent、Referer 与边缘位置**逐请求记了日志**，那就是完整的事件。
       实时日志秒级流到 Kinesis Data Streams，标准日志落 S3。**没有应用要扩容**，
       也不需要为"50ms 以内响应"辩护，因为 CDN 边缘本来就更快。
       代价：**失去对响应的控制与在门口拒绝畸形事件的能力**——对分析而言两者都可接受
       （像素无论如何返回同一个 GIF，畸形事件在处理阶段过滤，且过滤成本是可度量的）。
194. ☆ 🔴 实时路径与批路径的分界规则是什么？哪一类需求要当场推回去？
     - 要点：规则是**实时路径只回答计数类问题**（当前在线人数、每秒事件数、热门页面、错误率，
       存在 DynamoDB 里的一小组固定计数器）。**漏斗是跨会话的 join，归因是跨周的 join**，
       两者都不属于流式聚合器——把它们放进去，就是让一个实时分析系统变成一个**实时地给出错误答案**的系统。
       所以"30 秒延迟的实时看板"可以满足，**"实时漏斗"是一个应该推回去的需求**。
195. ☆ 🔴 Athena 按扫描字节计费，文件布局怎么决定账单？三件必须做的事是什么？
     - 要点：① **Parquet 而不是 JSON**——列式让"按国家看页面浏览量"只读两列而不是整个事件（Firehose 进来时就转换）；
       ② **按 `date/property` 分区**（就这个顺序，因为几乎所有查询都同时过滤这两者，且 property 基数高）；
       ③ **合并小文件（compaction）**——每秒 116 万事件在 Firehose 小缓冲下产出海量小对象，
       Athena 在数百万对象上的**查询计划时间会变成查询时间**，每天一个 Glue 作业把昨天重写成大 Parquet 文件不是可选项。
       另外单独提一句 **partition projection**：让 Athena 从谓词推算分区位置而不是去 Glue catalog 列举，
       在 26 个月 × 数百万 property 的规模上，这是"目录能用"与"目录超时"的差别。
