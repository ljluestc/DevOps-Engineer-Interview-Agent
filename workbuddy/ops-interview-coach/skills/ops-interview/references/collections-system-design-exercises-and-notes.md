## 一、系统设计基础：单点、CDN、分层与服务拆分（devops-exercises System Design，7 题）

> 主题取自 https://github.com/bregman-arie/devops-exercises#system-design 章节开头的基础概念部分（单点故障、CDN / Multi-CDN、三层架构、单仓 vs 多仓、单体 vs 微服务、Service Mesh、松耦合、消息队列）。该仓库为 CC BY-NC-ND 3.0，**题目与要点均由本项目按这些主题原创撰写**，按 Senior SRE 系统设计面试的深度改写为带故障模式、数字与取舍的追问。

1. ☆ 🟡 给你一张「LB → 3 台 Web → 1 主 1 从 MySQL → 单个 Redis → 单个 NFS」的架构图，请系统地找出所有单点故障（SPOF），并按「爆炸半径 × 发生概率 × 修复成本」排出治理优先级。
   - 要点：SPOF 不止看「几台机器」，要沿请求路径逐层看：DNS（单服务商 / TTL 过长）、LB 本身（单实例或单 AZ）、证书与密钥服务、主库（从库存在但**无自动切换 = 仍是 SPOF**）、Redis（若承担 session / 锁则是硬依赖）、NFS（共享存储常被遗忘）、单 AZ / 单 Region、甚至「只有一个人会操作」的人员单点和单一 CI 账户。治理排序：先处理**有状态且无自动切换**的组件（主库、NFS、Redis session），再处理无状态层冗余；每项写清检测（健康检查 / 告警）与切换时长（RTO），并用故障演练验证「冗余真的生效」——未演练过的副本按 SPOF 对待。
2. ☆ 🔴 什么情况下值得上 Multi-CDN？流量怎么在多家 CDN 之间调度，带来哪些新的运维负担？
   - 要点：动机：单 CDN 故障 / 区域劣化（历史上多次大厂 CDN 全局事故）、地域性能差异（某些国家某家节点弱）、价格议价与承诺量、合规（中国大陆需备案的本地 CDN）。调度方式：**DNS 层加权 / 基于 RUM（真实用户测速）的智能 DNS**（如 NS1、Cedexis 类方案）、客户端 SDK 选路、按路径 / 按内容类型分流（视频走 A、API 走 B）。新负担：缓存键 / 头部 / 签名 URL / TLS 证书**在多家行为必须一致**、回源流量翻倍（每家各自冷缓存，需 origin shield）、清缓存要多家同时 purge、日志与指标口径不一需统一、DNS TTL 决定切换速度（30–60s 级）；故障判定要基于多地探测 + RUM，避免误切导致全量回源打爆源站。
3. 🟡 三层架构（展示层 / 应用层 / 数据层）在今天的云原生环境里还成立吗？每一层分别该怎么扩容、怎么做安全隔离？
   - 要点：作为**逻辑分层**仍成立：展示层（CDN + 静态资源 / BFF）、应用层（无状态服务，水平扩容 + 自动伸缩）、数据层（有状态，靠读写分离 / 分片 / 托管数据库扩容）。安全：按层划子网与安全组，**只允许相邻层通信**（Web 不能直连 DB），数据层不出公网。代价：每跳增加延迟与序列化开销；层间强同步调用在高峰下形成级联；变更往往要跨层协调。追问点：三层是「部署分层」，与微服务的「业务垂直拆分」是正交的，一个微服务内部仍可以是三层。
4. ☆ 🔴 一个 5 年历史的单体要拆微服务，你会用什么标准决定「拆不拆、先拆哪块」？拆完后运维侧最先暴露的三类问题是什么？
   - 要点：拆分驱动应是**组织与变更频率**（多团队互相阻塞发布、某模块需独立扩缩、故障隔离需求），而不是技术时髦；先拆变更频繁、边界清晰（数据独立）、资源画像差异大的模块，用 Strangler Fig 在网关层逐步切流。运维侧三类问题：① **分布式故障**：网络调用替代函数调用，超时 / 重试风暴 / 级联雪崩，需超时预算、熔断、限流；② **可观测性**：一次请求跨 N 服务，必须有 trace ID 贯穿、统一日志与 RED 指标，否则排障时间暴涨；③ **数据一致性与发布协调**：拆库后跨服务事务变成 Saga / 最终一致，接口契约版本化与向后兼容。反例提醒：「分布式单体」——拆了服务但共享一个库、必须一起发布，代价全拿、收益全无。
5. 🟡 Service Mesh 解决了什么问题？在什么规模 / 场景下你会反对引入它？
   - 要点：把 mTLS、重试 / 超时 / 熔断、流量切分（金丝雀）、遥测从业务代码下沉到 sidecar（Envoy）或节点级代理（Istio ambient 的 ztunnel + waypoint），实现多语言统一治理。反对场景：服务少（< 十几个）、单语言且已有成熟 SDK（如 gRPC 拦截器）、团队无人能排查 Envoy 配置、对延迟极敏感（sidecar 每跳增加亚毫秒到毫秒级）、资源紧（每 Pod 一个 sidecar 的内存 / CPU 乘以 Pod 数）。运维要点：控制面故障时数据面应「保持最后已知配置」继续工作；升级需按 revision 金丝雀；排障多了一层（503 UF / UH 等 Envoy 响应标志要会看）。
6. 🟡 「松耦合」在架构里具体体现在哪些维度？请用消息队列举例说明它解耦了什么、又引入了什么新风险。
   - 要点：维度：**时间解耦**（生产者不需消费者在线）、**空间解耦**（不知道对方地址）、**速率解耦**（削峰填谷）、**部署解耦**（各自发布）、契约解耦（schema 演进）。消息队列（Kafka / RabbitMQ / SQS）带来的新风险：投递语义（至少一次 → 消费者必须幂等）、顺序只在分区 / 队列内保证、**积压（consumer lag）成为新的核心 SLI**、毒消息需死信队列、端到端延迟不再可预测、调用链断裂需在消息头传 trace context；还有「异步把错误藏起来」——生产者成功不代表业务成功，需要对账或回执。
7. 🟡 Mono-repo 和 Multi-repo 对 CI/CD 和发布运维分别意味着什么？你在什么条件下推荐 mono-repo？
   - 要点：Mono-repo：原子化跨模块变更、统一依赖版本与工具链，但需要**按变更路径的增量构建 / 测试**（Bazel、Nx、Pants、Turborepo 或 path filter），否则 CI 时长随仓库线性增长；clone 体积大需 sparse checkout / partial clone；权限粒度靠 CODEOWNERS。Multi-repo：团队自治、CI 简单且快，但跨仓变更要协调多次发布，依赖版本漂移（钻石依赖）、共享库升级需要推动全员。推荐 mono-repo 的条件：有平台团队维护构建系统、强耦合组件需频繁同时变更、希望统一安全扫描与依赖治理；无论哪种，**部署单元与仓库结构应解耦**（一个仓库可产出多个独立发布的制品）。

## 二、可扩展性与韧性：伸缩、高可用、容灾与零停机（devops-exercises System Design · Scalability，7 题）

> 主题取自 https://github.com/bregman-arie/devops-exercises#system-design 的 Scalability 小节（可扩展性 vs 弹性、HA vs DR、容错、垂直 vs 水平扩展、韧性、一致性哈希、无停机更新、输入小增长导致处理时间暴涨、从几个用户扩到几百用户）。题目与要点由本项目原创撰写，侧重可量化的判断与运维追问。

8. 🟢 可扩展性（Scalability）和弹性（Elasticity）有什么区别？各自用什么指标证明你做到了？
   - 要点：可扩展性是**能力**：加资源后吞吐近线性增长（关注扩展效率、瓶颈在哪，Amdahl / USL 曲线）；弹性是**自动化与速度**：负载变化时多快自动增减资源、缩容是否省钱。证明：可扩展性看压测「实例数 vs QPS / p99」曲线是否线性、拐点在哪；弹性看扩容反应时间（从指标越线到新实例 Ready 的分钟数，含镜像拉取 / 预热）、高峰期 SLO 是否守住、低谷期资源利用率与成本。一个系统可以可扩展但无弹性（手工加机器），也可以「有弹性但不可扩展」（自动扩了但被数据库卡死）。
9. ☆ 🟡 高可用（HA）、容错（Fault Tolerance）和容灾（DR）分别对应什么故障域和什么指标？请为一个 99.95% 的核心服务给出组合方案。
   - 要点：容错：组件故障时**用户无感**（冗余 + 自动切换，如 RAID、多副本仲裁）；HA：以可用性百分比衡量，故障域通常是实例 / 机架 / AZ，靠多副本 + 健康检查 + 自动摘除；DR：应对 Region 级灾难、数据损坏、误删、勒索，用 **RPO / RTO** 衡量，靠异地备份、跨区复制、演练。99.95% ≈ 每月约 21.9 分钟不可用预算：多 AZ 部署无状态层 + 数据库多 AZ 同步副本自动切换（HA）；跨 Region 异步复制 + 定期快照与**不可变备份**（DR，RPO 分钟级、RTO 小时级），并强调**HA 不能代替备份**——误删会被同步复制到所有副本。
10. 🟡 垂直扩展什么时候比水平扩展更合理？水平扩展前通常要先改造哪些东西？
   - 要点：垂直扩展合理：单机有状态组件（关系型主库、单线程热点如 Redis 主）、软件不支持分布式、规模可预期且大机型仍够用、追求运维简单；缺点是上限（最大机型）、升级常需重启停机、单点、单价非线性上涨。水平扩展前置改造：**应用无状态化**（session 外置到 Redis / JWT）、本地文件改对象存储、定时任务去重（选主 / 分布式锁）、连接池总量控制（N 实例 × 池大小别打爆 DB `max_connections`）、引入 LB 与健康检查、数据层分片或读写分离。
11. ☆ 🔴 解释一致性哈希：为什么普通取模哈希在扩缩容时是灾难？虚拟节点解决了什么，又有什么代价？
   - 要点：`hash(key) % N` 在 N 变化时约 (N-1)/N 的 key 重映射，缓存场景表现为**命中率断崖 + 回源打爆 DB**。一致性哈希把节点与 key 映射到哈希环，增删一个节点只迁移约 1/N 的 key。虚拟节点（每物理节点 100–200 个 vnode）解决**负载不均**和「节点下线时负载全压到一个邻居」的问题，并可按权重分配异构机器；代价是环元数据变大、查找 O(log V)、迁移涉及更多小区间。变体：Jump Consistent Hash（无内存、只支持尾部增删）、Rendezvous / HRW 哈希（Envoy / 部分 LB 用 Maglev）。追问：热点 key 一致性哈希也救不了，需要副本或本地缓存。
12. ☆ 🟡 foo.com 由 LB 后的多台 Web + 后端 API + 数据库组成，如何做到所有组件更新都零停机？数据库 schema 变更怎么办？
   - 要点：无状态层：滚动 / 蓝绿 / 金丝雀，配合 **readiness 探针、LB 连接排空（deregistration delay）、优雅退出（处理 SIGTERM、preStop sleep 等待端点摘除）**，保证 `maxUnavailable` 下容量够用；前后端版本并存期间 API 必须向后兼容。LB 自身：托管 LB 或双实例 + VIP / DNS。数据库：**expand / contract（扩展-收缩）模式**——先加列 / 加表（兼容旧代码）→ 双写 / 回填 → 切读 → 再删旧列，绝不在一次发布里做破坏性变更；大表 DDL 用 gh-ost / pt-online-schema-change 或原生 online DDL。验证：发布期间持续拨测，错误预算不应有可见消耗。
13. 🔴 用户反馈「输入数据只多了一点点，处理时间却暴涨数倍」，你会怀疑哪些原因？怎么定位？
   - 要点：典型非线性根因：① 算法复杂度 O(n²)（嵌套循环、逐条查重）；② **越过资源阈值**——数据刚好超出内存 / CPU cache / 页缓存导致开始 swap 或磁盘溢写（排序、hash join spill），或超出 JVM 堆导致频繁 Full GC；③ 排队论：利用率接近 100% 时等待时间 ∝ 1/(1−ρ) 急剧上升；④ 数据库执行计划突变（统计信息变化走了全表扫描）、锁竞争；⑤ 批量变大触发超时 → 重试放大。定位：对比两次运行的 profile（火焰图）、`vmstat` / `sar` 看 swap 与 iowait、GC 日志、`EXPLAIN` 对比执行计划，并用 2×、4× 数据量做规模化测试画出耗时曲线判断是复杂度还是阈值问题。
14. 🟡 一个单机部署（Web + DB 同机）的小应用要扩到支撑数百并发用户、未来上万，你的演进步骤和每一步的触发信号是什么？
   - 要点：步骤：① Web 与 DB 拆机（信号：CPU / 内存互相争抢）；② 加 LB + 多个无状态 Web 实例、session 外置（信号：单 Web CPU 持续 > 60–70%、需要无停机发布）；③ 加缓存层与 CDN 承接静态资源（信号：DB 读 QPS 高、重复查询多）；④ DB 读写分离 / 连接池代理（信号：读多写少、连接数逼近上限）；⑤ 异步化——队列承接邮件、报表等慢任务（信号：p99 被少数慢操作拖累）；⑥ 多 AZ 与自动伸缩、最后才考虑分库分表。每一步先上监控（USE + RED），以数据驱动而非预先过度设计。（与 `system-design` Q4 的「0 到百万用户」互补：此题强调触发信号与早期阶段的取舍。）

## 三、缓存与迁移：命中率、淘汰策略与平滑迁移（devops-exercises System Design · Cache / Migrations，6 题）

> 主题取自 https://github.com/bregman-arie/devops-exercises#system-design 的 Cache 与 Migrations 小节（何时用缓存、分布式缓存、替换策略、为什么不全放缓存、迁移规划、Branch by Abstraction）。题目与要点由本项目原创撰写，避免与 `system-design` Q7（分布式缓存总论）重复，侧重淘汰策略细节、容量与迁移操作。

15. 🟡 你怎么判断一个接口「值得加缓存」？上线后用哪几个指标判断缓存是在帮忙还是在添乱？
   - 要点：值得加：读多写少（读写比 > 10:1）、计算或查询昂贵、数据可容忍一定陈旧、访问有局部性（Zipf 分布，少量热 key 占大部分请求）。上线后看：**命中率**（以及按 key 前缀拆分的命中率）、回源 QPS 与 DB 负载是否真的下降、缓存层 p99 延迟、淘汰速率（evictions）与内存使用、陈旧数据导致的业务投诉 / 不一致数。添乱信号：命中率 < 50% 却额外增加一跳延迟、缓存失效时 DB 被打爆（缓存已成承重墙却无降级）、大 key / 热 key 导致单分片 CPU 打满。
16. 🔴 自建分布式缓存集群（如 Redis Cluster / Memcached + 客户端分片）时，节点故障、扩容和「缓存冷启动」分别会发生什么？怎么减轻？
   - 要点：Redis Cluster 16384 个哈希槽，主挂后由副本经 gossip 投票升主（`cluster-node-timeout` 决定故障检测时长，期间该槽不可写）；异步复制意味着切主可能**丢最近写入**。扩容：槽迁移期间客户端收到 `MOVED` / `ASK` 重定向，大 key 迁移会阻塞。Memcached 客户端一致性哈希下节点故障只损失 1/N。冷启动（整集群重启 / 新 Region）：命中率归零、回源洪峰——缓解：预热脚本按热 key 列表回填、请求合并（singleflight）、回源限流、逐步切流量、给 TTL 加随机抖动避免同时过期。监控：`instantaneous_ops_per_sec`、`evicted_keys`、`keyspace_hits/misses`、复制偏移量、`used_memory` 与 `maxmemory` 比。
17. 🟡 比较 LRU、LFU、FIFO、TTL 与 Redis 的近似 LRU / LFU：各适合什么访问模式？一次全表扫描会对 LRU 缓存造成什么破坏？
   - 要点：LRU 适合时间局部性强的负载，但**一次性扫描（批处理 / 爬虫遍历）会把热数据全部挤出（cache pollution）**；LFU 抗扫描、适合长期稳定热点，但对热点漂移反应慢（需计数衰减）；FIFO 实现最简单、命中率通常较差；TTL 管的是「新鲜度」而非容量，常与 LRU 组合使用。Redis 不维护全局 LRU 链表，而是**采样近似**（`maxmemory-samples` 默认 5），策略由 `maxmemory-policy` 选（`allkeys-lru` / `allkeys-lfu` / `volatile-ttl` / `noeviction` 等），LFU 有 `lfu-decay-time` 衰减。抗扫描方案：2Q、ARC、W-TinyLFU（Caffeine）、或批任务绕过缓存。
18. 🟡 为什么不能把所有数据都只写进缓存、不要数据库？如果业务坚持「Redis 当主存储」，你要提出哪些保障条件？
   - 要点：缓存以内存为介质：**单位成本高**（内存约为 SSD 的数十倍）、容量受限会触发淘汰（数据静默丢失）、默认持久化弱（RDB 有间隔丢失窗口、AOF `everysec` 最多丢约 1 秒）、异步复制切主丢数据、查询能力弱（无二级索引 / 事务语义有限 / 无约束校验）。若坚持当主存储：`maxmemory-policy noeviction`、AOF + 定期 RDB 备份到对象存储并做恢复演练、容量告警留 30% 余量、副本 + `min-replicas-to-write` 降低丢写、明确 RPO 并让业务签字；或选用持久化型兼容方案（如 MemoryDB 一类事务日志持久化的服务）。
19. ☆ 🔴 你要把一个核心服务的数据库从自建 MySQL 迁到云上托管数据库（或从 MySQL 迁到另一种存储），请给出迁移计划：阶段、验证、回滚点。
   - 要点：阶段：① 盘点（数据量、QPS、依赖方、隐式依赖如触发器 / 定时任务 / 直连报表）与成功标准；② 全量 + 增量同步（DMS / binlog CDC 如 Debezium、Canal）；③ **双写或 CDC 追平 + 数据校验**（行数、checksum、抽样比对，pt-table-checksum 一类工具）；④ 影子读 / 对比读验证新库结果一致与性能；⑤ 灰度切读 → 短暂停写窗口切写（或双写下切主）；⑥ 保留**反向同步**一段时间作为回滚路径，确认稳定后下线旧库。每个阶段都要有明确的回滚点与 go / no-go 指标（错误率、延迟、复制延迟 < 阈值）；提前做全链路演练、准备 runbook 与沟通计划；注意字符集 / 时区 / 自增 ID / SQL 模式差异。
20. 🟡 什么是 Branch by Abstraction？它和 feature flag、Strangler Fig 有什么关系？在基础设施迁移（例如换消息队列）中怎么用？
   - 要点：在主干上**先引入一个抽象层**（接口），让所有调用方改为依赖抽象 → 在抽象背后并行实现新方案 → 用开关逐步把流量切到新实现 → 删除旧实现与（必要时）抽象层；全程在主干持续集成，无长期分支。与 feature flag：flag 是切换的「开关」，BbA 是代码结构上的「插槽」；与 Strangler Fig：后者在**系统边界**（网关 / 路由）逐步替换，BbA 在**代码内部**替换。换 MQ 示例：定义 `Publisher` 接口 → 同时实现 RabbitMQ 与 Kafka 版本 → 灰度双发并对比消费结果 → 按服务切换 → 下线旧实现；运维侧要为两套实现同时准备监控与告警。

## 四、设计题：视频、图片、短链与延伸问题（devops-exercises System Design · Design a system / More System Design Questions，6 题）

> 主题取自 https://github.com/bregman-arie/devops-exercises#system-design 的 Design a system（视频网站、图片上传网站、短链）与 More System Design Questions 小节（该小节指向作者的 system-design-notebook 仓库）。原仓库只列题目不展开；这里的题目与要点由本项目原创撰写，刻意从**运维视角**切入（容量数字、故障模式、成本、可观测），与 `system-design` Q15 / Q19 等通用设计题互补，出题时可作为深挖追问。

21. ☆ 🔴 设计一个视频点播网站时，从运维角度最贵、最容易出事的环节分别是什么？请估算 100 万日活、每人日均观看 30 分钟的出口带宽量级。
   - 要点：估算：100 万 × 30 min ≈ 3000 万分钟/天；按平均 3 Mbps 码率，日流量 ≈ 3×10⁷ × 60 s × 3 Mb ÷ 8 ≈ 675 TB/天，平均出口约 62 Gbps，峰值按 3× 约 190 Gbps——**带宽 / CDN 费用是最大成本**，因此 CDN 命中率（目标 > 95%）与码率阶梯直接决定账单。最易出事：① 转码管道（队列积压、GPU / CPU 池耗尽、某些编码参数失败需死信与重试）；② 源站回源洪峰（新热门视频首发、CDN 缓存刷新）；③ 播放失败难以从服务端感知——必须采集客户端 QoE 指标（起播时间、卡顿率、码率切换、错误码）；④ 存储分层（多码率副本 × 冷热分层到低频存储）。HLS / DASH 切片 + 签名 URL 防盗链。
22. 🟡 设计一个图片上传网站：上传路径怎么设计才能不让应用服务器成为瓶颈？缩略图生成失败或积压时怎么办？
   - 要点：**客户端直传对象存储**（应用只签发预签名 URL / 分片上传凭证），应用服务器不承载字节流；上传完成事件（S3 Event / 消息队列）触发异步处理：校验类型与大小、病毒 / 内容审核、EXIF 去除（隐私）、生成多尺寸缩略图；也可改为 CDN 边缘按需裁剪（imgproxy、Thumbor、云厂商图片处理）减少预生成存储。失败处理：任务幂等（以对象 key + 尺寸为幂等键）、指数退避重试、死信队列 + 告警、前端在缩略图未就绪时降级显示原图或占位图；积压时按队列深度自动扩容 worker。监控：上传成功率、处理延迟 p99、队列深度、存储增长与每月成本。
23. ☆ 🔴 短链服务的读路径上，301 与 302 的选择、CDN 缓存和数据库之间是什么关系？如果一个短链在 1 分钟内被访问 5000 万次，系统的哪一层先扛不住？
   - 要点：301（永久）会被浏览器与中间缓存长期缓存，**省流量但失去点击统计与改目标 / 封禁的能力**；302 / 307 每次回到服务端，可统计但成本高；折中是 302 + CDN 短 TTL（如 60s）缓存重定向响应，统计改为边缘日志异步汇总。5000 万 / 分钟 ≈ 83 万 QPS 的单 key 热点：若无 CDN 缓存，先扛不住的是**承载该 key 的缓存分片（单 Redis 主 10 万级 QPS）**，其次是统计写入（每次点击一条写 = 写放大）。对策：CDN / 边缘缓存、应用进程内本地缓存 + 短 TTL、热 key 多副本、点击计数在内存聚合后批量写（或写 Kafka 再流式聚合）。另需防滥用：短链被用于钓鱼时的封禁链路要能在 CDN 上快速 purge。
24. 🟡 为 Pastebin 类服务（用户粘贴文本、生成链接、可设置过期）设计存储与过期清理：元数据和正文分别放哪？过期删除怎么做才不影响线上？
   - 要点：元数据（id、所有者、过期时间、可见性）放 KV / 关系库；正文（可达 MB 级）放对象存储，按 id 前缀散列避免热点前缀。过期：读路径**惰性判断**过期即返回 404，后台批量清理；对象存储用生命周期规则或按过期日期分桶 / 分前缀整体删除；数据库用 TTL 索引（MongoDB TTL、DynamoDB TTL、Cassandra TTL——注意墓碑与 compaction 压力）或按日期分区 drop 分区，而不是大批量 `DELETE`（锁与复制延迟）。追问：滥用治理（恶意内容、数据外泄粘贴）、大小限制、读多写少用 CDN 缓存公开 paste。
25. 🔴 设计一个分布式网页爬虫时，「礼貌性」和「去重」在运维上分别会造成什么问题？爬虫集群被大量目标站封禁或卡在陷阱里，你怎么发现和处理？
   - 要点：礼貌性：按域名（更准确是按 IP / 托管商）限速并遵守 `robots.txt` 与 `Crawl-delay`，实现上是**按 host 分队列 + 每 host 单并发调度**，导致负载不均（少数大站队列极长）；DNS 解析成为瓶颈需本地缓存解析器。去重：URL 级用 Bloom filter（误判可接受）或 RocksDB 一类 KV，内容级用 SimHash 检测近重复；规模到数十亿时 seen-set 的内存与持久化是主要成本。异常发现：按域名统计 4xx / 429 / 403 比例突增（被封）、单域名 URL 数异常膨胀或 URL 深度 / 参数组合爆炸（爬虫陷阱如无限日历）、抓取吞吐下降而队列增长；处理：自动退避该域、限制每域最大页面数与 URL 深度、URL 规范化去参数、出口 IP 池与 User-Agent 标识及联系方式。
26. 🟡 在系统设计面试里被要求「设计一个分布式任务调度 / 通知 / 计数」这类开放题时，你如何把运维关注点（SLO、容量、故障演练、成本）自然地融入设计，而不是最后附一句「加监控」？
   - 要点：在**需求阶段**就给出 SLI / SLO（如通知 99.9% 在 30s 内送达、调度误差 < 1s），用它倒推架构（是否需要队列、多少副本、是否跨区）；估算阶段给出容量与成本数字并说明扩容触发点；每画一个组件就回答「它挂了会怎样、怎么发现（哪个指标 / 告警）、怎么恢复（自动 / 手动、RTO）」；说明发布方式（灰度、feature flag、回滚）和数据层的备份与恢复演练；最后列出取舍与已知风险（例如至少一次投递 → 需幂等）。评分上对应 `system-design-questions.md` 五维中的「可运维性 20%」，SRE 候选人这一项权重更高。

## 五、推荐系统设计：漏斗、召回服务、特征服务与冷启动（ai_interview_note · rec，9 题）

> 笔记以小红书信息流为主线（部分数字作者注明「非真实数据」），覆盖召回 → 粗排 → 精排 → 重排四段漏斗、双塔召回的在线服务与模型更新、曝光过滤、特征服务、分层 A/B 实验和新物品冷启动。这里只取系统设计与可运维的部分，跳过损失函数推导；面试对象是要为这条链路做容量、时延与发布的高级 SRE / 基础设施候选人。

27. ☆ 🔴 画出信息流推荐的四段漏斗，并说明每一段大概进出多少候选、为什么不能用一个模型直接给全库打分？
   - 要点：几十条召回通道各取几十到上百条，合并后去重、过滤（屏蔽作者 / 话题）得到「几千」→ 粗排（小模型，截断到「几百」）→ 精排（大网络逐条打分，几百条，可截断可不截断）→ 重排（多样性抽样 + 规则打散 + 插广告 / 运营位，输出「几十」条曝光）。拆段是在计算量与准确率之间折中：越往后候选越少、单条推理越贵。运维视角要追问每段的时延预算、各通道并发与超时降级（某通道超时就丢弃该路而不是拖垮整次请求），以及「缓存召回」这种复用手段——精排前 50 但未曝光的结果缓存成一条召回通道，曝光即退场，最多被召回 10 次、最多保留 3 天。
28. ☆ 🔴 双塔召回上线后，物品向量和用户向量分别在哪里算、存在哪里？为什么不反过来？
   - 要点：训练完用物品塔离线算出「几亿」个物品向量写入向量库（Milvus / Faiss / HnswLib）并建 ANN 索引；请求到达时用用户塔现场算用户向量，作为 query 做最近邻查找取 top-k。反过来不行：一次请求只有 1 个用户却要几亿物品，线上算物品塔代价不可承受；用户兴趣变化快而物品特征相对稳定，离线缓存用户向量会损失效果。运维风险点：用户塔版本与向量库里的物品向量必须来自同一次训练，发布要原子切换（双索引 / 别名切换），否则召回质量静默下降而不报错。
29. 🔴 双塔模型的「全量更新」和「增量更新」分别怎么做？能不能只做增量？
   - 要点：全量：每天凌晨用前一天全量数据、在昨天参数基础上训练 1 个 epoch（数据随机打乱），发布新的用户塔与物品向量，对数据流要求低。增量：实时收集线上行为、流式生成 TFRecord，做 online learning，只更新 ID Embedding、锁住全连接层（工程考量），每隔几十分钟发布最新的用户 ID Embedding。不能只做增量：小时级、分钟级数据按时间顺序喂入有偏，全量随机打乱能消除时段差异，效果更好；实际系统两者结合。追问：增量发布失败或流式管道积压时如何回退到当日全量版本、如何监控 embedding 新鲜度。
30. 🟡 ItemCF 召回通道离线要建哪些索引？线上一次请求的计算量是多少？
   - 要点：离线建「用户 → 物品」索引（用户最近交互的 last-n）和「物品 → 物品」索引（每个物品最相似的 top-k），用索引把计算量挪到离线。线上：取 last-n（n = 200）→ 每个取 top-k（k = 10）→ 给最多 nk = 2000 个物品估兴趣分 → 返回分数最高的 100 个。设计取舍：离线计算量大、线上计算量小；物品相似度依赖交互，所以对新物品无效（冷启动要靠别的通道）。
31. 🟡 曝光过滤为什么用 Bloom Filter？参数怎么定？它带来哪些运维约束？
   - 要点：每个用户维护已曝光集合，召回后剔除看过的物品；暴力比对是 O(nr)。Bloom Filter 只会误伤（把没看过的判为看过）不会漏过；误伤率 δ ≈ (1 − e^(−kn/m))^k，给定 δ 时最优 k = 1.44·ln(1/δ)、m = 2n·ln(1/δ)。约束：只能加不能删，所以要每天把超过 1 个月的物品（反正不会再被召回）从集合中剔除重建以压低 n；曝光写入链路要走 Kafka + Flink 实时计算，刷新后几秒内生效，否则两次下拉之间会重复出同一条；召回服务向曝光过滤服务取位向量后在本地算哈希。短视频 / 图文用，长视频基本不用。
32. 🔴 排序服务的特征从哪来？为什么说「用户画像可以很大，物品画像不能塞大向量」？粗排三塔模型的推理次数怎么算？
   - 要点：特征分用户画像、物品画像、统计特征（30 天 / 7 天 / 1 天 / 1 小时多粒度计数）和随请求带来的场景特征；用户画像库每次只读 1 个用户，压力小，物品画像库每次要读几千个物品，压力极大，因此大向量不要放在物品侧；画像较静态，可缓存在排序服务器本地；特征打包发 TF Serving 打分后回排序服务器按融合分、多样性与规则排序，返回几十条给主服务器。三塔粗排（COLD 思路）：用户塔 1 次；物品塔只在缓存未命中时算，几千个候选通常只需几十次；交叉塔与上层网络必须做 n 次，计算量主要在上层。行为序列：简单平均可进用户塔，DIN 这类注意力需要候选物品，只能放精排，不能进用户塔；SIM 先按候选从几千条长序列里检索 top-k 再做注意力，普通 DIN 序列一般只有 200 左右。
33. 🟡 推荐团队几十个实验同时跑，流量不够怎么办？分层实验、Holdout、反转实验各解决什么？
   - 要点：用户 ID 哈希分桶（例如 10 桶各 10%）；分层实验按召回 / 粗排 / 精排 / 重排 / UI / 广告分层，同层互斥（同类策略会相互增强或抵消，一个用户只受一个召回实验影响），不同层正交（每层独立分桶，各自可用 100% 用户，召回桶与精排桶交集为 n/100）。Holdout：留 10% 用户不进任何新实验，周期末用 90% 实验桶与之的归一化差值衡量整个部门的收益，然后清空重划分。推全时新开一层（用 90% 用户）；反转实验：在推全层保留一个旧策略小桶，长期观察留存这类有滞后性的指标，兼顾「尽快推全腾出桶」与「长期观测」。
34. 🟡 精排做了负样本降采样后，线上预估点击率为什么偏高？上线时如何校准与监控？
   - 要点：训练只用 α·n₋ 个负样本（α ∈ (0,1)），预估 CTR 系统性高于真实值，α 越小高估越重；线上先出 p_pred，再按 p_true = α·p_pred / ((1 − p_pred) + α·p_pred) 校准后再进融合分。融合分本身是多目标预估的加权和或乘积形式，权重靠 A/B 调。运维信号：按天对比校准后的预估 CTR 与实际 CTR，偏差突变通常意味着采样率、特征缺失（覆盖率低的特征要有合理默认值）或模型版本不一致。
35. ☆ 🔴 新发布的 UGC 内容没有交互、没有 ID embedding，召回和流量分配该怎么设计？怎么评估冷启动做得好不好？
   - 要点：召回：ItemCF 不适用；双塔改造——新物品共享一个 default embedding，或取内容最相似的 k 个高曝光物品 embedding 的平均；按 1 小时 / 6 小时 / 24 小时 / 30 天建多个向量召回池，共用一个双塔模型不增加训练成本；类目 / 关键词倒排（按时间倒序取最新 k 篇，只对刚发布的有效）；聚类召回（多模态向量 k-means 成 1000 个 cluster，cluster → 物品列表按时间倒排）；Look-Alike（把有交互用户的向量平均作为新物品表征，近线分钟级更新）。流量调控：自然分发下 24 小时新内容曝光占比约 1/30，演进路径为强插 → 粗排 / 重排提权 → 保量（如 24 小时 100 次曝光，按已发布时长与已获曝光比例动态算提权系数）→ 差异化保量（基础 100，内容质量与作者质量各最多 +200，即 100～500）。提权过猛会把内容推给不合适的人反而压低其长期表现；线上环境（新召回通道、新模型、新打散规则）一变，提权系数就要重调。评估：作者侧（发布渗透率 = 当日发布人数 / DAU、人均发布量）、用户侧（新内容 CTR 按高曝光 >1000 与低曝光分开看，大盘时长 / DAU 不显著受损）、内容侧（高热占比：30 天内 1000+ 点击）。用户侧 A/B 因保量总额固定会高估负向 diff，推全后会缩小。

## 六、搜索系统设计：模块划分、索引、多路召回与排序（ai_interview_note · search，7 题）

> 笔记作者从 RAG 的视角重讲传统搜索：拿腾讯（客户端 / AS / BS / Query 理解 / 召回组件 / 排序 / 离线 七模块）、淘宝向量检索、闲鱼、QAnything 等案例归纳出「离线内容理解 → Query 理解 → 检索召回 → 排序」四大块，并给出 0-1、中期、后期的演进建议；精排部分引用美团、知乎的公开分享。这里按系统设计面试改写，不涉及模型公式。

36. 🟡 一个成熟的搜索系统一般拆成哪几大模块？以腾讯搜索的七模块为例，说出 AS 和 BS 的分工，以及离线模块为什么要单独成块。
   - 要点：通用的四块是离线（物料与用户画像的内容理解、入库建索引）、Query 理解、检索召回、排序。腾讯案例：客户端（结果页、直达、联想词、相关搜索）、AS（高级检索，对外暴露搜索能力、编排下游）、Query 理解、BS（基础检索：字面、Tag、语义向量召回）、召回组件（真正加速检索的搜索引擎）、排序（在线 LTR）、离线（文档、推搜日志处理）。闲鱼案例额外点出容灾、运营投放平台、「中控台」（舆情、debug、评测、请求回放）。运维追问：AS 作为编排层要对每路 BS 设超时与降级，请求回放平台是排序变更前做回归的关键基础设施。
37. ☆ 🟡 从零搭一个站内搜索，第一版你选 Elasticsearch BM25 还是通用向量模型 + Milvus / FAISS？中期、后期再加什么？
   - 要点：作者建议第一版优先字面检索（ES 自带 BM25 排序后截断）：泛化差但准确率可控、好排查；向量召回泛化强，但对 query 与 doc 不对称（类似问答匹配）的场景不突出、细节不稳定。第一版的时间主要花在基础结构、中间件和发布风险上，算法不宜复杂。中期：围绕 bad case 逐步建 Query 理解，补多路召回并借机规划精排。后期：场景特有问题凸显，转向研究型优化。面试关键是「架构服从项目阶段」，不要一上来画终局图。
38. 🔴 离线入库阶段，数据量从「千条」到「几十万」到「更多」各该用什么方案？标签抽取和向量化各适合什么内容？
   - 要点：千条以下逐条匹配即可，无需专门数据库；几十万以内内存放得下，可单机自建倒排或用 FAISS / hnswlib / annoy / ngt；再大或内存吃紧就上分布式中间件（ElasticSearch、Milvus，也可了解 Postgres / Redis / MySQL）以及 Hadoop / HDFS / Hive / Spark 做离线批处理。标签抽取（如音乐场景的歌手、歌名、专辑、作词作曲）准确、可解释、可控，但定制化、离线工作量大；向量化通用，但对数字、型号这类「差一字差很远」的实体（如氯化钠 / 氯化钾）不敏感，长文本会稀释关键信息——应切片缩短、补同义说法、能结构化就别急着拼成纯文本。入库字段会被算法频繁改动，索引 schema 与回灌流程要能重复执行。
39. 🟡 「语文考 90 分左右的同学」「故宫附近的美食」「雪花牛肉」三个 query 分别暴露了只用向量检索的什么问题？该用什么索引或 Query 理解手段？
   - 要点：数字检索要用数值索引（范围查询），向量对数字不敏感；地理查询要用 GeoHash 等地理哈希索引按位置检索；「雪花牛肉」误召回「雪花啤酒、红烧牛肉」要靠 Term 分析里的紧密度配合字面相似度。Query 理解的基础工作还包括预处理（大小写、全半角、繁简、长度截断）、分词、改写（纠错、同义词如 KFC → 肯德基）、词权重、意图识别、敏感 / 时效识别与人工干预；ES 基本能覆盖这些索引类型，只做向量召回时 FAISS 更轻。倒排查到 ID 后再到正排（ID → 文档详情）取展示字段，索引里不放与检索无关的内容。
40. 🔴 意图识别在生产上常遇到哪些问题？类目频繁变化、上千个类目、垃圾 query 各怎么处理？
   - 要点：可选方案有词典 / 规则 / 正则、分类模型（TextCNN、BERT）、「以搜代分」（用检索近邻样本的类别代替分类器）、大模型 prompt / in-context。难点：类目体系高频变化时，大一统分类模型每次都要重训，以搜代分或词典更易增量；成百上千类且样本不均；必须预留 other 兜底类，否则无意义 / 超纲 query 会被强行分进某类；手机端短句缺上下文、长句信息多易干扰。实体抽取配合字面检索能解决向量召回搞不定的数字、型号场景，大模型显著改善了归一化和不连续实体。
41. ☆ 🔴 多路召回该怎么分路？各路结果怎么并发、合并？召回、粗排和精排的目标有什么本质区别？
   - 要点：分路依据：按意图 / 路由（查音乐走音乐库、查天气走天气接口）、按内容结构（同一说法可能指不同业务的数据）、按检索方式（字面一路、向量一路）、按表征方式（不同训练目标的多种向量）；各路通常服务化后并发请求，互不依赖。粗排绑定检索逻辑，目标是干掉「肯定不合适」的（cos / L2、数值误差、直线或导航距离）；召回是「大海捞针」面对全库，精排是「百里挑一」面对少量候选并要综合相关性、物料质量、用户偏好。QAnything 用两阶段（embedding 检索 + rerank）的理由：知识库越大，单阶段 embedding 检索越容易退化。
42. 🔴 精排特征从哪几个维度来？位置偏差怎么处理？重排阶段还要做什么？大模型适合直接当精排吗？
   - 要点：特征分 Query 侧（意图、实体、关键词）、用户侧（偏好，推理时只读）、Doc 侧（质量、点击率、停留时长等）与交互特征（语义 / 字面相似度、统计量）；融合方式从规则加分 → GBDT / XGBoost → 深度模型演进（知乎：GBDT → TF-Ranking 多目标；美团：多业务配额模型 MQM、多业务精排 MBN 用 PLE 的 CGC 层、Transformer 建模行为序列）。位置偏差：硬编码 / 自学习位置权重收益不高，更好的是独立的浅层 position tower。重排：listwise 全局排序、流量调控（热门 / 新品前移）、窗口内打散；推荐侧的打散可用带滑动窗口的 MMR（窗口如最近 10 个）叠加硬规则（如最多连续 5 篇同类型、每 9 篇最多 1 篇运营内容、首屏前 4 篇最多 1 张电商卡），规则优先于多样性算法。大模型精排：早期特征少时可临时顶上，后期稀疏特征难以塞进 prompt、对输入顺序敏感、上限打不过成熟精排，成本与迭代速度也不划算。

## 七、对话系统与 RAG 系统设计：理解、对话管理、检索式 vs 生成式与评估（ai_interview_note · dialogue + rag，7 题）

> 对话系统部分以平安智能问答、微软小冰、美团智能问答为案例，归纳出 Query 理解 → 对话管理（DST + DP）→ 结果生成（多路召回 + 排序）的流程；RAG 部分是对综述论文 arXiv:2312.10997（Gao et al., 2023）的解读：Naive / Advanced / Modular 三阶段、检索优化、生成侧后处理与 RAGAS / ARES 评估。对话系统笔记写于大模型普及前后，部分生成式的局限（万能回复、一致性差）在 LLM 时代表现形式已变，但「可控性靠检索兜底」的结论仍成立。

43. 🟡 对话系统的在线流程分哪三段？它和搜索系统在「排序」这一步有什么根本区别？
   - 要点：Query 理解（意图、实体 / 槽位、语义表征，以及拒识、澄清）→ 对话管理（维护历史与画像、决定当前策略）→ 结果生成（文本 q-q / q-a 召回、向量召回、知识图谱推理、受控生成，多路召回后排序）。与搜索的区别：对话通常只返回一个答案且要求精准，多意图时只能澄清或「我猜你想问」；几乎没有点击这类反馈数据（客服场景的「满足 / 不满足」占比很小），所以排序初期多靠策略与规则综合，规则复杂到难维护后再转机器学习。早期单路检索式问答甚至不必拆召回与排序、可以不做意图识别。
44. 🔴 对话场景的 Query 理解比搜索多了哪些任务？时效性、口语化和短句问题分别怎么处理？
   - 要点：美团问答拆为领域意图识别、领域路由与意图澄清、实体识别与链接、时效识别（活动已结束要拒答）、实体澄清（「苹果」）、句式识别、槽位填充；做什么要由下游（检索式需要哪些字段、生成式需要哪些信息）倒推。时效：新品 / 热词靠可热更新的词典，而不是等模型重训；口语化：定向补样本收益最大，模型侧用对抗训练、R-Drop 增强鲁棒性；短句：区分有意义（「维修」）与无意义（「请问」），无意义的由意图模型负类 + 黑名单拦下，没见过的短句应拒识。运维点：词典与黑名单是线上配置，要有版本、灰度和回滚。
45. ☆ 🔴 任务型多轮对话（如订机票）的对话管理怎么拆？DST 和 DP 各存什么、做什么？端到端方案的取舍是什么？
   - 要点：识别订票意图后进入多轮，列出必填槽位（出发地、目的地、时间等）；Query 理解持续抽槽，DST 记录已填槽位（最简单就是按会话缓存一个槽位结构），DP 根据缺失信息选择追问、确认、完成或处理打断，复杂后演进为树 / 有限状态机，再到分类或强化学习选策略。状态数随意图与槽值组合指数增长，需要合理的状态表示。拆分式好理解、可扩展、可控但泛化差；端到端泛化强、比赛榜单更稳但可控性差。工程点：会话状态必须有 TTL 与持久化（服务重启 / 漂移到另一副本不能丢上下文），还要处理话题转移、主动对话与人设一致性（前后回答自相矛盾就是没维护机器人侧状态）。
46. 🟡 检索式和生成式回复各有什么上限与下限？新建一个客服机器人，你怎么排先后？
   - 要点：检索式答案来自人工维护 / 开源 / 从历史人工对话挖掘的知识库，只要理解与匹配不出错，下限高且可控、可加黑白名单；生成式泛化强、句式灵活，但存在可控性不足（敏感内容）、把天聊死、万能回复（「不知道」）、换个问法答案不一致、知识缺失等问题。作者的顺序：先检索式保证可控，黑白名单必备；后期处理长尾和闲聊时再引入生成式，并用统一知识库做条件约束（这就是 RAG 的思路），敏感 query 在上游过滤、生成结果在下游再审。
47. ☆ 🟡 Naive RAG、Advanced RAG、Modular RAG 有什么区别？Naive RAG 的三类典型故障是什么？
   - 要点：Naive 只有离线索引（解析、分块、嵌入、入库）、在线检索、生成三步；故障分三类：检索质量（分块丢内容、覆盖不全、向量不准）、回复质量（幻觉、拒答、答非所问）、增强过程（检索噪声误导模型、冗余重复）。Advanced 在检索前优化索引（提升数据粒度 / 清洗、调块大小与索引结构、加元数据如修改时间、用 LLM 为文档块生成问题做对齐、混合检索），并对向量模型微调；检索后做重排与 prompt 压缩。Modular 把能力拆成可替换模块：搜索、记忆、额外生成、任务适配、对齐、验证（判断检索结果能否回答问题），并可调整模块间协同（如 Self-RAG 主动判断是否检索）。
48. ☆ 🔴 RAG 的检索侧，query 与文档语义空间不对齐时有哪些手段？递归检索、HyDE、LostInTheMiddleRanker 各解决什么？
   - 要点：Query 侧改写 / 子查询（借搜索里的 must / should / filter 检索语法约束）；Doc 侧抽特征、挖掘问题；模型侧做领域自适应预训练（DAPT）或任务自适应（TAPT），如从 q-q 匹配转为 q-a 匹配必须微调。递归检索：用小片段算相似度、把对应的大片段交给模型（索引单元与返回单元分离）；HyDE：先让模型生成一个可能错误的假答案，用它的 embedding 去检索，因为关键词通常相近；LostInTheMiddleRanker：把最相关的文档交替放到上下文开头和结尾，避开中段被忽略；Diversity Ranker 按多样性重排。检索对了模型仍答错时，可用 LLM 反馈训练检索器，或用 adapter 抽取关键信息。运维视角：每加一个 LLM 调用（改写、HyDE、验证）都增加延迟与成本，要按链路预算取舍。
49. 🔴 RAG 上线后怎么评估？RAG 与微调怎么选？各自在延迟、更新与权限上的运维代价是什么？
   - 要点：评估分独立评估（检索：命中率、MRR、NDCG；生成：ROUGE 等）与端到端评估（有标注 / 无标注）；三个核心质量指标是答案忠实度（与上下文一致且符合事实）、答案相关性（不答非所问）、上下文相关性；四项能力是抗噪声、拒答无效问题、信息综合、反事实鲁棒性；自动化框架 RAGAS（用 LLM 拆解答案评估）与 ARES（少量标注 + LLM 判别）。选型：RAG 更新知识只需改库、无需训练、可溯源、能按知识库权限做安全控制，但多一跳检索、延迟更高，且要维护外部数据源与索引；微调适合定制风格 / 术语、推理无检索延迟，但知识更新要重训、可解释性差。生产上常两者协同；评测集要随知识库一起版本化，否则无法判断回归来自索引变更还是模型变更。

## 八、Meta PE 系统设计：从教学代码到生产级监控系统（meta-pe-interview-guide，9 题）

> 资料是用户自有的 Meta Production Engineer 备考仓库，`src/monitoring/` 用纯 Python 写了指标类型（metrics.py）、push / pull 采集（collector.py）、内存时序库（storage.py）和告警状态机（alerting.py），并有 pytest 覆盖。它是**刻意简化的教学版**——面试官最爱问的恰恰是「这段代码放到 10 万台主机上哪里会先坏、Prometheus / Gorilla / Alertmanager 是怎么解决的」。要点里的类名、默认值均以仓库代码为准；生产系统的行为以各项目官方文档为准。

50. ☆ 🟡 仓库里的 `Counter` / `Gauge` / `Histogram` 是怎么存值的？`Histogram.get_percentile` 返回的是什么精度的结果，`Histogram` 注册进 `MetricsRegistry` 后调用 `export_prometheus()` 会发生什么？
   - 要点：三者都用 `Dict[tuple, float]` 存值，key 是 `tuple(sorted(labels.items()))`，每个实例一把 `threading.Lock`；`Counter.inc` 传负数直接 `ValueError`（单调递增，进程重启归零靠查询端 `rate()` 处理 reset）。`Histogram` 默认桶 `(0.005 … 10.0)` 共 11 个，`observe` 时把**所有 ≥ 值的桶都 +1**（累积桶，同 Prometheus `le` 语义），但**没有 `+Inf` 桶**；`get_percentile` 返回**第一个累积计数 ≥ 目标的桶上界**，不做桶内线性插值（测试里 100 个 0.05 的 p50 断言为 0.1），超出最大桶的值（如 20s）只会报成 10.0。另外 `Histogram` **没有实现 `collect()`**，注册后 `export_prometheus()` 抛 `AttributeError`——测试只测了 Counter/Gauge 导出所以没发现。追问：Prometheus 的 `histogram_quantile()` 在桶内线性插值、必须有 `+Inf`；Summary 在客户端算分位数，**跨实例不可聚合**，Histogram 可以 `sum by (le)` 后再算。
51. 🔴 这套代码里「基数爆炸」会从哪里冒出来？你会在哪一层加什么护栏？
   - 要点：每个不同的 labels 字典都会在 `_values` / `_data[name][label_key]` 里新建一条序列，`Metric.__post_init__` 只校验指标名是否 snake_case，**对 label 的取值个数毫无限制**；`export_prometheus` 也不转义 label 值。一旦有人把 `user_id`、`pid`、请求 URL 当 label，内存线性膨胀，`InMemoryTimeSeriesDB.get_stats()` 的 `series_count` 会先暴涨。护栏分层加：客户端（每指标 label 组合上限、超限折叠成 `other`）→ 采集端（Prometheus 的 `sample_limit` / `label_limit` / `metric_relabel_configs` drop）→ 存储端（多租户 TSDB 的每租户活跃序列上限）→ 治理（新指标评审、按 `count by (__name__)` 排 Top 序列）。规模换算：10 万主机 × 每台 1000 条序列 = 1 亿活跃序列，单个高基数 label 再 ×100 就是 100 亿，直接决定架构能否成立。
52. ☆ 🟡 读 `PullCollector`：`ThreadPoolExecutor(max_workers=10)`、`future.result(timeout=5.0)`、`scrape_interval=15.0`。把它直接用于 10 万个 target，会出现哪些问题？`up == 0` 告警为什么在这套实现里永远不会触发？
   - 要点：① 吞吐：若目标都卡满 5s 超时，10 个线程每秒只能处理约 2 个 target，10 万个 target 一轮要十几个小时，远超 15s 间隔；要撑住 10 万/15s ≈ 6.7k scrape/s，按 100ms 一次也需要约 670 并发，必须**水平分片**（Prometheus `hashmod` 分片、按机房分层）。② 计时：`scrape_loop` 是「采完再 `sleep(15)`」，实际间隔 = 采集耗时 + 15s，会漂移，且没有 jitter，所有 target 同一时刻被打。③ `result(timeout)` 从调用 `result()` 才开始计时，排在后面的 future 实际可能等远超 5s。④ 采集失败只 `print("Scrape failed")`，**不写 `up=0`**；而存储的 `query_latest` 又没有过期判断，主机死后最后一个 `up=1` 永远是「最新值」——这就是「缺失即健康」的经典坑。Prometheus 的做法：每次抓取都合成 `up` 与 `scrape_duration_seconds`，target 消失时写 staleness marker，查询有 5 分钟 lookback。
53. 🔴 `PushCollector` 有 `push()` / `collect()` / `aggregate()`，聚合输出 count/sum/min/max/avg。指出它在生产里的三个缺陷，并说明什么场景必须用 push。
   - 要点：① `_buffer` 是无界 list，没有背压 / 丢弃策略，客户端一拥而上会把采集端打爆（`get_monitoring_system_design` 自己也写了 push 的缺点是 "Can overwhelm monitoring"）；② `aggregate()` **不区分指标类型**，对累积型 Counter 求 sum/avg 毫无意义——StatsD 的做法是客户端发**增量**，服务端按 counter 求和、gauge 取最后值、timer 算分位数，每 `aggregation_interval`（这里 10s）flush；③ 推送端身份不可信，无法区分「没数据」和「挂了」，需要心跳或期望列表。必须 push 的场景：短命批任务（Pushgateway，但它不会自动过期序列）、防火墙 / NAT 后的边缘设备、事件型指标、或者大规模下 agent 统一 `remote_write`（Prometheus Agent mode / OTel Collector）把 pull 降到本机、跨网络改成 push。
54. ☆ 🟡 `InMemoryTimeSeriesDB` 的数据结构与写读路径是什么？在 1 亿序列、每 15 秒一个点的负载下，哪几处会最先成为瓶颈？
   - 要点：结构是 `Dict[name, Dict[label_key, TimeSeries]]`，`TimeSeries.points` 是按时间排序的 Python list。写：`add_point` **每次都重建一份完整的 timestamps 列表**再 `bisect_right` 并 `list.insert`，单点写入 O(n)；读：`query_range` 从头线性扫描到 `end`，没有用二分定位起点；全库一把 `RLock`，读写互斥；`cleanup_old_data` 全量重建每条序列的列表；纯内存、无 WAL，进程重启全丢；默认 `retention_seconds=86400`。规模：1 亿序列 ÷ 15s ≈ 670 万点/秒写入。生产 TSDB（Prometheus）的对应设计：内存 head block + **WAL** 保证崩溃恢复；约 2 小时切一个不可变 block，后台 compaction 合并；chunk 追加写、按 series 分片锁；**倒排索引（postings）**按 label 定位序列；默认拒绝乱序样本（新版本可配 `out_of_order_time_window`）。
55. 🔴 storage.py 的注释写着「Could use delta encoding for timestamps / Gorilla encoding for values」，`get_tsdb_design_guide` 把 Facebook 的 Gorilla/Beringei 列为参考。讲清 Gorilla 压缩原理，并用它估算内存。
   - 要点：时间戳用 **delta-of-delta**：采集间隔固定时二阶差分几乎都是 0，只需 1 bit；值用与前一个值 **XOR**，相同值 1 bit，否则只存有效位的前导零 / 长度 + 中间有效位。论文报告平均约 **1.37 字节/点**（原始 8B 时间戳 + 8B double = 16B，约 12 倍压缩），Gorilla 在内存里保留 **26 小时**热数据，更老的数据落 HBase。估算：15s 间隔 26h ≈ 6240 点 × 1.37B ≈ 8.5KB/序列，1 亿序列 ≈ 850GB 内存，所以必须按序列哈希分片到几十上百台机器并跨区域双写。延伸：Prometheus chunk 编码也是 delta-of-delta + XOR 思路；M3 的 M3TSZ 是在其上的变种；**乱序写会破坏差分编码**，这也是为什么 TSDB 通常要求时间有序追加。
56. 🟡 `aggregate(name, labels, start, end, step, agg_func)` 用 `(ts // step) * step` 分桶并支持 avg/sum/min/max/count；设计指南给出「原始 2 周 / 5 分钟 30 天 / 1 小时 1 年 / 1 天永久」的降采样阶梯。照此实现降采样有什么陷阱？
   - 要点：① **avg 的 avg 不等于 avg**：rollup 层应保存 sum 和 count（以及 min/max）而不是只存平均值，上层再合并；② **分位数不能降采样**：p99 的平均没有意义，要么保留 histogram 各桶计数再算，要么用可合并的 sketch（t-digest / DDSketch）；③ Counter 降采样要保留**桶末值**或先转 rate，否则 reset 被平均掉；④ 查询时要按时间跨度自动选分辨率，并对齐 step，否则图表在分辨率切换处出现台阶。注意仓库自身的 `InMemoryTimeSeriesDB` 默认只保留 24 小时，指南里的阶梯并未实现——Thanos / M3 / Mimir 才把多分辨率做成独立的 compactor 后台任务（Thanos 保存 count/sum/min/max/counter 五个聚合）。
57. ☆ 🟡 走一遍 `AlertManager.evaluate_rule` 的状态机：INACTIVE → PENDING → FIRING → RESOLVED 分别由什么触发？这套实现为什么只能对「单条无 label 的序列」告警，又会怎样抖动（flapping）？
   - 要点：条件满足时在 `_pending_since[rule.name]` 记下首次时间，持续 ≥ `for_duration` 才变 FIRING 并记入 `_alerts`，否则返回 PENDING；条件一旦不满足立即 pop `_pending_since`，若之前在 `_alerts` 里就返回 RESOLVED。限制：`query_latest(metric_name, {})` 写死空 label，**一个 rule 只对应一个告警实例**（按 rule.name 作 key），无法「每台主机一条」；表达式只是 `metric op threshold` 的正则解析。抖动：值在阈值附近来回跳时，**一次低于阈值就清零 for 计时**，FIRING 后一次回落就 RESOLVED、下一轮再 FIRING。生产做法：Prometheus 规则对表达式结果**每个 label 集合**各自维护状态并写出 `ALERTS` 序列；用 `for` 抑制瞬时尖峰、`keep_firing_for` 防止过早恢复；阈值留滞回区间或用 `avg_over_time` 平滑；另外配一条永远 firing 的 Watchdog（dead man's switch）由外部系统检测「告警链路本身是否活着」。
58. 🔴 `evaluate_all_rules` 会在每轮评估中对所有 FIRING 和 RESOLVED 告警同步调用通知 handler。在 15 秒评估间隔、一次机房网络故障导致 5000 台主机同时告警的场景下会怎样？Alertmanager 是怎么解决的？
   - 要点：问题：① **没有去重 / 重复间隔**——只要还在 FIRING，每 15 秒重发一次，等于每小时 240 次呼叫；② handler 在 `self._lock` 内同步执行，一个慢的 webhook 会拖住整轮评估；失败只 `print`，没有重试与持久化；③ 5000 条告警逐条发出，形成告警风暴、根因淹没。Alertmanager 的对应机制：按 `group_by`（如 alertname + 机房）**分组**合并成一条通知，`group_wait`（默认 30s）攒批、`group_interval`（默认 5m）发增量、`repeat_interval`（默认 4h）控制重复；**inhibit_rules** 用「机房网络不可达」抑制其下所有主机级告警；**silence** 处理已知维护；路由树按 team / severity 分发；多副本通过 gossip 去重保证 HA。再结合仓库 `get_alerting_design_guide` 的原则：对症状告警而非原因、每条告警可操作并带 runbook 链接、只有需要立即处理的才呼叫。监控系统自身要被**带外**的另一套监控盯住（meta-monitoring）。

## 九、Meta PE「设计 + 排障」：把单机排障知识放大到全量主机（meta-pe-interview-guide，5 题）

> 同一仓库的 `src/linux/`（进程状态、`/proc` 内存、文件系统排障）与 `src/networking/`（`NetworkTroubleshooter`、DHCP / DNS 指南、八步排障法）是单机视角的知识点。Meta PE 面试常把它们改造成「全量主机规模的设计题」：怎么检测、爆炸半径多大、怎么做成工具。注意 README 列出的 `src/troubleshooting/` 目录在仓库里并不存在，排障方法论实际在 `networking/troubleshooting.py` 的 `get_networking_guide()` 里。

59. ☆ 🟡 设计一个检测全量主机上「僵尸进程堆积」和「进程内存泄漏」的系统：主机上采什么、上报什么、怎么告警、怎么处置？
    - 要点：采集：遍历 `/proc/[pid]/status`（或 stat）统计各状态（仓库 `ProcessState` 枚举 R/S/D/Z/T/t/X），对 Z 状态**按父进程名 + ppid 聚合计数**再上报，不要把 pid 当 label（基数爆炸）；泄漏看 `/proc/[pid]/statm` 的 RSS（仓库 `MemoryMonitor.get_process_memory` 按页大小换算），按服务聚合后看**斜率**而不是绝对值。告警：僵尸数持续增长（如 `deriv` > 0 持续 30 分钟）或接近 `pid_max`；RSS 线性上涨且与流量无关。处置：僵尸本身不占 CPU / 内存，只占进程表项，`kill -9` 杀不掉（已经死了）——要么修父进程的 `wait()` / SIGCHLD 处理，要么重启父进程让 init / subreaper 收养后回收；容器里 PID 1 不回收子进程是常见根因（用 tini / `--init`）。全量规模下先看「同一父进程名在多少台机器上出现」来区分代码 bug 与单机异常。
60. 🔴 一个数据中心的 DNS 递归解析器集群故障，爆炸半径怎么评估？用仓库的 `NetworkTroubleshooter.check_dns` 做全量探测够吗，该怎么设计？
    - 要点：爆炸半径取决于缓存层级：应用内缓存 / nscd / 本地 stub → 递归解析器缓存 → 权威。TTL 内的热门名字还能解析，冷门名字与短 TTL 名字先失败，所以故障是**逐渐扩大**而非瞬间全挂；负缓存（NXDOMAIN）会把短暂故障延长。`check_dns` 用的是 `socket.gethostbyname_ex`，走系统解析库（nsswitch、`/etc/hosts`、本地缓存），**测的是「这台机器能不能解析」，不是「某台解析器健不健康」**，也区分不了 NXDOMAIN / SERVFAIL / 超时。全量设计：每台主机对**每个配置的解析器**直接发查询（`dig @resolver`），按返回码与延迟打点，label 只用解析器 / 机房 / 机架；中心侧按「多少比例主机对同一解析器失败」判断是解析器故障还是主机侧故障；结合仓库 `dns_issues`（servfail = 权威侧问题，refused = 访问控制）分流。缓解：多解析器 + 合理超时 / 重试、本地缓存 serve-stale、关键依赖不在请求路径上实时解析。
61. 🔴 DHCP 服务器（或 relay）在一个集群里宕机，什么时候会被发现？受影响的是哪些主机？如何设计监控和租期？
    - 要点：按仓库 `get_dhcp_guide`：DORA 四步、服务端 UDP 67 / 客户端 UDP 68；租期到 **T1（50%）** 单播向原服务器续租，**T2（87.5%）** 广播向任意服务器续租，到期必须释放 IP 重走 DORA。所以已在线主机**不会立刻受影响**，故障是「定时炸弹」：先挂的是**新装机 / 重启 / PXE 引导**的主机，然后在租期到期时陆续掉线，表现为「过了几小时开始成片失联」。监控：DHCP 服务端的 DISCOVER/ACK 比、NAK 数、地址池使用率；全量视角统计「距租约到期的最短剩余时间」；relay 跨子网转发的健康。设计：服务端多活（仓库提到 Facebook 的 **dhcplb** 在数据中心做 DHCP 负载均衡）、租期长短的取舍（长租期扩大容错窗口但回收地址慢），服务器机房常用静态 / 长租期降低对 DHCP 的运行时依赖。
62. ☆ 🟡 把仓库 `get_networking_guide()` 的「八步排障法」做成一个可在全量主机上运行的诊断工具：你会怎么设计输出、步骤和安全边界？
    - 要点：八步：确认问题 → 本地服务是否在跑 / 监听 → DNS → 连通性（ping / traceroute / mtr）→ 端口 → 防火墙 → 应用日志 → 抓包。现有 `run_diagnostics` 只做了 DNS + 端口两步，结果是 `DiagnosticResult(test_name, success, message, details, duration_ms)`，`get_summary` 给出通过率与失败列表——这个**结构化结果**是对的方向。改进：① 按错误类型分流——`connect_ex` 返回码区分 refused（RST，没进程监听）/ timeout（防火墙或主机不通）/ no route（路由），对应仓库 `common_issues`；② 步骤有依赖：DNS 失败就不必做端口检查，但要标记「跳过」而不是「通过」；③ 全量下发时限并发、限速，避免诊断工具自己压垮目标；④ 只读、可审计，抓包类步骤要有 `-c` 包数 / 时长上限；⑤ 结果按机房 / 机架聚合，靠「有多少台主机、在哪一步失败」定位故障层级。
63. 🟡 全量主机的磁盘问题怎么监控：仓库 `SystemMetricsCollector.collect_disk` 只上报 `f_blocks` 和 `f_bfree` 两个值，会漏掉哪些故障？
    - 要点：① `f_bfree` 包含 root 保留块，普通用户实际可用的是 `f_bavail`（node_exporter 分别给出 `node_filesystem_free_bytes` 与 `node_filesystem_avail_bytes`），按 free 告警会晚报约 5%；② **不采 inode**（`f_files` / `f_ffree`），而仓库 `filesystem.get_troubleshooting_guide` 自己就写了「有空间但建不了文件 → `df -i`，小文件过多」；③ 不检测**只读重挂载**（文件系统报错后内核把它改成 ro，需 `mount | grep ' ro,'` / `dmesg`）；④ 同理 `collect_memory` 用的是 `MemFree` 而非 `MemAvailable`，会把 page cache 误判成内存不足。告警设计：用趋势预测「几小时后写满」（`predict_linear`）代替固定阈值，按挂载点区分系统盘与数据盘，只读挂载与 inode 用尽单独告警且直接呼叫；全量规模下自动清理（日志轮转、`find /tmp -mtime +7 -delete`）先于人工介入。
