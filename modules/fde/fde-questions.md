# 前沿部署工程师 / Forward Deployed Engineer（FDE）面试题（30 题）

> 遵循 [../../docs/STANDARD.md](../../docs/STANDARD.md) 模板。难度：🟢 初级 · 🟡 中级 · 🔴 高级。
> 素材提炼自 [pierpaolo28/Awesome-FDE-Roadmap](https://github.com/pierpaolo28/Awesome-FDE-Roadmap)（MIT，Pier Paolo Ippolito & Paolo Perrone）
> 以及其引用的一手资料（Palantir「Dev vs Delta」、Google Cloud 架构框架、DoD Platform One、NIST SP 800-171 等）。本模块为**提炼与转述**，不照搬原文；来源见文末。
>
> FDE（Palantir 叫 Delta，OpenAI / Scale AI / Anthropic / Google 都有同类岗位）是「总部完美代码」与「客户混乱现实」之间的桥：
> 一半时间写集成 / 胶水代码，一半时间做技术策略与干系人管理，目标是**尽快交付价值，然后让自己在客户现场变得多余**。
> 面试因此不是纯算法或纯架构，而是**案例（case）**：给你一个客户场景，看你怎么澄清、架构、找到「Delta」、证明价值、搞定人。

---

## FDE 面试怎么进行（面试官执行手册）

1. **形式**：以案例为主。给一个客户场景（行业 / 数据现状 / 安全约束 / 政治环境 / 时限），要求候选人给出「前 30 天计划」或「架构 + 落地路径」。技术追问穿插其中。
2. **推进顺序用 C.A.S.E.**：Clarify（澄清数据量 / 分类 / 完成定义）→ Architect（从源系统到终端用户的数据流）→ Solve the Delta（产品开箱不能做的那部分怎么用胶水补）→ Evaluate（怎么证明 AI 没有幻觉、怎么监控、怎么交接 Day 2）。
3. **每个阶段只推进一步**，候选人卡壳给 `hint`；每一步都追问「谁是 Champion / 谁会挡你 / 数据在哪 / 不做会怎样」。
4. **级别映射**：🟢 初级 → 概念与工具题（Q1–Q3、Q6、Q9）；🟡 中级 → 单项技术方案（数据 / 云 / RAG / 评测）；🔴 高级 → 完整案例 + 隔离网络 + 干系人。
5. 与 `system-design` 模块互补：那里考「系统怎么设计」，这里考「在别人的环境里、带着政治与合规约束，怎么把系统落地并交出去」。

## FDE 评分维度（每题 1–10 分按此打）

| 维度 | 权重 | 看什么 |
|---|---|---|
| 澄清与诊断（Clarify） | 20% | 先问数据 / 分类 / 完成定义 / 系统记录源，而不是先写代码；识别红旗 |
| 架构与落地（Architect） | 25% | 从客户现有系统到价值交付的可行数据流；用最小可行架构，而非镀金 |
| Delta 与胶水（Solve） | 20% | 准确指出产品与需求的缺口，给出可维护的集成方案 |
| 评测与 Day 2（Evaluate） | 15% | 有可测的成功定义（命中率 / 幻觉率 / 延迟）、监控与交接计划 |
| 干系人与沟通（Soft stack） | 20% | BLUF、Champion / Blocker 识别、处理敌意、SOW 边界、每周价值叙事 |

9–10：五维全到位并有现场细节 · 7–8：技术扎实但人 / 合规面浅 · 5–6：只会写脚本 · 3–4：无澄清、镀金架构 · 1–2：无法给出计划。

## 一、角色认知与工作方式

### Q1. FDE 和普通软件工程师（SWE）的区别是什么？Palantir 的「Dev vs Delta」讲了什么？

- **难度**：🟢 初级
- **关键词**：FDE, Delta, 嵌入式工程 embedded engineering, 产品化咨询 productized consulting, 最后一公里集成 last-mile integration
- **概念速记**：
  - **Delta**：Palantir 对 FDE 的称呼，指「产品开箱即用的能力」与「客户任务真正需要的能力」之间的**差距**，FDE 的工作就是填这个差。
  - **嵌入式工程**：FDE 不是「给建议」的顾问，而是拿客户凭证、坐客户 Slack、直接往客户生产环境交付代码的人。
  - **产品化咨询**：为单个客户写的解法，最终要能抽象回核心产品。
- **问题**：用一张对比表说明 SWE 与 FDE 在用户、环境、目标、代码比例上的区别；为什么说 FDE 是「为任务（mission）而不是为用户画像（persona）构建」？
- **参考答案**：
  1. **用户**：SWE 面对百万匿名用户；FDE 面对少数高风险干系人（CTO、将军、CEO），每个人的意见都能决定项目生死。
  2. **环境**：SWE 在受控统一的云；FDE 在敌意 / 遗留 / 隔离网络 / 混合基础设施里，「标准软件遇到真实数据（损坏的 schema、air-gap、政治阻力）就会失败」是常态。
  3. **目标**：SWE 追求规模与稳定；FDE 追求**价值交付速度**与解决问题。
  4. **代码比例**：SWE 约 90% 功能代码；FDE 约 50% 集成 / 胶水代码 + 50% 策略与沟通。
  5. **为任务构建**：成功不是「功能上线」，而是客户的任务指标动了（少一次再入院、快 40% 的查询、少一个人的手工）；因此 FDE 要定义成功指标、找到系统记录源、设计 Day 2 交接，而不只是把 PR 合了。
  6. **终极目标**：让自己在客户现场变得多余——系统好到能自运行、客户团队能接管。
- **易错点 / 面试官关注**：
  - 把 FDE 理解成「现场支持工程师」或「售前」。
  - 只讲技术不讲干系人、合规与交接。
- **延伸**：Q2、Q3、Q26、[Palantir: Dev versus Delta](https://blog.palantir.com/dev-versus-delta-demystifying-engineering-roles-at-palantir-ad44c2a6e87)、[behavior/behavior-questions.md](../behavior/behavior-questions.md)

### Q2. FDE 案例面试的 C.A.S.E. 框架是什么？拿到案例后前 5 分钟你做什么？

- **难度**：🟢 初级
- **关键词**：C.A.S.E., Clarify, Architect, Solve the Delta, Evaluate, 完成定义 definition of done
- **概念速记**：
  - **C.A.S.E.**：Clarify（澄清）→ Architect（架构）→ Solve（找到并填补 Delta）→ Evaluate（评测与监控）。四步都要走完，**不要一上来写代码**。
  - **完成定义（DoD）**：在澄清阶段就把「成功」定义成可测数字，否则项目永远做不完。
- **问题**：面试官给你「某银行想用我们的平台做反洗钱调查助手」，请按 C.A.S.E. 说出你前 5 分钟会问的问题与后续每一步的产出物。
- **参考答案**：
  1. **Clarify**：数据量与形态（多少笔交易 / 天，结构化还是 PDF）；数据分类（PII / PHI / 机密）；系统记录源在哪；成功怎么量化（调查时长下降 X%、命中率 ≥ Y）；谁是 Champion、谁会挡（法务 / IT）；网络与访问（有没有项目权限、是否私有集群）。
  2. **Architect**：画从源系统（核心银行系统 / 数据仓库）→ 摄取 → 存储 / 索引 → 检索 / 模型 → 分析师 UI 的数据流；用最小可行架构，先证明价值再扩。
  3. **Solve the Delta**：产品开箱不支持的部分——比如客户的私有报文格式、遗留 AS400 接口、特定合规脱敏——用胶水服务补，且要能抽象回产品。
  4. **Evaluate**：金标集 + 命中率 / 忠实度 / 延迟目标；上线后监控与漂移；UAT 让真实分析师用；Day 2 谁运维。
  5. **产出物**：现场调研报告（Site Survey）→ 技术范围文档 / PRD（含评测定义与分阶段计划）→ 架构图 → 每周高管摘要。
- **易错点 / 面试官关注**：
  - 直接开始讲「我会用 X 框架」而不问数据与合规。
  - 没有可测的成功定义；没有 Day 2。
- **延伸**：Q3、Q4、Q27、Q28

### Q3. 「三个为什么」诊断法与「前沿部署发现清单」：客户提需求时你先问什么？

- **难度**：🟢 初级
- **关键词**：系统记录源 System of Record, 不作为成本 Cost of Inaction, Day 2, Champion / Blocker, 发现清单 discovery checklist, 影子 IT
- **概念速记**：
  - **三个为什么**：① 系统记录源在哪（如果在某人桌面的 Excel 里，项目已经有风险）；② 不做的代价是什么（决定优先级与预算）；③ Day 2 长什么样（FDE 走后谁维护，没有内部 owner 项目必死）。
  - **影子 IT**：客户员工私建的「野生」数据库 / 工具，常常是最干净、最有用的数据所在。
- **问题**：CEO 说「我要 AI 让我们更高效」。请把它翻译成可执行的技术任务，并列出动手前必须清掉的行政 / 数据 / 基础设施三类检查项。
- **参考答案**：
  1. **连问五个为什么**：效率 → 哪个流程慢 → 分析师每天花 3 小时查历史工单 → 工单在 SQL Server + 邮件附件里 → 需求变成「对工单与附件做检索问答，把查找时间从 3 小时降到 30 分钟」。
  2. **行政 / 政治**：Champion 是谁；最可能挡的部门（IT / 法务）；成功指标是延迟、准确率还是减员。
  3. **数据 / 安全**：分类（PII / PHI / 机密）；流式（Pub/Sub）还是批量；要不要 VPC Service Controls 或 DLP 脱敏。
  4. **基础设施**：有没有项目 Editor / Owner 权限；是否私有集群、要不要 VPN / Interconnect；GPU 配额够不够。
  5. **输出**：把答案写进 Site Survey；找不到系统记录源或没有内部 owner 就是红旗（Q4）。
- **易错点 / 面试官关注**：
  - 接受模糊需求就开工。
  - 忽略「谁在客户侧负责」这个决定生死的问题。
- **延伸**：Q2、Q4、Q27

### Q4. FDE 在发现阶段应立即升级的红旗有哪些？为什么？

- **难度**：🟡 中级
- **关键词**：红旗 red flags, 范围蔓延 scope creep, 数据就绪, 项目经理, 本地部署 on-prem 抗拒
- **概念速记**：
  - **红旗**：早期出现、预示项目会失败的信号；FDE 的价值之一是在第 1 周而不是第 12 周发现它们并升级。
- **问题**：列出至少三个典型红旗，说明每个背后的真实风险与你的应对。
- **参考答案**：
  1. **「数据两周内就绪」**：从来不会。应对：第 1 周就做数据剖析审计，自己去看系统记录源，把「数据就绪」写成 SOW 里客户的可验收交付物。
  2. **「我们这边不需要项目经理」**：项目会失去方向与决策人。应对：要求指定内部 owner / 决策人，写进 SOW；否则升级给高管发起人。
  3. **「能不能先在本地跑」**：通常反映对云 / 平台的深层不信任，后期会卡住迁移与集成。应对：把它当信任问题处理（Q26），用小范围试点证明安全与价值，同时评估隔离网络方案是否真是合规必需（Q19）。
  4. **其他常见**：没有 Champion；数据分类没人能回答；GPU 配额 / 网络权限申请没人推动；成功指标是「让领导满意」。
  5. **升级方式**：BLUF 写进每周高管摘要的「风险与阻塞」，附影响（几天延期）与需要谁做什么。
- **易错点 / 面试官关注**：
  - 把红旗当成「正常的项目困难」默默扛。
  - 升级时只说问题不给动作与影响。
- **延伸**：Q3、Q26、Q28

### Q5. 应对「敌意干系人」：客户首席工程师讨厌你的产品、拒绝给 VPC 访问，怎么办？

- **难度**：🔴 高级
- **关键词**：信任 trust, 威胁感, 1 对 1, 自动化脏活, 可信顾问公式, 升级路径
- **概念速记**：
  - **可信顾问公式**：信任 = （可信度 + 可靠性 + 亲密度）/ 自我导向。FDE 要降低「自我导向」——关注客户的赢，而不是推销自家功能。
- **问题**：这是高频 FDE 面试题。请给出你的处理步骤，并说明什么情况下该升级、怎么升级而不伤关系。
- **参考答案**：
  1. **先定性**：这是信任问题不是技术问题；对方常常担心平台替代自己的工作或暴露现有系统的问题。
  2. **1 对 1**：单独约谈，听而不辩，弄清具体担忧（安全？失控？被评价？）；承认对方对系统的了解是项目最需要的资产。
  3. **给对方赢**：展示平台如何接管 ETL / 运维「脏活」，让对方去做更有价值的事；邀请对方成为架构评审人 / 共同作者；把对方的贡献写进每周高管摘要。
  4. **降低风险的访问方式**：不要求完整 VPC 访问，先申请最小权限（只读、单项目、IAP 访问某个应用），用 Terraform 把要做的事透明化供对方审阅。
  5. **升级**：只有在阻塞影响交付里程碑时，通过 Champion / 高管发起人以「影响 + 需要的决策」的方式升级，且事先告知对方，避免背后捅刀。
  6. **面试加分**：举一个真实例子（STAR），量化最终结果（拿到访问、里程碑按期）。
- **易错点 / 面试官关注**：
  - 直接升级或硬怼。
  - 只讲「沟通」没有具体动作（最小权限、共同署名、透明化）。
- **延伸**：Q4、Q26、Q28、[behavior/behavior-questions.md](../behavior/behavior-questions.md)

## 二、数据工程（Phase 1：地基）

### Q6. 什么是 Medallion 架构？Star Schema 和 One Big Table 怎么选？

- **难度**：🟢 初级
- **关键词**：Medallion 架构, Bronze / Silver / Gold, 星型模型 star schema, 大宽表 OBT, 数据建模
- **概念速记**：
  - **Medallion**：Bronze（原始落地区，不可变）→ Silver（清洗、关联后的单一事实来源）→ Gold（业务就绪的聚合，供 UI / AI 直接用）。
  - **星型模型**：事实表 + 维度表，写入规范、存储省、可维护；**OBT**：把维度提前 join 进一张宽表，查询简单快、对分析师与 LLM 友好，但冗余大、变更贵。
- **问题**：客户有 20 年的遗留 SQL Server，你要在上面建分析与 AI 层。请说明分层方案，以及 Gold 层用星型还是 OBT 的判断依据。
- **参考答案**：
  1. **Bronze**：原样落地（含坏数据），不可变、可重放，记录来源与时间；这是审计与「重算」的基础。
  2. **Silver**：去重、标准化、关联实体、修 schema 漂移；这里定义「单一事实来源」，数据质量检查在此层强制。
  3. **Gold**：按消费者组织——报表用星型（BI 工具友好、维度可复用）；AI / 检索 / 自助分析用 OBT（一次查询拿全、便于向量化与提示词组装）。两者可共存，OBT 从星型物化出来。
  4. **判断依据**：查询模式（是否总是 join 同一组维度）、更新频率（维度常变则星型）、消费者能力（分析师 / LLM 偏爱宽表）、成本（BigQuery 按扫描量计费，OBT 配合分区 / 聚簇可反而更省）。
  5. **落地**：dbt 管理各层转换与测试；DuckDB 在本地快速剖析客户 CSV / Parquet 而不用起集群。
- **易错点 / 面试官关注**：
  - 直接在原始数据上建模；Bronze 可变。
  - 只知道一种模型，说不出取舍。
- **延伸**：Q7、Q8、[middleware/middleware-questions.md](../middleware/middleware-questions.md)

### Q7. 客户的查询在扫描 10TB 却只需要 10GB：你怎么用 EXPLAIN 定位并优化？BigQuery 的分区与聚簇怎么用？

- **难度**：🟡 中级
- **关键词**：执行计划 EXPLAIN, 窗口函数, 递归 CTE, 分区 partitioning, 聚簇 clustering, 扫描量 bytes scanned, 谓词下推
- **概念速记**：
  - **分区**：按日期 / 整数范围把表物理切块，查询带分区过滤时只扫相关块；**聚簇**：分区内按列排序存储，进一步裁剪块并加速过滤 / 聚合。
  - **EXPLAIN**：看扫描的行数 / 字节、是否用到分区剪枝、join 顺序与 shuffle 量、是否有笛卡尔积。
- **问题**：一条报表 SQL 跑 20 分钟、扫 10TB。请给出定位步骤、常见根因与改法，并说明 BigQuery 上分区与聚簇的选择原则。
- **参考答案**：
  1. **看计划**：扫描字节 / 行数、每阶段耗时、shuffle 与 join 类型；找「全表扫」「分区未剪枝」「join 爆炸」。
  2. **常见根因**：过滤条件对分区列做了函数运算（`DATE(ts)`）导致无法剪枝；`SELECT *`；先 join 后过滤；用子查询代替窗口函数导致多次扫描；递归 CTE 无终止条件。
  3. **改法**：把过滤改成分区列直接比较；只选需要的列（列存按列计费）；先过滤 / 预聚合再 join；用窗口函数一次扫描算排名 / 累计；物化视图或 Gold 层预聚合。
  4. **分区**：按最常用的时间过滤列（摄取时间或事件时间），粒度按数据量（天 / 小时），控制分区数（上限与元数据开销）。
  5. **聚簇**：选高基数且常做等值 / 范围过滤或 GROUP BY 的列（客户 ID、地区），最多 4 列且顺序重要；对未分区的大表也能用。
  6. **验证**：对比优化前后扫描字节与耗时（成本直接与扫描量挂钩）；把「每查询最大扫描量」设为配额防误操作。
- **易错点 / 面试官关注**：
  - 只会加索引（BigQuery 没有传统索引）。
  - 不知道分区列上的函数会禁用剪枝。
- **延伸**：Q6、Q8、[BigQuery 性能最佳实践](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-overview)

### Q8. Spark / Ray 处理客户数据时出现 Data Skew 与 OOM，怎么排查与解决？

- **难度**：🟡 中级
- **关键词**：数据倾斜 data skew, 分区 partition, OOM, shuffle, 加盐 salting, 广播 join, 执行器内存
- **概念速记**：
  - **数据倾斜**：某些 key 的数据量远大于其他，导致个别任务跑几小时、其他几秒；典型来源是空值 / 默认值 key 与热门实体。
  - **加盐**：给热 key 拼随机后缀拆成多个分区处理，再聚合回来。
- **问题**：一个 join 作业 99% 的任务 1 分钟完成、最后 1 个任务跑 2 小时后 OOM。请给出定位步骤与至少三种解决方案。
- **参考答案**：
  1. **定位**：UI 里看各任务的输入行数 / shuffle 读大小分布；对 join key 做 `GROUP BY key COUNT(*)` 找 top-N；检查 null / 空字符串 / 默认值是否占大头。
  2. **解决**：过滤或单独处理 null key；小表广播 join 避免 shuffle；热 key 加盐（大表 key 加 0–N 随机后缀，小表复制 N 份）；提高 shuffle 分区数；开启自适应查询执行（AQE）自动拆倾斜分区。
  3. **OOM 面**：执行器内存与堆外内存配置、每分区数据量控制（分区数 × 平均大小）、避免 `collect()` 到 driver、用列式格式减少读取。
  4. **预防**：Silver 层就把 key 标准化、去 null；数据质量检查对 key 分布做断言（「数据熔断器」：分布异常就告警并停下游，别让 CEO 先看到坏仪表盘）。
- **易错点 / 面试官关注**：
  - 只会「加内存」。
  - 不知道 null key 是最常见倾斜来源。
- **延伸**：Q6、Q9

### Q9. 「客户有 5PB 数据在本地，48 小时内要进 BigQuery 做应急演练」——你怎么做？

- **难度**：🟡 中级
- **关键词**：带宽瓶颈, Transfer Appliance, 并行准备, 分区策略, 增量同步, 期望管理
- **概念速记**：
  - **Transfer Appliance**：云厂商寄到现场的大容量存储设备，装满后寄回上传；适合 PB 级、网络带宽不足的迁移。数量级：1Gbps 链路传 5PB 需要约 460 天，10Gbps 也要 46 天。
- **问题**：这是高频题。请给出你的方案、并行做的准备工作，以及对客户的期望管理。
- **参考答案**：
  1. **先算账**：5PB / 10Gbps ≈ 46 天，网络不可能；48 小时只能靠物理设备或缩小范围。
  2. **物理迁移**：申请 Transfer Appliance 到现场并行灌数；设备在途时建 BigQuery 数据集、schema、分区 / 聚簇策略、加载作业与校验脚本。
  3. **缩小范围**：与客户确认演练真正需要的数据子集（最近 90 天？某几个表？）——通常 5PB 里 5% 就够，先通过专线 / VPN 传子集，全量走设备。
  4. **增量与校验**：设备装载后的新增数据通过 Storage Transfer / Pub/Sub 增量补；行数与校验和对账。
  5. **期望管理**：BLUF 告诉客户「48 小时内可用的是子集 X，全量 T+N 天」，写进演练范围；不要承诺物理上不可能的事。
- **易错点 / 面试官关注**：
  - 说「开大带宽传」而不算数。
  - 没想到缩小范围与并行准备。
- **延伸**：Q7、Q10、Q28

### Q10. 为客户设计 GCP「着陆区（Landing Zone）」：网络、身份、连接与最小可行架构

- **难度**：🟡 中级
- **关键词**：Landing Zone, 共享 VPC, Cloud Interconnect / VPN, Identity-Aware Proxy, 零信任, 最小可行架构 MVA, Terraform
- **概念速记**：
  - **着陆区**：客户项目里为你的平台准备的安全基础：项目 / 组织结构、网络、身份、日志、预算；代码要「落地」的地方。
  - **IAP**：不用 VPN，按身份与上下文授权访问内部应用，零信任的实现方式。
  - **MVA**：能在 30 天内证明价值的最简单架构（如 Cloud Run + BigQuery），拒绝镀金。
- **问题**：客户零云经验、有本地数据中心与 Okta 身份、要求数据不出境。请给出着陆区设计与第一周就能用 Terraform 拉起来的最小组件。
- **参考答案**：
  1. **组织与项目**：按环境（dev / prod）与工作负载拆项目；共享 VPC 让多个项目共用一张网、由网络团队集中管控；预算告警与 IAM 最小权限从第一天起。
  2. **连接**：本地 ↔ GCP 用 Cloud Interconnect（带宽大、稳定）或 Cloud VPN（快、便宜）；Private Google Access 让无公网 IP 的资源访问 Google API；区域固定在合规地区。
  3. **身份**：Okta 通过 OIDC / SAML 联合到 Cloud Identity；人访问内部应用走 IAP；工作负载用服务账号 + Workload Identity（Q11），不发 JSON 密钥。
  4. **数据**：Cloud Storage 摄取 → BigQuery 仓库；敏感数据先过 DLP 脱敏；高安全客户加 VPC Service Controls（Q12）。
  5. **MVA**：Cloud Run（无状态服务）+ BigQuery + Pub/Sub（事件胶水）+ Cloud Logging / Monitoring；GKE 只在确有需要时上。
  6. **Terraform**：模块化（网络 / IAM / 数据 / 计算），状态放远端并加锁，CI 里 `plan` 审阅；「5 分钟内拉起 GKE + BigQuery 数据集 + IAM 策略」是 FDE 的基本功。
- **易错点 / 面试官关注**：
  - 上来就上 GKE + 微服务。
  - 忘记身份联合与日志 / 预算这些「无聊但必须」的部分。
- **延伸**：Q11、Q12、[cicd-iac/cicd-iac-questions.md](../cicd-iac/cicd-iac-questions.md)、[cloud-security/cloud-security-questions.md](../cloud-security/cloud-security-questions.md)

### Q11. GKE Autopilot vs Standard、Workload Identity、私有集群：企业客户的 Kubernetes 该怎么选？

- **难度**：🟡 中级
- **关键词**：GKE Autopilot, Standard, Workload Identity, 私有集群 private cluster, 服务账号密钥, 节点池
- **概念速记**：
  - **Autopilot**：Google 管节点、按 Pod 资源计费、安全基线强制；**Standard**：自己管节点池、可用特权 / DaemonSet / GPU 定制，运维负担大。
  - **Workload Identity**：让 K8s 服务账号扮演 IAM 服务账号，工作负载访问 GCP API 不需要下载 JSON 密钥——密钥泄露是云上最常见的事故来源。
  - **私有集群**：节点无公网 IP，控制面通过私有端点访问，满足「不暴露公网」的企业要求。
- **问题**：客户安全团队要求「不允许公网 IP、不允许长期凭证」，同时 AI 工作负载要 GPU。你怎么选与配置？
- **参考答案**：
  1. **选型**：默认 Autopilot（少运维、安全基线自动满足），需要 GPU 节点定制、特权 DaemonSet（监控 / 网络插件）或特殊内核参数时用 Standard 专用节点池；也可两者并存（不同集群）。
  2. **私有集群**：启用私有节点 + 私有控制面端点，授权网络限制谁能访问 API；出网通过 Cloud NAT；镜像从 Artifact Registry 私有拉取。
  3. **身份**：全部工作负载用 Workload Identity 绑定最小权限 IAM 服务账号；禁止创建服务账号密钥（组织策略约束）。
  4. **GPU**：Standard 节点池 + GPU 驱动 DaemonSet，或 Autopilot 的加速器 Pod 类；提前申请 A100 / H100 配额（发现清单里的项）；用节点自动扩缩与抢占式实例控成本。
  5. **运维**：发布通道（Release channel）跟版本、维护窗口、PodDisruptionBudget、网络策略、二进制授权 / 镜像签名（与 Q20 呼应）。
- **易错点 / 面试官关注**：
  - 用 JSON 密钥挂 Secret 给 Pod。
  - 说不出 Autopilot 的限制（特权容器、部分 DaemonSet、节点级定制）。
- **延伸**：Q10、Q20、[kubernetes/kubernetes-questions.md](../kubernetes/kubernetes-questions.md)

### Q12. VPC Service Controls 与 DLP：金融 / 政府客户的数据防泄露怎么设计？

- **难度**：🔴 高级
- **关键词**：VPC Service Controls, 安全边界 perimeter, 数据外泄 exfiltration, 访问级别 access level, 边界桥 bridge, Sensitive Data Protection / DLP, 脱敏 masking
- **概念速记**：
  - **VPC SC**：围绕 Google 托管服务（BigQuery、Storage、Agent Platform 等）划一个安全边界，只有边界内的项目 / 授权网络 / 满足访问级别的身份才能调用这些 API，防止把数据复制到未授权项目——身份被盗也搬不走数据。
  - **DLP**：识别并脱敏 PII / PHI（姓名、身份证、病历号），在数据进入分析层之前处理。
- **问题**：医院客户有 HIPAA 要求，数据不得离开边界且分析层不能看到 PII。请设计边界、常见坑与与第三方 / 跨项目集成的处理。
- **参考答案**：
  1. **边界设计**：把数据项目、分析项目、AI 项目放同一边界；受限服务列全（BigQuery、GCS、Pub/Sub、Agent Platform、Logging）；访问级别绑定公司网络 / 设备 / 身份。
  2. **脱敏流水线**：摄取时 DLP 扫描 → 令牌化 / 掩码 / 泛化（生日 → 年龄段）→ 脱敏后的数据进 Silver / Gold；原始数据只在受限项目、最小权限可读；审计日志开全。
  3. **常见坑**：CI / 开发机在边界外调用 API 被拒（要配访问级别或跳板）；跨项目（客户其他项目、第三方 SaaS）访问要用**边界桥**或出入站规则精确放行；日志 / 监控导出也受限；先用 dry-run 模式观察违规再强制。
  4. **与 Agent / RAG 的关系**：向量索引与提示词日志也是 PHI，必须在边界内；模型调用不能走边界外的公网端点。
  5. **证明合规**：把边界配置、访问级别、DLP 规则、审计日志作为 ATO / HIPAA 评审的证据材料（Q19）。
- **易错点 / 面试官关注**：
  - 把 VPC SC 当成防火墙（它约束的是 API 访问不是 IP 包）。
  - 忘了 dry-run，直接强制导致所有集成断掉。
- **延伸**：Q10、Q19、Q22、[VPC Service Controls 概述](https://cloud.google.com/vpc-service-controls/docs/overview)

### Q13. 用 Pub/Sub / Cloud Run / Cloud Functions 做「实时胶水」：客户系统与你的平台之间的事件集成怎么设计？

- **难度**：🟡 中级
- **关键词**：Pub/Sub, Cloud Run, 事件驱动, 幂等, 死信主题 dead-letter, 变更数据捕获 CDC, 企业集成模式
- **概念速记**：
  - **胶水（glue）**：把客户遗留系统（SQL Server、SAP、SharePoint）与平台连起来的一层，FDE 的一半代码在这里；要求可观测、幂等、可交接。
  - **企业集成模式**：消息通道、翻译器、内容过滤、聚合器、死信通道——Hohpe 那本书的词汇表。
- **问题**：客户的 SQL Server 每分钟产生新工单，你的平台要在 30 秒内看到并触发 Agent 处理。请设计集成，并说明失败、重复与格式变化怎么处理。
- **参考答案**：
  1. **捕获**：优先 CDC（Debezium / Datastream 读事务日志）而不是轮询大表；无法装 CDC 时用带水位的增量轮询（更新时间 + 主键）。
  2. **传输**：Pub/Sub 主题按事件类型分；消息带 schema（Avro / Proto）与版本；订阅者 Cloud Run 按推送触发，自动扩缩。
  3. **可靠性**：至少一次投递 → 消费者按事件 ID 幂等；失败重试指数退避；超过次数进死信主题并告警；顺序需要时按 key 排序发布。
  4. **翻译层**：客户私有格式（`.xyz`、固定宽度报文）用独立 Cloud Function 转成 Parquet / JSON，这就是「Delta」的典型胶水，代码要能进产品仓库而不是留在客户项目里。
  5. **观测与交接**：每条消息带 trace id；仪表盘看积压、错误率、端到端延迟；Runbook 与告警交给客户 Ops（Day 2）。
- **易错点 / 面试官关注**：
  - 轮询全表；没有幂等与死信。
  - 胶水代码没有 schema 版本，客户改字段就全断。
- **延伸**：Q3、Q14、[system-design/system-design-questions.md](../system-design/system-design-questions.md) Q10

### Q14. 企业 RAG 蓝图：从复杂 PDF 摄取到混合检索，你会怎么搭、怎么用托管服务？

- **难度**：🟡 中级
- **关键词**：文档解析 LlamaParse, 托管 RAG（Agent Search / Vertex AI Search）, 向量检索 Vector Search, 混合检索 BM25 + 向量, 行业术语, 引用 grounding
- **概念速记**：
  - **企业 RAG 蓝图**：摄取（解析 PDF / 表格）→ 落地（托管检索引擎做语义检索）→ 向量存储（高规模索引）→ 混合检索（向量抓语义、关键词抓行业专有名词）→ 带引用生成。
  - **托管 vs 自建**：托管检索引擎（Agent Search 类）几天可上线、自带权限与引用；自建（向量库 + 自己的分块 / 重排）灵活可控但要自己运维——FDE 默认先托管证明价值。
- **问题**：客户有 10 万份合规 PDF（带表格与扫描件），要在 30 天内交付一个能引用来源的问答助手。请给出方案与你会先做的两个「快速胜利」。
- **参考答案**：
  1. **摄取**：用专门的文档解析器处理表格 / 多栏 / 扫描 OCR；按结构分块并保留页码与章节路径作为引用元数据；写入对象存储 Bronze，解析结果进 Silver。
  2. **检索**：先用托管检索引擎（自带分块、嵌入、权限、引用）拿到基线；行业术语（药品编号、条款号）靠关键词检索兜底 → 混合检索 + 融合排序；需要时再加自建向量索引与重排。
  3. **生成**：只依据检索证据、逐句引用；无证据则说不知道；输出经 DLP 过滤。
  4. **权限**：文档 ACL 同步到索引元数据，检索时过滤（不是生成后过滤）。
  5. **快速胜利**（第 2 周）：① 在「政策」子集上跑出 ≥ 90% 的 Top-3 命中率并给客户看；② 给 5 个真实用户一个最简 UI 做 UAT。
  6. **评测**：金标问答集（客户专家标注）、命中率 / 忠实度 / 延迟；每次改分块 / 模型跑回归（Q16）。
- **易错点 / 面试官关注**：
  - 一开始就自建全套（向量库、重排、微调）而不是先托管证明价值。
  - 只有向量检索，行业术语召回不到；引用不可追溯。
- **延伸**：Q16、[system-design/system-design-questions.md](../system-design/system-design-questions.md) Q31、[gpu-ai/gpu-ai-questions.md](../gpu-ai/gpu-ai-questions.md)

### Q15. 多 Agent 编排（以 Google ADK 为例）：层级委派、A2A 协议、工作流 Agent 与 LLM Agent 怎么选？

- **难度**：🟡 中级
- **关键词**：Agent Development Kit（ADK）, 多 Agent 层级, Agent2Agent（A2A）, 工作流 Agent（Sequential / Parallel / Loop）, 模型无关 LiteLLM, Agent Runtime
- **概念速记**：
  - **ADK**：Google 开源的代码优先多 Agent 框架，把 Agent 开发当软件工程做（模块化、层级、可测试）；可部署到托管的 Agent Runtime。
  - **A2A**：让不同系统的 Agent 通过一致的 HTTP 接口互相发现、交接任务的开放协议。
  - **工作流 Agent**：确定性编排（顺序 / 并行 / 循环），不靠 LLM 规划下一步；**LLM Agent**：由模型决定调用哪个工具 / 子 Agent。
- **问题**：客户要一个「读财务报表 → 查数据仓库 → 生成审阅报告」的助手。请设计 Agent 拓扑，说明哪些环节用确定性工作流、哪些用 LLM 决策，以及怎么部署与观测。
- **参考答案**：
  1. **拓扑**：Manager（LLM Agent，理解请求、分派）→ Planner / SQL Coder / Reviewer 三个专职子 Agent；SQL Coder 只有 BigQuery 只读工具；Reviewer 用独立提示词做校验。
  2. **确定性优先**：「解析报表 → 查库 → 汇总 → 审阅」的固定顺序用 SequentialAgent；多报表并行用 ParallelAgent；「审阅不通过就重来（最多 3 次）」用 LoopAgent——只在真正需要判断的节点用 LLM 决策，降低不可预测性与成本。
  3. **工具与权限**：每个工具声明 schema、超时、幂等；副作用工具（写库、发邮件）需人工审批；每个 Agent 用独立最小权限服务账号。
  4. **跨系统**：客户已有的 Agent（如其他厂商）通过 A2A 接入，而不是重写。
  5. **模型策略**：模型无关层（LiteLLM）让简单节点用小模型、关键节点用大模型；可切换供应商是客户采购上的硬需求。
  6. **部署与观测**：Agent Runtime（托管自动扩缩、会话与记忆）或 Cloud Run / GKE；Cloud Trace 默认开启，追踪每次工具调用；提示词 / 响应日志进 BigQuery 做分析；LangSmith 类工具看链路断在哪。
- **易错点 / 面试官关注**：
  - 全部交给一个大 Agent 自由规划（不可预测、难评测）。
  - 没有权限边界；工具输出当可信指令（提示注入）。
- **延伸**：Q16、Q18、[system-design/system-design-questions.md](../system-design/system-design-questions.md) Q34、[Google ADK](https://github.com/google/adk-docs)

### Q16. LLM 系统评测的「两层循环」：怎么向客户证明 Agent 可靠、怎么证明一次改动是进步？

- **难度**：🔴 高级
- **关键词**：内循环 inner loop（adk eval）, 外循环 outer loop（生产评测）, 金标数据集, 工具轨迹评分 tool trajectory, 成对评测 pairwise（AutoSxS）, 逐点评测 pointwise, RAG 三元组（Groundedness / Fulfillment / Coherence）, 忠实度 faithfulness
- **概念速记**：
  - **内循环**：开发时对金标集快速、交互式跑评测；指标如工具轨迹平均分（是否调了对的工具）、响应匹配分（ROUGE）、基于评分表的最终质量。
  - **外循环**：生产规模、自动化、接入 CI/CD 的评测；用于证明模型 / 提示词改动在成千上万用例上是可测的进步。
  - **成对评测**：用更强的模型当「自动评审」比较 A / B 两个输出给出胜率；**逐点评测**：对单个输出按维度打分：Groundedness（只依据检索上下文）、Fulfillment（遵循系统指令）、Coherence（语言质量）。
- **问题**：客户问「你怎么证明它不胡说」。请给出评测体系：数据集怎么来、离线与在线各测什么、一次提示词改动怎么放行、上线后怎么监控。
- **参考答案**：
  1. **金标集**：与客户专家共建 100–500 条真实问题 + 证据 + 期望答案 + 期望工具轨迹；覆盖高价值与高风险场景；持续从线上失败样本补充。
  2. **内循环**：每次改动本地跑 `eval`，看工具轨迹分（Agent 是否走了对的步骤）、响应质量、延迟；不达标不进 PR。
  3. **外循环**：CI 里对全量金标集跑逐点评测（Groundedness / Fulfillment / Coherence）+ 与当前生产版本的成对评测；放行标准写进 PRD（如「忠实度 ≥ 0.9、胜率 ≥ 55%、p95 < 5s」）。
  4. **自动评审的边界**：LLM-as-judge 与人工抽样对齐（一致率），高风险领域保留人工复核；避免用同一个模型既生成又评审。
  5. **在线**：影子流量 / A/B；用户反馈；模型监控看输入分布漂移、拒答率、幻觉抽检；告警接 Day 2 团队。
  6. **向客户呈现**：BLUF 一页：金标集来源、当前分数、放行门槛、监控仪表盘——这就是「Definition of Success」。
- **易错点 / 面试官关注**：
  - 「凭感觉测」；没有金标集与放行门槛。
  - 只测最终答案不测工具轨迹；不区分离线 / 在线。
- **延伸**：Q14、Q15、Q18、[Anthropic: Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### Q17. 「银行要 < 100ms 的实时欺诈检测，还想用 LLM」——怎么架构？

- **难度**：🔴 高级
- **关键词**：延迟预算, 两级架构 two-tier, 确定性模型（XGBoost）, 异步 LLM 复核, 特征存储, 可解释性, 合规
- **概念速记**：
  - **两级架构**：主路径用快速确定性模型在预算内决策；只把「可疑」交易异步送给 LLM Agent 做深度调查与解释，输出给人工或后置动作。
- **问题**：这是高频题。请给出架构、延迟预算分配、LLM 的角色边界，以及监管（可解释、可审计）要求怎么满足。
- **参考答案**：
  1. **先否定**：LLM 一次推理通常几百毫秒到秒级，不能在主路径。
  2. **主路径（< 100ms）**：特征存储在线拉取（毫秒级）→ GBDT / 逻辑回归类模型（个位数毫秒）→ 规则引擎兜底 → 决策；模型部署在托管推理端点或本地，就近部署、连接复用、批量特征。
  3. **第二级（异步）**：被标记的交易进队列 → LLM Agent 调用工具（客户历史、相似案例、外部名单）生成调查摘要与建议 → 分析师 UI；可用于事后冻结、通知、报告生成。
  4. **可解释与审计**：主模型提供特征贡献（SHAP 类）；LLM 输出带证据引用；所有决策与输入快照留档以满足监管；模型变更走评测门槛（Q16）。
  5. **运维**：主路径 SLO（p99 延迟、可用性）、模型漂移监控、特征新鲜度；LLM 路径失败不影响主路径（降级为规则）。
  6. **面试加分**：给数字（1 万 TPS、特征拉取 5ms、模型 3ms、网络 20ms）说明预算怎么分配。
- **易错点 / 面试官关注**：
  - 把 LLM 塞进主路径。
  - 没有可解释性与审计留档（金融监管必问）。
- **延伸**：Q16、Q28、[system-design/system-design-questions.md](../system-design/system-design-questions.md) Q32

### Q19. 合规地基：ATO、DoD 影响级别、FedRAMP、STIG、ITAR、CMMC 分别约束什么？

- **难度**：🔴 高级
- **关键词**：ATO（Authority to Operate）, NIST RMF, IL2 / IL4 / IL5 / IL6, FedRAMP Moderate / High, STIG, ITAR / EAR, CMMC 2.0, NIST SP 800-171
- **概念速记**：
  - **ATO**：政府机构授权官签字允许系统上其网络运行；通过 NIST 风险管理框架取得；没有 ATO 一切归零。
  - **影响级别**：IL2 公开 / 非关键 → IL4 受控非密信息（CUI）→ IL5 更敏感 CUI 与关键任务 → IL6 机密（Secret）；级别决定能用哪些云与哪些服务。
  - **FedRAMP**：联邦民用等价体系；多数生成式 AI 服务只到 Moderate，是很多国防工作负载的硬阻塞——承诺功能前先查市场目录。
  - **STIG**：DISA 发布的逐行加固清单（OS / 容器 / 数据库）；CI 必须产出合规工件。
  - **ITAR / EAR**：出口管制；用受控数据训练的模型权重本身也受控，不能交给非美籍人员。
  - **CMMC 2.0**：国防承包商认证，Level 2 是实际门槛，按 NIST SP 800-171（110 项）评估。
- **问题**：客户是国防承包商，要在其网络里部署你们的 AI 平台。请说明你在发现阶段要确认哪些合规要素、它们如何改变架构选择，以及哪些承诺你绝不能随口做。
- **参考答案**：
  1. **先问级别**：数据与系统的 IL / 分类 → 决定云区域（政府云 / 隔离）、可用服务（FedRAMP 级别）、人员要求（国籍 / 许可）。
  2. **ATO 路径**：谁是授权官、现有 ATO 边界能否继承、需要哪些控制证据（NIST 800-53 / 800-171 映射）；把评审所需证据（架构、加固、审计日志、SBOM）当交付物规划，周期按月计。
  3. **加固**：基础镜像必须 STIG 合规（用 Iron Bank 等，Q21）；CI 产出扫描报告；配置基线自动化。
  4. **出口管制**：模型权重、训练数据、文档的流向与人员访问要审；跨境远程支持可能被禁止。
  5. **不能随口承诺**：「我们用 X 生成式 AI 服务」（可能只有 FedRAMP Moderate）、「远程团队来支持」（ITAR）、「几周拿到 ATO」（通常几个月）、「跨域传输很简单」（CDS 是独立审批，Q22）。
  6. **架构后果**：可能必须完全隔离网络部署（Q20–Q24），托管 AI 服务改为本地推理。
- **易错点 / 面试官关注**：
  - 把合规当上线前的检查项而不是第一周的架构输入。
  - 不知道 FedRAMP 级别会直接排除某些 AI 服务。
- **延伸**：Q12、Q20、Q22、[NIST SP 800-171](https://csrc.nist.gov/pubs/sp/800/171/r2/final)、[DoD Platform One](https://p1.dso.mil/)、[cloud-security/cloud-security-questions.md](../cloud-security/cloud-security-questions.md)

### Q20. 隔离网络里没有 pip / HuggingFace / 公网 API：模型权重、软件包与漏洞扫描怎么预置？

- **难度**：🔴 高级
- **关键词**：离线模型权重, 物理介质, SHA-256 校验, safetensors vs pickle, 许可与溯源 provenance, PyPI / npm / APT 镜像, 离线 NVD, Trivy / Grype
- **概念速记**：
  - **预置（pre-stage）**：隔离主机不能联网安装任何东西，所有依赖（权重、包、镜像、漏洞库）必须提前经审批带进去。
  - **safetensors**：只含张量的安全格式；pickle 反序列化可执行任意代码，在机密环境里就是远程代码执行漏洞。
- **问题**：请给出把一个开源 LLM 与其 Python 依赖安全带入隔离网络的完整流程，以及审计员会问的问题。
- **参考答案**：
  1. **权重**：加密物理介质由持证人员或快递送达；到达后 SHA-256 校验；用 safetensors 加载，禁止 pickle；每个权重文件附签名的溯源记录（来源、许可证：Apache-2.0 / Llama 社区 / Gemma 条款、训练数据声明）——「从 HuggingFace 下的」不是答案。
  2. **软件包**：内部 PyPI 镜像（devpi / bandersnatch）、npm（Verdaccio）、APT（apt-mirror）；`pip.conf` / `.npmrc` 指向内网镜像；镜像内容按清单同步、版本锁定（lock 文件 + 哈希）。
  3. **漏洞扫描**：每个镜像工件进入前过 Trivy / Grype；漏洞库用**离线 NVD 快照**并定期更新；高危未修复需豁免记录与到期时间。
  4. **进入流程**：签名清单 → 人工审批 → 不可变审计日志（Q22 的清单式同步）；没有后台自动同步。
  5. **审计员会问**：权重从哪来、许可证是什么、谁批准的、哈希是否核对、哪些 CVE 未修、豁免谁签的、SBOM 在哪。
- **易错点 / 面试官关注**：
  - 用 pickle 权重；权重没有许可 / 溯源记录。
  - 漏洞库不更新，扫描形同虚设。
- **延伸**：Q19、Q21、Q22、[gpu-ai/gpu-ai-questions.md](../gpu-ai/gpu-ai-questions.md)

### Q21. 加固容器供应链：Iron Bank、Harbor、Cosign 签名、准入控制与 distroless 各解决什么？

- **难度**：🟡 中级
- **关键词**：Iron Bank, Harbor, 镜像签名 Cosign / Sigstore, 离线信任根, 准入控制 Kyverno / OPA Gatekeeper, distroless / chainguard, SBOM
- **概念速记**：
  - **Iron Bank**：DoD 集中维护的预加固、STIG 合规、持续扫描的容器镜像库；基础镜像不在里面通常就不能上 Platform One 集群。
  - **Harbor**：隔离环境事实标准的私有镜像仓库，自带签名、复制、CVE 扫描。
  - **签名 + 准入**：每个镜像用离线信任根密钥签名；集群准入控制器拒绝未签名 / 签名不匹配的镜像。
  - **distroless**：没有 shell 与包管理器的最小基础镜像——攻击者进不去也横向不了。
- **问题**：设计从构建到隔离集群部署的镜像流水线，说明每一环节的控制点。
- **参考答案**：
  1. **基础镜像**：优先 Iron Bank / chainguard / distroless；自建基础镜像要过 STIG 加固与扫描。
  2. **构建**：可重复构建、固定依赖哈希、生成 SBOM（SPDX / CycloneDX）；CI 里扫描（Trivy / Grype），策略门槛（无 Critical）。
  3. **签名**：Cosign 用离线信任根签名镜像与 SBOM 证明（attestation）；密钥在 HSM / Vault，签名记录进离线 Rekor 或等价审计日志。
  4. **传输**：镜像按清单导出 → 审批 → 导入内网 Harbor（Q22）；Harbor 再次扫描与复制到各站点。
  5. **部署**：Kyverno / Gatekeeper 策略：只允许内网仓库、必须验签、禁止 latest、禁止特权、必须有资源限制；二进制授权类机制在托管 K8s 上等价。
  6. **运行**：只读根文件系统、非 root、seccomp / AppArmor；镜像无 shell 时排障靠临时调试容器。
- **易错点 / 面试官关注**：
  - 只扫描不签名；或签名了但集群不验。
  - 用 latest 标签；基础镜像来源不可控。
- **延伸**：Q11、Q20、[Sigstore](https://www.sigstore.dev/)、[kubernetes/kubernetes-questions.md](../kubernetes/kubernetes-questions.md)

### Q22. 跨域与回传：数据二极管、跨域解决方案（CDS）、清单式同步与脱敏管道怎么配合？

- **难度**：🔴 高级
- **关键词**:单向数据二极管 data diode, 跨域解决方案 CDS, 分类级别, 清单式同步 manifest-based sync, 人工签核, 不可变审计, DLP 脱敏 redaction
- **概念速记**：
  - **数据二极管**：硬件上只允许单向流动的设备；常见模式是权重流**进**飞地、遥测流**出**。
  - **CDS**：经过认证、在不同密级之间中转数据的软硬件；审批本身是数月流程，要在发现阶段就规划。
  - **清单式同步**：每个进出飞地的工件都有签名清单 + 人工签核 + 不可变审计记录；没有「后台自动同步」。
- **问题**：你的平台在飞地里运行，总部需要遥测来改进产品，飞地需要新模型版本。请设计双向流动的架构与流程，并说明脱敏管道要处理什么。
- **参考答案**：
  1. **方向与设备**：入向（模型、补丁、镜像）经二极管或 CDS 进；出向（遥测、评测结果）经独立的出向二极管 / CDS 出；不同密级之间必须走认证的 CDS。
  2. **入向流程**：Q20 的预置流程——清单、哈希、签名、审批、审计；接收侧自动验签后才入仓。
  3. **出向脱敏**：遥测先过 DLP 阶段（正则 + 分类模型）清洗 PII、坐标、单位番号、任何命中机密关键词表的字符串；聚合而非原始日志；人工抽检；再进清单与签核。
  4. **审计**：谁批准、什么时候、哈希、内容摘要，写入不可变日志；定期与授权官复核。
  5. **规划**：CDS 审批周期长，发现清单里就要有；不要在第 12 周才发现遥测出不去。
- **易错点 / 面试官关注**：
  - 假设可以「开一条 VPN 同步」。
  - 出向没有脱敏 / 聚合就想传原始日志。
- **延伸**：Q19、Q20、Q23

### Q23. 边缘运行时：车载、船上、工厂车间不跑完整 GKE，你的栈是什么？

- **难度**：🟡 中级
- **关键词**：K3s / MicroK8s / k0s, Google Distributed Cloud（GKE on Bare Metal）, 本地推理运行时（Ollama / vLLM / llama.cpp / TensorRT-LLM）, 量化模型, 存储转发 store-and-forward, Fluent Bit + WAL
- **概念速记**：
  - **轻量 Kubernetes**：单二进制、离线优先的发行版，适合边缘与断网环境。
  - **存储转发遥测**：假设网络会断几小时，日志与指标先落本地磁盘 WAL，联通时再机会性上传。
- **问题**：客户要在几十辆车 / 几艘船上运行视觉 + LLM 推理，网络间歇。请给出运行时栈、模型策略、遥测与升级方案。
- **参考答案**：
  1. **编排**：K3s（或 k0s / MicroK8s）单节点或小集群，离线安装（镜像与二进制预置）；需要与云侧统一管理时用 Google Distributed Cloud 类方案，周期性回连控制面。
  2. **推理**：按硬件选运行时——GPU 用 vLLM / TensorRT-LLM，CPU / 小卡用 llama.cpp / Ollama；模型量化（INT8 / 4-bit）适配显存与功耗；模型即容器镜像 / 制品，签名与版本化。
  3. **遥测**：Fluent Bit 本地缓冲 + 磁盘 WAL，联通时转发；本地最小告警（磁盘、GPU 温度、模型错误率）；回传经 Q22 的脱敏与清单流程。
  4. **升级**：期望状态声明 + 差分更新 + 本地健康判定与自动回滚（与 system-design 模块 Q27 的边缘发布一致）；分波次（内测车 → 区域 → 全量）。
  5. **本地基础设施**：时间（Q24）、PKI、密钥、本地镜像缓存、离线包镜像的精简副本。
- **易错点 / 面试官关注**：
  - 把云上的栈原样搬到边缘。
  - 遥测无缓冲，断网即丢；升级无本地回滚。
- **延伸**：Q20、Q24、[system-design/system-design-questions.md](../system-design/system-design-questions.md) Q27、[K3s air-gap install](https://docs.k3s.io/installation/airgap)

### Q24. 隔离网络特有的故障模式：时钟漂移、证书轮换、密钥管理、「首次启动」问题怎么在第一周就设计好？

- **难度**：🔴 高级
- **关键词**：时钟漂移 clock drift, NTP / Chrony / PTP, 内部 PKI（Vault / step-ca）, 证书轮换, 密钥管理 Vault HA + HSM 自动解封, SOPS + age, 首次启动 first boot, 签名 ISO
- **概念速记**：
  - **时钟漂移**：没有 NTP，TLS 证书会「悄悄过期」、Kerberos 票据停发；第一天就要有本地时间源。
  - **证书**：不能用 Let's Encrypt；飞地内要有内部 PKI 并自动轮换。
  - **密钥**：云 KMS 不可达；Vault HA + HSM 自动解封，或 GitOps 流程用 SOPS + age。
  - **首次启动**：Day-1 配置怎么进去？通常是持证人员送来的签名 ISO / 介质，要从第一周设计而不是第十二周才发现。
- **问题**：这些是「云上从不发生、客户现场必然发生」的问题。请逐项给出设计与验证方法。
- **参考答案**：
  1. **时间**：本地 Chrony 服务器（GPS / 原子钟 / 硬件时钟源，PTP 用于高精度）；所有节点指向它；监控偏移并告警；证书与令牌校验对时间容忍度设合理值。
  2. **PKI**：内部根 CA 离线保存、中间 CA 在 Vault / step-ca 签发；短有效期证书 + 自动轮换（cert-manager 对接内部 CA）；到期前告警；根证书分发进入信任库的流程。
  3. **密钥**：Vault HA 集群、HSM 自动解封、审计日志；应用通过短期动态凭证取密钥；GitOps 仓库里的密文用 SOPS + age，私钥只在飞地。
  4. **首次启动**：签名 ISO / 引导介质包含最小配置（时间、CA、Vault 引导、镜像仓库地址）；验签后才继续；文档化「谁带、怎么验、怎么回滚」。
  5. **验证**：演练——拔网、跳时钟、让证书过期、重启 Vault，看系统是否自愈；把这些演练写进交接。
- **易错点 / 面试官关注**：
  - 认为这些是运维细节、以后再说。
  - 证书 / 密钥没有轮换与告警，半年后全站宕机。
- **延伸**：Q20、Q23、[linux/linux-questions.md](../linux/linux-questions.md)、[sre-reliability/sre-questions.md](../sre-reliability/sre-questions.md)

### Q25. 金字塔原理（BLUF）、MECE、80/20：给 CTO 汇报架构方案时怎么组织内容？

- **难度**：🟢 初级
- **关键词**：金字塔原理 Pyramid Principle, 结论先行 BLUF, MECE, 80/20 价值范围, 镀金 gold-plating, 需求翻译
- **概念速记**：
  - **BLUF**：先给结论与「所以呢」，再给支撑数据；高管要先听答案。
  - **MECE**：相互独立、完全穷尽；把「AI 战略」拆成不重叠、不遗漏的技术任务。
  - **80/20**：找到能解决 80% 痛点的 20% 功能，拒绝没人要的复杂功能。
- **问题**：你要在 15 分钟里向 CTO 汇报「是否要把分析平台迁到云」。请给出汇报结构与一句话开头。
- **参考答案**：
  1. **开头（BLUF）**：「建议：分两阶段迁移，先分析层后交易层，6 个月内把报表时延从小时级降到分钟级、成本下降 30%；需要您决定的是安全边界方案与内部 owner。」
  2. **结构**：结论 → 三个支撑理由（价值 / 风险 / 成本，MECE）→ 每个理由 2–3 个数据点 → 需要的决策与下一步。
  3. **80/20**：明确第一阶段只做最痛的 20%（如报表与自助分析），交易系统与遗留接口放后面并说明原因。
  4. **风险与替代方案**：列出不做的代价（Cost of Inaction）与另一条路的取舍，让 CTO 做选择而不是被推销。
  5. **形式**：一页摘要 + 附录；口头汇报不念架构图，架构图放附录供技术追问。
- **易错点 / 面试官关注**：
  - 从技术细节讲起，10 分钟后还没结论。
  - 只讲收益不讲风险与需要谁决策。
- **延伸**：Q3、Q27、[behavior/behavior-questions.md](../behavior/behavior-questions.md)

### Q26. SOW、MVA、技术演示与 UAT：怎么用这些工件防止范围蔓延并证明价值？

- **难度**：🟡 中级
- **关键词**：SOW 工作说明书, MSA 主服务协议, 范围蔓延 scope creep, 最小可行架构 MVA, 价值叙事 value narrative, UAT 用户验收测试, 架构决策记录 ADR
- **概念速记**：
  - **SOW**：项目的法律「围栏」，定义你的工作到哪里为止；不在 SOW 里的就是范围蔓延。
  - **技术演示 ≠ 功能巡展**：FDE 的演示是**价值叙事**——数据如何从客户混乱的遗留系统流到干净的 AI 洞察。
  - **UAT**：客户员工真的用了并接受，项目才算完成；代码再好、不被采纳也是失败。
- **问题**：客户在第 6 周提出「顺便把 CRM 也接进来」。请说明你怎么处理，以及从第 1 周起哪些工件能让这个对话变简单。
- **参考答案**：
  1. **当场回应**：不拒绝也不答应；确认业务价值与紧迫度，说明对当前里程碑的影响，承诺 48 小时内给评估。
  2. **对照 SOW**：不在范围内 → 走变更流程：影响（时间 / 成本 / 风险）→ 由客户发起人与我方决定是否换出其他范围或追加；写进每周高管摘要。
  3. **MVA 思维**：即使接受，也先用最小方案（只读同步一张表）证明价值再扩。
  4. **工件**：SOW（边界）、Site Survey（现状与已知缺口）、技术范围文档 / PRD（含成功定义与 Out of Scope 列表——「AS400 集成推迟到 Q3」这种明确写下的不做项就是防蔓延的最好证据）、ADR（为什么当初这么选）。
  5. **UAT 与演示**：每个里程碑用真实用户的 UAT 结果与价值叙事演示收尾，让「新增范围」的讨论建立在已交付价值之上。
- **易错点 / 面试官关注**：
  - 为了讨好客户直接答应。
  - 没有书面的 Out of Scope，事后扯皮。
- **延伸**：Q4、Q27、Q28

### Q27. 现场调研报告（Site Survey）、技术范围文档 / PRD、每周高管摘要（WES）：各自写什么、给谁看？

- **难度**：🟡 中级
- **关键词**：Site Survey, 数据版图 data landscape, 技术与安全约束, Delta 与胶水, 快速胜利 quick win, PRD 成功定义, 分阶段部署, 每周高管摘要 WES, 风险与阻塞
- **概念速记**：
  - **Site Survey**（第 1 周）：记录「混乱的现实」——源系统、数据体量与增长、已知质量问题、身份与连接约束、外泄风险、产品缺口与拟议胶水、第 2 周的快速胜利。
  - **技术范围文档 / PRD**：目标与用户画像 → 成功定义（可测的评测指标）→ 分阶段部署 → 明确不做什么。
  - **WES**：每周一页：本周交付的价值（指标变化、里程碑）、风险与阻塞（影响 + 需要谁做什么）、Day 30 展望——这是续约的依据。
- **问题**：请为「保险公司理赔文档问答助手」写出三份工件的骨架，各 5 条以内要点。
- **参考答案**：
  1. **Site Survey**：源系统（本地 SQL Server 2016 + SharePoint 非结构化）；数据 5TB、日增 50GB、必须留在境内；30% 记录缺时间戳、CRM 无主键；身份 Okta OIDC；无公网、需 Interconnect + Private Google Access；VPC SC 已启用需申请边界桥；产品缺口：不支持客户私有 `.xyz` 格式 → Cloud Function 转 Parquet；第 2 周快速胜利：在「保单条款」子集上做到 90% 检索命中。
  2. **PRD**：让理赔员用多 Agent 助手完成理赔调查；成功 = Top-3 命中率 > 90%、端到端 < 5s、金标集幻觉率 0%（客户人工验证）；阶段 1 手动触发 + BigQuery 静态导出，阶段 2 Pub/Sub 实时；不做：AS400 集成（Q3 再议）。
  3. **WES**：状态绿 / 黄 / 红；价值：查找时间下降 40%、GKE 私有集群过安全评审、12 亿行历史日志入库并优化分区；风险：客户 IT 延迟开防火墙端口 → 实时仪表盘延期 3 天 → 需要发起人批准例外单；Day 30：完成成对评测、一线支持移交客户 Ops。
  4. **原则**：每份都 BLUF；数字而非形容词；风险必须带动作与责任人。
- **易错点 / 面试官关注**：
  - 文档写成技术流水账，没有成功定义与不做项。
  - 高管摘要只报进度不报价值与阻塞。
- **延伸**：Q2、Q25、Q26

### Q28. 案例：大型医院集团要用你的平台预测再入院，20 年数据在本地 SQL Server、零云经验、HIPAA 极严——走一遍你的前 30 天。

- **难度**：🔴 高级
- **关键词**：30 天计划, 数据剖析 profiling, 定义指标, 着陆区, VPC SC + DLP, 检索增强 + 胶水服务, 成对评测, UAT, 信任建立
- **概念速记**：
  - **30 天节奏**：1–7 天发现与信任 → 8–15 天安全着陆区 → 16–25 天流水线与 Delta → 26–30 天价值验证。
- **问题**：请按周给出技术动作与干系人动作，并说明每周的可验收产出。
- **参考答案**：
  1. **第 1–7 天（发现与信任）**：技术：对 SQL Server 做数据剖析审计（年龄、诊断、上次就诊、缺失率、主键）；干系人：与首席医疗官定义「再入院」（30 天还是 90 天？哪些排除？）、与感到被威胁的 IT 团队建立关系（Q5）；产出：Site Survey + 指标定义。
  2. **第 8–15 天（安全着陆区）**：Cloud Storage 摄取 + BigQuery 仓库；VPC Service Controls 边界 + DLP 在进入分析层前脱敏 PII / PHI（满足 HIPAA）；Interconnect / VPN 与身份联合；Terraform 化；产出：通过客户安全评审的着陆区。
  3. **第 16–25 天（流水线与 Delta）**：以病人病史为基础的检索增强流水线（托管检索引擎）；Delta：Cloud Run 上的自定义服务实时从 SQL Server 拉「生命体征」更新预测；数据熔断器与监控；产出：端到端可跑的预测流水线。
  4. **第 26–30 天（价值验证）**：成对评测对比模型预测与历史结局；给 5 位医生一个最简仪表盘做 UAT——如果他们不因数据改变行为，项目就失败；产出：评测报告 + UAT 结论 + Day 2 计划。
  5. **贯穿**：每周 WES；红旗（数据「两周就绪」、无内部 owner）第一周升级；合规证据同步积累。
  6. **评分口径**（面试官）：初级只讲 Python 脚本；高级会提安全、成本（FinOps）与干系人；顶级会说清指标定义、评测门槛与「医生是否改变行为」这个真正的成功标准。
- **易错点 / 面试官关注**：
  - 第一周就开始建模。
  - 没有 HIPAA 架构动作；没有 UAT。
- **延伸**：Q2、Q3、Q12、Q16、Q30

### Q29. 「初级答案 vs 高级答案」：FDE 案例评分表长什么样？你的技术演示怎么讲成价值叙事？

- **难度**：🟡 中级
- **关键词**：案例评分表 rubric, 初级 vs 高级, 安全, 成本优化 FinOps, 干系人认同, 价值叙事 value narrative
- **概念速记**：
  - **初级答案**：聚焦代码 / Python 脚本；**高级答案**：主动提安全、成本优化与干系人认同；**Staff 级**：讲清成功定义、评测门槛、Day 2 与政治风险。
- **问题**：请给出你会用的 FDE 案例评分表（维度与初 / 中 / 高级表现），并用「把遗留工单系统接入检索助手」为例说明技术演示怎么讲。
- **参考答案**：
  1. **评分表**：见本文件开头五维（澄清诊断 / 架构落地 / Delta 胶水 / 评测 Day 2 / 干系人沟通）。初级：能写脚本跑通；中级：能画可行架构并说安全与成本；高级：先定义成功指标与不做项，识别 Champion / Blocker，给 Day 2。
  2. **演示结构（价值叙事）**：① 客户的痛（分析师每天 3 小时翻工单）→ ② 数据从遗留系统怎么流出来（CDC → 脱敏 → 索引，用真实数据）→ ③ 一个真实问题的回答与引用 → ④ 指标（命中率、时延、节省时间）→ ⑤ 下一步与需要的决策。不做功能巡展。
  3. **演示准备**：用客户数据的脱敏子集；准备失败案例的坦诚说明；让 Champion 先看一遍。
  4. **面试加分**：说出你会怎么把这个案例的胶水抽象回产品（产品化咨询）。
- **易错点 / 面试官关注**：
  - 演示成「我们的产品有 20 个功能」。
  - 评分只看技术。
- **延伸**：Q1、Q26、Q28

### Q30. Day 2 与「让自己变得多余」：交接给客户运维团队的完整清单是什么？

- **难度**：🟡 中级
- **关键词**：Day 2 运维, 运行团队 run team, Runbook, 监控与告警交接, 模型再训练, 培训, 一线支持移交, ADR
- **概念速记**：
  - **Day 2**：FDE 离开后的一切——监控、再训练、故障处理、内部运行团队的能力。没有内部 owner，项目会死。
- **问题**：项目进入最后两周。请给出交接清单、验收标准与你如何验证客户团队真的能接。
- **参考答案**：
  1. **文档**：架构与 ADR、Runbook（告警 → 处理步骤）、评测集与运行方法、发布与回滚流程、权限与密钥清单、成本预算与告警、已知问题与路线图。
  2. **系统**：监控仪表盘与告警路由到客户值班；备份与恢复演练记录；IaC 全量在客户仓库；所有胶水代码有测试与 CI。
  3. **人**：指定内部 owner 与运行团队；培训（影子值班 → 反向影子：他们主导你旁观）；一线支持移交日期写进 WES。
  4. **验收**：客户团队独立完成一次发布 + 一次回滚 + 一次告警处理 + 一次评测运行；通过即交接完成。
  5. **产品化**：把可复用的胶水与模式抽回产品或内部库，给下一个客户。
  6. **心态**：FDE 的目标是系统好到能自运行、客户能接管——你在现场变得多余就是成功。
- **易错点 / 面试官关注**：
  - 交接 = 发一堆文档。
  - 没有「客户独立操作一次」的验收。
- **延伸**：Q18、Q28、[sre-reliability/sre-questions.md](../sre-reliability/sre-questions.md)
