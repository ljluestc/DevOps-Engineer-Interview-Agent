# 行为与架构面试题（10 题）

> 模板见 [../../docs/STANDARD.md](../../docs/STANDARD.md)。高级以上必考，考察系统视野、推动力与成长力。

### Q1.（STAR）讲一个你主导的重大故障排查 / 架构改造项目。
- **难度**：⚫ 资深
- **关键词**：STAR, 量化结果, 技术决策
- **概念速记**：Situation→Task→Action→Result，高级重点在「你推动并拍板」。
- **参考答案**：S 背景/规模→T 职责→A 你做了什么（技术决策）→R 量化结果（可用性 99.5%→99.95%、排障小时级→分钟级）。重点在「推动并拍板」，而非执行。
- **易错点**：只讲团队成果不突出个人决策与权衡。
- **延伸**：sre Q7（复盘）；Q2

### Q2. 如何推动跨团队技术改进落地（统一监控/容器化）？
- **难度**：⚫ 资深
- **关键词**：跨团队, 影响力, 试点, 标准化
- **概念速记**：靠影响力非职权，小试点出数据再推广。
- **参考答案**：对齐目标与收益（业务/稳定性价值）→ 小范围试点出数据 → 拉相关方共识（靠影响力）→ 分阶段推广+标准化（模板/平台降接入成本）→ 度量效果。体现沟通、权衡、韧性。
- **易错点**：一上来大推，无试点数据，难达共识。
- **延伸**：Q1、Q3

### Q3. 技术选型：自研 vs 开源 vs 云托管，怎么权衡？
- **难度**：⚫ 资深
- **关键词**：技术选型, 自研, 开源, 可移植性
- **概念速记**：核心能力可自研；通用能力用托管；避免强绑定单厂商。
- **参考答案**：维度：成本（人力/金钱）、可控性、演进风险、团队熟悉度、SLA。核心差异化能力可考虑自研/定制；通用能力（对象存储/MQ）用托管省心；避免重复造轮子，但关键路径避免强绑定单厂商（可移植）。
- **易错点**：什么都自研，维护成本失控；或什么都托管，被厂商绑定。
- **延伸**：cloud-security Q1；Q4

### Q4. 你如何带人 / 做技术规划？高级工程师还需具备什么？
- **难度**：⚫ 资深
- **关键词**：技术规划, 技术债, 培养, 系统视野
- **概念速记**：高级=技术深度+系统视野+兜底责任心。
- **参考答案**：带人：代码评审、复盘传导、给挑战性任务；规划：基于业务路线做 1~2 年技术债治理与平台路线图，平衡「救火」与「修堤」。
- **易错点**：只盯技术深度，忽视规划与培养。
- **延伸**：Q2、Q5

### Q5. 当业务方要求「既要快又要稳又要省」，你怎么回应与排序？
- **难度**：⚫ 资深
- **关键词**：权衡, SLO, 分层保障, 数据说话
- **概念速记**：用 SLO 定义「稳」底线，分阶段交付「快」，划边界保「省」。
- **参考答案**：拆解：SLO 定义稳的底线、MVP/分阶段交付快、省不牺牲核心可靠。用数据（错误预算、成本模型）争取资源与共识，必要时分层保障（核心链路高可用、非核心降级）。
- **易错点**：不排序全答应，结果都做不好。
- **延伸**：observability Q7（SLO/预算）；Q3

### Q6. 你遇到的最大技术失败/踩坑是什么？如何复盘与避免再犯？
- **难度**：⚫ 资深
- **关键词**：失败复盘, 成长, 无责复盘
- **概念速记**：真诚讲真实教训，重点在系统性改进。
- **参考答案**：真诚讲一个真实教训（非编完美），重点：当时判断、根因、承担什么、系统性改进（流程/工具/监控）。体现成长性与无责复盘思维，而非甩锅。
- **易错点**：编一个「完美无错」故事，显得不真实。
- **延伸**：sre Q7（无责复盘）；Q1

### Q7. 未来 1–2 年你所在领域的技术趋势与你的学习计划？
- **难度**：⚫ 资深
- **关键词**：技术趋势, 平台工程, AIOps, 持续成长
- **概念速记**：展现视野与持续学习能力。
- **参考答案**：视野：eBPF 统一可观测/网络、平台工程（Internal Developer Platform）、AIOps/智能告警、云原生 AI 基础设施（GPU 池化/推理平台）、FinOps。结合自学路径（源码、认证、项目实践）。
- **易错点**：只背名词无实质理解与学习计划。
- **延伸**：本仓库各模块；docs/ROADMAP.md

### Q8. 要让 AI Agent 进入运维链路（甚至能改生产），你怎么设计护栏？
- **难度**：⚫ 资深
- **关键词**：最小权限, 人在回路 HitL, 审批凭据, 沙箱, 可审计, 不可逆操作
- **概念速记**：2025 年 Replit 的 AI 助手在生产数据库上执行了删除操作，事后复盘的七条成因几乎全是**权限与流程问题**，而不是模型问题：AI 拥有近 root 的生产权限、没有权限边界、破坏性操作没有确认、没有 dry-run 环境、没有 RBAC、没有异常检测告警、以及对自主性的过度信任。这题考的是**「你把 Agent 当成什么」**。
- **参考答案**：
  1. **心智模型**：把 Agent 当作一个**能力很强、上下文可能错、且会被外部输入影响（提示注入）的新员工**。你不会给新员工生产 root，也不该给 Agent。
  2. **权限层（最重要）**：
     - 独立身份 + 最小权限，**绝不复用人的凭据**。
     - 用**权限边界**显式 Deny 不可逆动作（删除数据库/实例、改备份策略、动 IAM 本身），即使上层策略放开也拒绝。
     - 默认只读；写权限按操作类型、资源范围、时间窗口逐项授予。
     - 短期凭据（见 cloud-security Q13），不给长期 AK/SK。
  3. **人在回路（HitL）——关键是「批的是什么」**：
     - 区分两类：**交互式确认**（人当场看到并同意）与**异步审批**（工单/审批流）。
     - 真正的难点是**审批要能被「记住」并与实际执行的操作绑定**——批准的必须是「这一个具体操作的这一组具体参数」，而不是给 Agent 发一张通用通行证。否则 Agent 拿着批准去做了别的事，审计上无从分辨。
     - 审批凭据要**一次性、限定范围、有过期**，并在执行时被验证与记录。
  4. **执行层**：
     - 沙箱运行（隔离网络与文件系统），生产操作走**受控工具接口**而非任意 shell。
     - 强制 **dry-run / plan 先行**（`terraform plan`、`kubectl --dry-run=server`、`argocd app diff`），让人审查的是**将要发生的 diff**，不是 Agent 的自然语言描述。
     - 破坏性操作加**速率与规模阈值**（一次最多影响 N 个资源），超过就中断等待人工。
  5. **可观测与兜底**：全量审计日志（谁/什么身份/什么参数/什么结果）；异常行为告警（批量删除、权限变更）；**PITR 备份 + 演练过的恢复路径**（见 sre Q28）——最后一道防线永远是能恢复。
  6. **组织层**：明确 Agent 可以自主做什么（查询、诊断、生成 PR）、必须人工确认什么（任何写生产）、绝对不允许什么（碰备份与 IAM）。**把这件事写成明文策略，而不是靠默契。**
  7. **我的立场**（面试可以这么收尾）：现阶段让 Agent 在生产做**只读诊断 + 产出变更 PR** 是收益最高风险最低的组合——它省掉的是排查时间，而真正的执行仍然走已有的、被验证过的发布流程。
- **易错点**：只答「加个确认弹窗」——没想到审批凭据与具体操作的绑定问题；给 Agent 复用人的凭据导致审计无法区分；只做检测不做权限边界（检测到时已经删完了）。
- **延伸**：Q3、Q6、cloud-security Q2、Q13、sre Q28、来源：[Replit AI 事故复盘](https://medium.com/@ismailkovvuru/replit-ai-deletes-production-database-2025-devops-security-lessons-for-aws-engineers-4984c6e7a73d)、[Human-in-the-loop authorization patterns for agents (Christian Posta)](https://blog.christianposta.com/human-in-the-loop-authorization-patterns-for-agents/)

### Q9. 自动化程度怎么把握？什么时候「自动化过头」反而有害？
- **难度**：🔴 高级
- **关键词**：自动化权衡, 爆炸半径, 配置漂移, 人的判断, 自动化悖论
- **概念速记**：运维的默认价值观是「能自动化就自动化」，但自动化同时放大**正确操作**和**错误操作**。资深工程师的标志是能说清这个权衡，而不是无条件推崇自动化。
- **参考答案**：
  1. **自动化的两难**（Skyscanner 复盘里的原话大意）：把区域配置模板化，好处是避免**配置漂移**，坏处是一次改动会**同时铺满所有区域**。不模板化则相反。**两边都有代价，要选的是哪种代价更能承受、更容易发现。**
  2. **我的判断框架**：
     - **操作频率 × 出错代价**：高频低危 → 尽量全自动（部署、扩缩容）；低频高危 → 自动化"准备"环节但保留人工触发（DNS 切换、数据库主备切换、全局配置发布）。
     - **可逆性**：可逆的可以放开自动；不可逆的（删数据、删备份）永远留人工闸门。
     - **爆炸半径能否被限制**：能分批、能观察、能中止的自动化才是安全的自动化。**不能分批的全局自动化是最危险的一类。**
  3. **常见的「过头」形态**：
     - 自动修复掩盖了真实故障（自动重启把内存泄漏藏了半年，直到某天重启都救不回来）。
     - 自愈与人工应急打架（GitOps selfHeal 回滚掉救火扩容，见 cicd-iac Q21）。
     - 自动化链路本身没有可观测性，出问题没人知道它做了什么。
     - **自动化悖论**：日常全自动导致人失去手动操作的熟练度，真出事时没人会手动接管。对策是定期演练手动路径。
  4. **务实做法**：新自动化先跑 **dry-run/建议模式**，积累一段时间的「如果执行会发生什么」，确认判断准确后再放开执行；给每个自动化设**中止开关**并写进 runbook。
  5. **一句话收尾**：自动化要消除的是**重复劳动**，不是**人的判断**。判断该在哪里保留，正是架构设计的一部分。
- **易错点**：无条件说「越自动越好」；只讲收益不讲爆炸半径；没意识到自动修复可能掩盖问题。
- **延伸**：Q3、Q6、sre Q26、Q27、cicd-iac Q21

### Q10. 事故当中你怎么沟通？如果是你在指挥，前 15 分钟做什么？
- **难度**：🔴 高级
- **关键词**：止血优先, 事实与推测分离, 信息节奏, 升级决策, 无责
- **概念速记**：这题考的是**压力下的结构化行为**，不是技术方案。面试官想听到「先做什么、怎么排序、怎么和人协作」。
- **参考答案**（建议用 STAR 讲一个真实案例，框架如下）：
  1. **前 15 分钟的动作顺序**：
     - **① 确认影响面（2 分钟）**：谁受影响、多大比例、是否还在恶化。先看用户侧 SLI（成功率/延迟），不要一头扎进日志。
     - **② 定级并拉人**：按分级决定要不要拉 IC 和更多团队。**宁可高估一级**——降级容易，升级晚了很贵。
     - **③ 明确目标是止血**：当众说一句「我们现在的目标是恢复服务，根因稍后查」。这一句能防止团队跑偏去追根因。
     - **④ 找最近的变更**：**大多数故障来自变更**（见 sre Q18），先问「最近 1 小时发了什么/改了什么配置」，能回滚就先回滚。
     - **⑤ 建立节奏**：开专用频道、指定记录人、约定 15–20 分钟同步一次。
  2. **沟通的三条原则**：
     - **事实与推测分开说**：「监控显示 A 服务错误率 40%（事实）；我怀疑和 10 分钟前的配置变更有关，正在验证（推测）」。混在一起会误导别人做错决策。
     - **对外通报讲影响不讲内部细节**：「部分用户下单失败，正在处理，预计 X 分钟后更新」，而不是「etcd leader 切换了」。
     - **不确定就说不确定**，并给下次更新的时间点。沉默比坏消息更伤信任。
  3. **我会主动做但容易被忽略的事**：
     - 指定一个人**专职对外**，把干扰挡在修复团队之外。
     - 让记录人**实时记时间线**（事后靠回忆一定失真，且部分日志会被自动清理）。
     - 缓解之后**明确宣布事故结束**，并当场定下复盘时间——否则复盘永远被排到「下周」然后不了了之。
  4. **事后**：无责复盘，改进项必须有**责任人和截止时间**并进入正常的迭代排期，否则复盘只是仪式（见 sre Q7、Q29）。
- **易错点**：一上来就深挖根因，迟迟不止血；不通报或过度通报技术细节；复盘产出一堆没人认领的改进项。
- **延伸**：Q1、Q6、sre Q1、Q7、Q29
