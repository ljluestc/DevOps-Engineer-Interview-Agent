### Q1. 你的线上故障排查方法论是什么？
- **难度**：🔴 高级
- **关键词**：排障方法论, 止血优先, 黄金信号
- **概念速记**：先恢复再定位；四黄金信号圈范围。
- **参考答案**：先恢复（止损优先于定位）→ 再定位。四黄金信号（延迟/流量/错误/饱和度）快速圈定；分层（接入→应用→中间件→存储→主机→网络）；监控+日志+链路交叉；二八先找最可能是瓶颈的一层。止血手段（回滚/扩容/限流/摘流）要熟练且可一键。
- **易错点**：花大量时间定位而不先止血，扩大影响。
- **延伸**：observability Q；Q2

### Q2. 线上 CPU 飙到 100% 排查步骤？
- **难度**：🔴 高级
- **关键词**：CPU 100%, 热点, perf, 死循环
- **概念速记**：先定位进程/线程，再下钻栈。
- **参考答案**：`top` 定位进程/线程→`top -Hp <pid>`→线程号转十六进制→`jstack`/`perf`/`pstack` 看栈；`perf top -p <pid>`。区分：计算型、GC 频繁（Java）、死循环、锁竞争（sys 高）。容器看 cgroup 限额。
- **易错点**：只看整体 CPU 不看单线程热点。
- **延伸**：linux Q6、Q12

### Q3. 服务雪崩怎么发生？限流/熔断/降级/隔离分别应对？
- **难度**：🔴 高级
- **关键词**：雪崩, 限流, 熔断, 降级, 隔离
- **概念速记**：依赖变慢→线程池占满→连锁阻塞→整体不可用。
- **参考答案**：限流（控 QPS，护己）；熔断（依赖错误率超阈值快失败，半开探测恢复，如 Sentinel/Hystrix）；降级（返回兜底/关非核心）；隔离（舱壁/线程池/信号量，故障不扩散）。区分熔断（依赖侧）与降级（业务侧）。
- **易错点**：把降级当熔断，或只做限流不隔离。
- **延伸**：Q4、Q13（级联故障）

### Q4. 多活 vs 主备？脑裂怎么防？Raft/ZAB 核心思想？
- **难度**：⚫ 资深
- **关键词**：多活, 主备, 脑裂, Raft, 多数派
- **概念速记**：脑裂靠多数派（quorum）+ fencing 防。
- **参考答案**：主备（一主一从，切换有 RTO，利用率低）；多活（多机房同时服务，高可用但一致性/路由复杂）。脑裂防：多数派（>N/2 才能当选）、fencing（隔离旧主）、租约（lease 到期退位）。Raft：Leader 选举+日志复制+安全性（多数派确认，Term 防旧主）。
- **易错点**：双活无仲裁，网络分区出现双主写冲突。
- **延伸**：kubernetes Q40（etcd/Raft）；Q5

### Q5. 容量规划怎么做？如何估算需要多少机器？
- **难度**：🔴 高级
- **关键词**：容量规划, 压测, 冗余系数, 峰值
- **概念速记**：目标峰值 × 冗余 ÷ 单机容量。
- **参考答案**：确定 SLI（QPS/RT）→ 压测得单机容量（QPS/核、内存/连接瓶颈）→ 按目标峰值×冗余（1.3~2）×多 AZ → 算资源。考虑峰值/均值比、增长曲线、有状态状态量、带宽。工具：wrk/JMeter/ghz，结合历史监控趋势外推。
- **易错点**：按均值规划，大促峰值打垮。
- **延伸**：Q14（峰值突发）；observability Q7（SLO）

### Q6. 混沌工程是什么？如何在真实环境安全做？
- **难度**：🔴 高级
- **关键词**：混沌工程, Chaos Mesh, 韧性验证
- **概念速记**：主动注入故障验证系统韧性。
- **参考答案**：注入故障（kill pod、断网、延迟、丢包）验证。原则：先有稳定 SLI/SLO 与监控，低风期、小范围、可一键恢复；工具 Chaos Mesh/Litmus。把「以为能扛」变「验证过能扛」。
- **易错点**：无监控无回滚直接在生产注入大故障。
- **延伸**：Q16（GameDay）；Q1

### Q7. 一次无责复盘（blameless postmortem）结构？
- **难度**：🔴 高级
- **关键词**：无责复盘, 根因, 5 Why, 动作
- **概念速记**：对事不对人，聚焦系统/流程缺陷。
- **参考答案**：时间线（客观）→ 影响面（用户/营收）→ 根因（5 Why/鱼骨）→ 关键动作（止血/根治/预防，带 owner+deadline）→ 经验沉淀。聚焦监控缺失、告警不灵、变更无审批等系统缺陷。
- **易错点**：复盘变成追责会，没人敢说真话。
- **延伸**：Q16、observability Q16（Incident）

### Q8. RTO 与 RPO 区别？灾备方案怎么定？
- **难度**：🟡 中级
- **关键词**：RTO, RPO, 灾备, 备份
- **概念速记**：RTO=恢复时间；RPO=允许丢多少数据（决定备份频率）。
- **参考答案**：核心 RPO≈0（同步复制/多活）、RTO 分钟级；非核心可小时级/日备。方案：主从/同城双活/异地灾备 + 快照+异地归档。
- **易错点**：RPO 设 0 但实际异步复制，故障丢数据。
- **延伸**：Q4、middleware Q（备份演练）

### Q9. 限流算法：计数器/滑动窗口/令牌桶/漏桶区别？
- **难度**：🔴 高级
- **关键词**：限流, 令牌桶, 漏桶, 滑动窗口
- **概念速记**：令牌桶允许突发；漏桶强制恒定输出。
- **参考答案**：计数器（简单但有临界突刺）；滑动窗口（平滑）；令牌桶（平均速率恒定、允许突发，常用）；漏桶（强制恒定输出，削峰填谷）。API 网关多令牌桶+漏桶；分布式限流用 Redis/哨兵。
- **易错点**：固定窗口临界突刺两倍限流值。
- **延伸**：Q3

### Q10. 分布式锁（Redis/ZooKeeper/etcd）怎么实现与注意？
- **难度**：🔴 高级
- **关键词**：分布式锁, Redlock, 租约, 死锁
- **概念速记**：锁必须带超时防死锁，释放须校验持有者。
- **参考答案**：Redis（SET NX + 过期，Redlock 争议）；ZK/etcd（临时节点/租约，自动释放，强一致）。注意：超时防死锁、释放校验持有者（防误删）、网络分区下正确性权衡（CAP）。推荐 etcd/ZK 强一致锁。
- **易错点**：锁超时但业务未跑完，被别人抢走导致并发写。
- **延伸**：middleware Q（Redis）；Q3

### Q11. 幂等设计为什么重要？常见实现方式？
- **难度**：🔴 高级
- **关键词**：幂等, 去重, 乐观锁, 状态机
- **概念速记**：防重试/重发导致重复下单/扣款。
- **参考答案**：实现：唯一 ID+去重表、乐观锁(version)、状态机、Token 机制、Redis 原子校验。写入/支付类必考。
- **易错点**：只在前端防重复提交，后端无幂等。
- **延伸**：middleware Q（MySQL）

### Q12. 缓存击穿/穿透/雪崩区别与应对？
- **难度**：🔴 高级
- **关键词**：缓存击穿, 穿透, 雪崩, 布隆过滤器
- **概念速记**：击穿=热点失效瞬压 DB；穿透=查不存在；雪崩=大量同时失效。
- **参考答案**：击穿：互斥锁/逻辑过期/热点不过期。穿透：布隆过滤器/空值缓存。雪崩：随机过期/多级缓存/高可用。Redis 运维必考。
- **易错点**：把三者混为一谈，用一种方案应对所有。
- **延伸**：middleware Q（Redis）

### Q13. 级联故障（cascading failure）如何阻断？
- **难度**：⚫ 资深
- **关键词**：级联故障, 超时, 熔断, 有界队列
- **概念速记**：每跳加超时/熔断/隔离，失败快速返回而非堆积。
- **参考答案**：识别关键依赖链；每跳加超时/熔断/限流/隔离；失败快速返回而非堆积；队列有界；降级非核心；容量冗余；依赖异步化。监控依赖健康，自动摘流。
- **易错点**：无超时导致请求无限堆积拖垮整链。
- **延伸**：Q3、Q12

### Q14. 容量评估中的「峰值/均值比」与突发怎么处理？
- **难度**：🔴 高级
- **关键词**：峰值均值比, 突发, 弹性, 预热
- **概念速记**：业务突发可达均值数倍，需弹性+缓冲。
- **参考答案**：压测覆盖峰值而非均值；处理：弹性扩缩（HPA/Karpenter）、预留缓冲、预热（缓存/连接池）、限流保底、多 AZ 分散。
- **易错点**：按日均规划，大促/秒杀打垮。
- **延伸**：Q5；kubernetes Q6（HPA）

### Q15. 如何用 SRE 的「可靠性曲线」做投入决策？
- **难度**：⚫ 资深
- **关键词**：可靠性曲线, 边际成本, 错误预算
- **概念速记**：可靠性提升到一定点边际成本指数上升。
- **参考答案**：SRE 主张把错误预算投入「合理可靠性 + 功能速度」平衡，而非无限堆可靠。用数据驱动：哪类投入降低最多故障/损失。
- **易错点**：追求 100% 可靠，成本失控且拖累交付。
- **延伸**：observability Q7（Error Budget）

### Q16. 如何建设「故障演练 / GameDay」文化？
- **难度**：⚫ 资深
- **关键词**：GameDay, 演练, 韧性, 复盘
- **概念速记**：定期演练把韧性从文档变肌肉记忆。
- **参考答案**：定期选场景（断节点、杀 Pod、断网、加延迟），跨团队参与，验证监控/告警/预案/响应，事后复盘改进。
- **易错点**：演练只在文档里，从不实操。
- **延伸**：Q6、Q7

### Q17. 监控发现「饱和度」高但还没报错，怎么前瞻处理？
- **难度**：🔴 高级
- **关键词**：饱和度, 预测性告警, 扩容
- **概念速记**：饱和度（磁盘/CPU/连接）是 Four Golden Signals 之一，常被忽视。
- **参考答案**：设预测性告警（趋势/利用率阈值，如磁盘 80% 预警、连接数 70% 预警）；提前扩容/清理/优化；而非等饱和致故障。
- **易错点**：只告警「已故障」，不告警「将故障」。
- **延伸**：observability Q（黄金信号）

### Q18. 变更管理（Change Management）流程？为什么大多数故障来自变更？
- **难度**：🔴 高级
- **关键词**：变更管理, 灰度, 回滚, 冻结期
- **概念速记**：统计显示 70%+ 故障源于变更。
- **参考答案**：提出→评审→审批→灰度→监控→全量→复盘。小步、可回滚、可观测、灰度、自动化校验。设变更冻结期与快速回滚机制。
- **易错点**：大变更一次性全量，无回滚。
- **延伸**：Q7、Q19（配置/人为故障）

### Q19. 配置错误与人为误操作导致的故障如何预防与恢复？
- **难度**：🔴 高级
- **关键词**：配置错误, 误操作, 护栏, 审计
- **概念速记**：最小权限 + 双人复核 + 自动化护栏。
- **参考答案**：预防：配置校验（schema）、灰度推送、审批、dry-run、默认值安全、回滚。恢复：配置中心一键回滚、版本化、审计。误操作：最小权限、双人复核、变更窗口、操作审计、演练回滚。
- **易错点**：root 账号多人共用，误 `rm` 无审计。
- **延伸**：Q18、cloud-security Q（安全基线）

### Q20. 应急预案（Runbook / Playbook）怎么写才有效？
- **难度**：🟡 中级
- **关键词**：Runbook, 止损步骤, 演练
- **概念速记**：每种 SEV 级故障有可执行、可验证、常更新的预案。
- **参考答案**：现象→影响→止损步骤（明确命令/一键脚本）→升级路径→owner。平时演练（game day），而非故障时现查。
- **易错点**：预案写「联系 XX」却无具体命令，故障时用不上。
- **延伸**：Q16、Q7

### Q21. 全链路压测怎么做？生产压测的风险控制？
- **难度**：⚫ 资深
- **关键词**：全链路压测, 影子流量, 数据隔离
- **概念速记**：用影子流量打标隔离，验证真实容量。
- **参考答案**：构建影子库/影子流量（流量复制打标、隔离存储），压测模型贴合真实，逐步放量，实时监控 SLO，一键停。风控：限流保护、数据隔离（影子表）、低峰期、应急预案。
- **易错点**：压测流量写入真实库，污染生产数据。
- **延伸**：Q5、Q14

### Q22. 数据库慢查询怎么排查（MySQL）？
- **难度**：🟡 中级
- **关键词**：慢查询, EXPLAIN, 索引, 锁等待
- **概念速记**：慢查询日志 + EXPLAIN 看执行计划。
- **参考答案**：`slow_query_log` + `EXPLAIN`（是否走索引、扫描行数、filesort）；`SHOW PROCESSLIST` 看阻塞；索引缺失/失效（函数包裹、隐式转换）、锁等待、大表 JOIN、buffer pool。优化：加索引、改写、调参、分库分表。
- **易错点**：对索引列用函数导致索引失效。
- **延伸**：middleware Q（MySQL）

### Q23. 消息积压（Kafka/RabbitMQ）怎么排查与处理？
- **难度**：🔴 高级
- **关键词**：消息积压, lag, 消费慢, 分区
- **概念速记**：lag 大 = 消费速率 < 生产速率。
- **参考答案**：看消费 lag（`kafka-consumer-groups`）、分区数与消费者数。处理：加消费者/分区、提并行、优化消费逻辑、必要时重置 offset（谨慎）、削峰（限流上游）。根因多为消费慢或分区不均。
- **易错点**：只加消费者不增加分区，消费者分不到分区。
- **延伸**：middleware Q（Kafka）

### Q24. 如何用 Error Budget 做「发布冻结」治理？
- **难度**：⚫ 资深
- **关键词**：Error Budget, 发布冻结, 燃尽
- **概念速记**：预算耗尽则冻结发布，优先稳定性。
- **参考答案**：定义 SLI/SLO，预算政策（耗尽冻结、燃尽率告警），复盘预算消耗事件。公示 dashboard 让团队共识，避免空谈 100%。
- **易错点**：预算政策定而不执行。
- **延伸**：observability Q7；Q15

### Q25. 高可用架构的「单点」如何识别与消除？
- **难度**：⚫ 资深
- **关键词**：单点, 冗余, 多活, 依赖
- **概念速记**：任何「挂了就全挂」的组件都是单点。
- **参考答案**：识别：画依赖图找无冗余节点/服务/网络/数据。消除：冗余（多副本/多 AZ）、无状态化、数据多副本+选主、健康检查+自动切换、消除隐式单点（如单机缓存、单机定时任务）。定期混沌验证。
- **易错点**：应用多副本但底层依赖单点数据库未冗余。
- **延伸**：Q4、Q13

### Q26. 案例复盘：一次模板改动让 GitOps 在全球删掉了 478 个服务，你能学到什么？
- **难度**：⚫ 资深
- **关键词**：配置即代码, 全局变更, GitOps 双刃剑, 爆炸半径, 事故学习
- **概念速记**：Skyscanner 2021 年的公开复盘——工程师改了一个**根部的模板配置文件**，漏掉了一对 `{{ }}`，模板渲染失效，所有 namespace 的配置被污染；Argo CD 按 GitOps 的承诺**忠实地**把集群调谐成了「没有有效 namespace」的状态，于是删掉了全球所有区域、所有可用区里的 478 个服务。
- **参考答案**：
  1. **第一课：配置一旦带上模板和逻辑，它就是代码**。团队给配置引入了模板与条件判断，却没有随之引入**测试、linting、渲染结果 diff 评审**——因为「它只是配置」。防线：CI 里做 `helm template`/`kustomize build` 的渲染校验、schema 校验（kubeconform）、**把渲染后的 diff 贴到 PR 上让人看到真实影响**。
  2. **第二课：不要做全局配置发布**。这个文件因为「很少改」而没有被纳入分批发布机制，改动直接全球生效。防线：所有变更——包括配置——都要有**分区/分批次**的发布路径，先一个 AZ、再一个 region；越是「很少改」的东西越危险，因为没人记得它的爆炸半径。
  3. **第三课：GitOps 的自动化是双向放大器**。它能让正确配置秒级铺满全球，也能让错误配置秒级摧毁全球。**自动化程度是需要权衡的，不是越高越好**——团队事后自问「我们真的需要按区域模板化这个配置吗？不模板化的代价是配置漂移，模板化的代价是全局爆炸」。
  4. **第四课：备份没恢复过就不算备份**。他们的备份是好的，但一个 **IAM 策略变更**让备份在最关键的时刻难以取出。防线：定期做**真实恢复演练**，并把「恢复路径上的权限」纳入演练范围。
  5. **第五课：runbook 要为凌晨三点的疲惫工程师写**。步骤是否幂等？上下文是否清晰？这是可用性文档的 UX 问题。
  6. **做对的地方也要学**：正因为用了 GitOps（拉模式自愈），配置恢复后集群能**自己调谐回正确状态**，而不需要从中心逐个推送——这大幅缩短了恢复时间；有经验的 **Incident Commander** 坐镇、全程无责氛围，是 4.5 小时内恢复核心服务的关键。
- **易错点**：只总结成「要多加评审」——这条改动**是经过评审的**；把责任归到个人而不是系统（无 linting、无分批、无爆炸半径控制）。
- **延伸**：Q7、Q18、Q27、Q28、cicd-iac Q21、来源：[Skyscanner Engineering - How a couple of characters brought down our site](https://medium.com/@SkyscannerEng/how-a-couple-of-characters-brought-down-our-site-356ccaf1fbc3)

### Q27. 「配置即代码」之后，配置该怎么测试和灰度？
- **难度**：🔴 高级
- **关键词**：渲染校验, policy as code, 分批发布, 爆炸半径, dry-run
- **概念速记**：配置的变更频率远高于代码，但配置的**测试基础设施**通常远弱于代码。绝大多数「低级失误型」故障（Q18 说的变更类故障）都发生在这条缝里。
- **参考答案**：
  1. **分层防线（从便宜到昂贵）**：
     - **语法/schema**：`yamllint`、`kubeconform`（对着 K8s OpenAPI schema 校验）、Helm `--strict`。
     - **渲染校验**：CI 里执行 `helm template` / `kustomize build`，**渲染失败直接挂 PR**——Skyscanner 那次就是渲染语义失效但没人校验。
     - **策略校验（policy as code）**：Conftest/OPA、Kyverno 的 CLI，检查「是否设了 resources」「镜像是否来自可信仓库」「是否有 PDB」这类**组织规则**。
     - **渲染 diff 评审**：把「变更前后的渲染结果 diff」自动贴到 PR。**人评审的应该是最终生效的 YAML，而不是模板源码**——这是最能防住模板类错误的一招。
     - **服务端 dry-run**：`kubectl apply --dry-run=server` 或 `argocd app diff`，让 API Server 的 admission 链也参与校验。
  2. **灰度发布配置**：
     - 按环境分层（dev → staging → prod），且**生产内部再分批**（一个 AZ → 一个 region → 全球）。
     - 对全局性配置（网络策略、CNI、准入策略）尤其要有分批机制，并在每批之间设**观察窗口**与自动中止条件。
     - 关键配置加**金丝雀标记**：先对 1% 的工作负载生效。
  3. **爆炸半径设计**：
     - 把配置按影响范围**分级**（单应用 / 单集群 / 全局），级别越高审批和分批要求越严。
     - 用 AppProject/RBAC 限制谁能改全局配置（见 cicd-iac Q23）。
  4. **可回滚性**：配置回滚 = Git revert + 同步，要保证它**真的能在几分钟内完成**并演练过；对不可回滚的变更（数据库 schema、数据迁移）要单独走更严的流程。
- **易错点**：只做 YAML 语法检查就以为够了；评审模板而不评审渲染结果；生产内部不分批。
- **延伸**：Q18、Q19、Q26、cicd-iac Q21、Q22

### Q28. 为什么备份常常在最关键的时刻不可用？怎么验证？
- **难度**：🔴 高级
- **关键词**：恢复演练, RTO 验证, 权限依赖, 循环依赖, 备份完整性
- **概念速记**：**「备份不是备份，恢复成功才是备份。」** 绝大多数备份失效不是因为数据坏了，而是因为**恢复路径上的某个环节从没被验证过**。
- **参考答案**：
  1. **典型失效模式**：
     - **权限**：恢复需要的 IAM 角色/密钥被改了或过期了（Skyscanner 事故中就是 IAM 策略变更让备份难以取出，见 Q26）。
     - **循环依赖**：恢复流程依赖的系统自己也挂了——恢复脚本放在要恢复的那个集群里、解密密钥存在挂掉的 Vault 里、镜像仓库和被恢复的服务同生共死。
     - **完整性**：备了数据没备 schema/配置；备了主库没备关联的对象存储；快照是崩溃一致而非应用一致。
     - **时效**：能恢复，但要 20 小时，远超 RTO 承诺。
     - **规模**：单库恢复演练过，但没试过「整个 region 全挂」的量级。
  2. **验证方法**：
     - **定期真实恢复演练**（季度级），恢复到隔离环境并做**数据校验**（行数/校验和/关键业务查询）。
     - **测量而不是估计 RTO/RPO**：把恢复耗时记录下来对照 SLA（见 Q8）。
     - **断依赖演练**：假设「身份系统不可用」「主 region 完全不可达」，恢复路径是否还成立。恢复所需的凭据要有**离线/带外**的获取方式。
     - 把恢复流程本身纳入 GameDay（见 Q16）。
  3. **设计原则**：
     - 备份存**另一个账号/另一个 region**，且用**不同的权限体系**（防勒索与防误删同时生效），开对象存储的**对象锁/不可变**保留。
     - 遵循 3-2-1（3 份、2 种介质、1 份异地）。
     - 恢复文档独立于被恢复系统存放（打印件/离线副本听起来老派但真的救过命）。
  4. **和 GitOps 的配合**：声明式配置在 Git 里本身就是一种「配置备份」——集群重建后能自愈回正确状态（Q26 的正面教训）；但**有状态数据仍然必须单独备份**，GitOps 不管数据。
- **易错点**：只监控「备份任务成功」而从不恢复；恢复演练只在理想条件下做；备份和生产在同一个账号同一套权限下。
- **延伸**：Q8、Q16、Q26、kubernetes Q40

### Q29. 事故指挥（Incident Commander）制度怎么运作？为什么它比技术能力更能决定恢复速度？
- **难度**：🔴 高级
- **关键词**：Incident Commander, 角色分工, 事故分级, 沟通节奏, 无责文化
- **概念速记**：大型事故的瓶颈往往不是「没人知道怎么修」，而是**十个人同时在查、互相不知道对方在做什么、决策没人拍板、外部一直在打断**。IC 制度用**明确的角色分工**解决这个协调问题。
- **参考答案**：
  1. **核心角色**（借鉴 Google/PagerDuty 的 ICS 模型）：
     - **Incident Commander（指挥）**：**不动手修**，只负责决策、分派任务、控制节奏、决定升级。这是最反直觉也最关键的一条——让最强的工程师当 IC 反而是浪费，IC 需要的是协调而非技术深度。
     - **Operations Lead**：带队实际执行修复。
     - **Communications Lead**：对内对外通报（客服、管理层、客户），**把干扰从修复团队身上挡掉**。
     - **Scribe**：记录时间线——事后复盘的质量完全取决于时间线的完整度，而事后再回忆必然失真且部分日志已被自动清理。
  2. **分级与触发**：按影响面（用户数/收入/数据）定 SEV1–SEV4，不同级别对应不同的响应时间、通报范围和是否拉 IC。**分级要能快速判定**，不能变成开会讨论。
  3. **节奏控制**：固定间隔（如每 20 分钟）同步一次状态，即使「没有进展」也要说——这能防止外部反复插话，也能强迫团队定期跳出细节看全局。
  4. **为什么影响恢复速度**：
     - 避免多人重复劳动或互相踩踏（两个人同时重启同一个组件）。
     - 减少「缓解 vs 根因」的摇摆——**IC 的首要职责是明确「现在的目标是止血，不是找根因」**。
     - 挡住干扰，让工程师能连续思考。
     - **无责（blameless）氛围**由 IC 建立，直接决定信息是否被如实、及时地暴露出来。
  5. **落地建议**：IC 要**轮值和培训**（不能只有一个人会），有 checklist 和事故频道模板，演练时也任命 IC。事后由**外部引导者**（其他团队的资深工程师）主持复盘评审，避免自我辩护。
- **易错点**：让 IC 自己下场修（协调立刻失效）；没有专人做记录导致复盘靠回忆；只在超大事故时才用 IC，平时不演练所以真到时候用不起来。
- **延伸**：Q1、Q7、Q16、Q26、behavior Q1
